# Smartup Hub

Портал клиентов Smartup: обращения в поддержку, база решений, идеи по продукту. Адрес: `hub.smartup24.com`.

Состояние: вехи M0 (основа проекта), M1 (вход и личность), M2 (обращения клиента), M3 (рабочее место агента и сроки) и M4 (уведомления и почта) готовы и слиты в `main`. Веха M4b (уведомления в Telegram и выбор каналов) слита в `main`. Веха M8 (передача в разработку, правила автоматизации, макросы, теги, вебхуки, показатели) слита в `main`, отчёт `docs/plans/M8-report.md`. Веха M5 (решения, редактор, переводы, подсказка при создании обращения) готова на ветке, отчёт `docs/plans/M5-report.md`. Веха M5b (AI-помощник Тез первой линии, разбор обращения, очереди после AI, показатели помощника) готова на ветке на заглушке модели, отчёт `docs/plans/M5b-report.md`; проверочный набор помощника: `pnpm eval:ai`. Веха M5c (известные проблемы, рассылки, объявления, Тез и известная проблема, кандидаты в решения) готова на ветке на заглушках модели и векторов, отчёт `docs/plans/M5c-report.md`. Веха M8b (сервер MCP `POST /api/mcp` для внутренних AI-агентов, токены с перечнем инструментов, обезличивание, журнал вызовов, события агенту, всплески сигнатур, раздел "Сводки") готова на ветке на тестовом клиенте MCP, отчёт `docs/plans/M8b-report.md`; инструкция для команды агентов `docs/guides/agents.ru.md`. Веха M8c (знания из кода: отчёт о сканировании инструментом `code_catalog_upsert`, очередь утверждения, точные сигнатуры по утверждённым шаблонам, блок "Что известно по коду", "Разобрать по коду", решение из записи) готова на ветке на отчёте-примере и тестовом клиенте MCP, отчёт `docs/plans/M8c-report.md`. Веха M9 (готовность к пилоту), часть A, готова на ветке: перечень требований раздела 7, согласие на AI-обработку, сводка пилота, срок бездействия сотрудника, документы безопасности, сигналы ресурсов сервера, сценарии проверки сервера и почты, черновики юридических текстов; отчёт `docs/plans/M9-report.md`, сверка `docs/plans/M9-readiness.md`. Часть B (staging, production, люди) ждёт материалов владельца. По техническому аудиту (`docs/audit/`) сделана волна 0 плана оптимизации: готовность к staging (`docs/plans/W0-report.md`). Отчёты: `docs/plans/M<n>-report.md`. Порядок следующих вех: `docs/plans/README.md`.

Запуск на сервере (staging и production): все шаги по порядку в `docs/runbooks/launch.md`. Ниже описан запуск на машине разработчика.

## Что нужно

- Node.js 26 (точная версия в `.node-version`)
- pnpm 12 (версия в `package.json`)
- Docker с Compose

## Запуск одной командой

```bash
pnpm install
pnpm dev:up
```

`pnpm dev:up` создаёт файл `.env` со случайными паролями (если его нет), поднимает PostgreSQL, создаёт роли базы, применяет миграции и запускает приложение. Через минуту:

- `http://localhost:3000/ru` - кабинет клиента;
- `http://localhost:3000/ru/agent` - рабочее место сотрудника;
- `http://localhost:3000/api/ready` - готовность, ответ `{"status":"ready","checks":{"db":"ok"}}`.

Витрина компонентов открывается по адресу `/ru/dev/ui`, если в `.env` задано `HUB_SHOWCASE=1`.

### Как войти на своей машине

- Клиент: `pnpm dev:oidc` в соседнем окне поднимает ложные серверы Smartup (`pnpm dev:up` уже записал их в реестр). На `/ru/login` кнопка "Войти через Smartup" открывает форму ложного сервера: любой идентификатор, имя и компания. Роль `director` даёт администратора клиента.
- Сотрудник: `pnpm hub staff:create --email you@smartup.example --name "Имя" --role admin` печатает ссылку. По ней задаётся пароль, при первом входе на `/ru/staff/login` подключается второй фактор (любое приложение с кодами).
- Письма со ссылками входа в разработке печатаются в окне приложения (`MAIL_TRANSPORT=console`) или пишутся в каталог (`file`).
- Бот Telegram: `pnpm dev:telegram` поднимает ложный Bot API на порту 3192, в `.env` задаются `TELEGRAM_API_URL=http://localhost:3192`, `TELEGRAM_BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET`.
- Таск-менеджер разработки: по умолчанию ручной режим (`DEV_TRACKER=manual`), портал никуда не обращается. Для режима API `pnpm dev:tracker` поднимает ложный таск-менеджер на порту 3194; переменные и предполагаемый договор описаны в `docs/integrations/dev-tracker.md`.

| Команда | Что делает |

| `pnpm dev:up` | База, миграции и приложение для разработки |
| `pnpm dev` | Только приложение для разработки |
| `pnpm build`, `pnpm start` | Сборка и запуск собранного приложения |
| `pnpm check` | Типы, линтер и проверки правил ТЗ: тире, запрет кеша, токены оформления, переводы, контраст, шрифт |
| `pnpm test` | Модульные тесты |
| `pnpm test:integration` | Тесты с базой данных (PostgreSQL в контейнере) |

| `pnpm budget` | Размер скриптов первого экрана, предел 170 КБ |
| `pnpm lighthouse` | Lighthouse: скорость не ниже 0,85, доступность не ниже 0,95 |
| `pnpm db:bootstrap`, `pnpm db:migrate` | Роли базы и миграции |
| `pnpm fonts:build` | Файлы шрифта для веба из шрифта пакета бренда |
| `pnpm hub <команда>` | Команда консоли: сотрудники и серверы Smartup (раздел ниже) |
| `pnpm dev:oidc` | Ложные серверы Smartup для входа клиента: облако на порту 3190, выделенный сервер на 3191 (решение 0013) |
| `pnpm dev:telegram` | Ложный Telegram Bot API на порту 3192 (решение 0018) |
| `pnpm dev:tracker` | Ложный таск-менеджер Smartup на порту 3194 для режима `DEV_TRACKER=smartup` (`docs/integrations/dev-tracker.md`) |

Перед каждым коммитом: `pnpm check`, `pnpm test` и `pnpm test:integration`.

## Первый администратор и серверы Smartup

Сотрудников и серверы Smartup до появления экранов администратора ведёт команда консоли `hub`. В разработке: `pnpm hub <команда>`, на сервере в контейнере: `node hub.mjs <команда>`. Каждое изменение пишется в журнал аудита.

```bash
# Первый администратор портала (FR-ID-12): команда печатает одноразовую ссылку на 24 часа.
# По ссылке человек сам задаёт пароль, затем при первом входе подключает второй фактор.
pnpm hub staff:create --email admin@smartup24.com --name "Имя Фамилия" --role admin

# Сотрудник потерял телефон с кодами: пароль и второй фактор удаляются, все сессии завершаются, печатается новая ссылка.
pnpm hub staff:reset --email admin@smartup24.com

# Сервер Smartup. Секрет клиента OAuth не передаётся аргументом: он берётся из переменной
# HUB_OAUTH_CLIENT_SECRET или спрашивается без отображения на экране.
pnpm hub server:add --code cloud --name "Облако Smartup" --base-url https://cloud.smartup.example \
  --issuer https://id.smartup.example --client-id hub --default
pnpm hub server:list
pnpm hub server:disable --code cloud
pnpm hub server:check --code cloud

# Справочник модулей из выгрузки Smartup (поле "Модуль" в форме обращения). Справочник меняет только администратор:
# загрузка идёт от имени действующего администратора с этим адресом. Модули добавляются и обновляются по коду,
# отсутствующие в файле скрываются. При ошибке справочник не меняется, команда называет запись и строку.
pnpm hub modules:import --file modules.json --admin admin@smartup24.com

# Удалить просроченные служебные строки вручную (решение 0023). С вехи M2 то же делает ночная задача
# фонового процесса в 03:00 по Ташкенту (решение 0028).
pnpm hub maintenance:cleanup
```

Файл справочника: массив модулей вида `{ "code": "orders", "parentCode": null, "name": { "ru": "Заказы", "uz": "Buyurtmalar", "en": "Orders" }, "screens": [{ "code": "order_new", "name": { "ru": "Новый заказ" } }] }`. Русское название обязательно.

Адреса сервера принимаются только внешние и только по https (исключение: сам портал запущен на localhost). Команда `server:add` печатает адрес возврата, который нужно сообщить разработчикам Smartup при регистрации портала как клиента OAuth. Команда `server:check` проверяет документ discovery, адреса входа, ключи и PKCE S256. То же самое администратор портала делает в рабочем месте: "Настройки", раздел "Серверы Smartup" (решение 0019).

## Как устроено

- Одно приложение Next.js и одна база PostgreSQL. Данные клиентов разделены политиками RLS: сервис обращается к базе только через `withActor` (`src/db/with-actor.ts`).
- Код модулей лежит в `src/modules/<префикс>`, имена таблиц и файлов описаны в `docs/naming.md`.
- Тексты интерфейса лежат в `messages/`, языки перечислены в `src/i18n/locales.ts`. Новый язык: одна правка этого файла и один файл сообщений.
- Оформление задаётся токенами `src/ui/tokens.css` в три слоя. Новая поставка Smartup Web меняет только слой 1.
- Вход: клиенты через свой сервер Smartup, по ссылке на подтверждённый email или из бота Telegram; сотрудники по паролю и обязательному коду второго фактора. Таблицы идентичности работают под отдельной ролью базы `hub_auth` через `withIdentity`.
- Внешние сервисы (Cloudflare Turnstile, Resend, Telegram, Cloudflare R2, ClamAV) включаются ключами в окружении; без ключей портал работает на заглушках (решения 0018, 0027).
- Фоновый процесс `worker` (pg-boss в той же базе) проверяет вложения, обходит зависшие загрузки и чистит служебные таблицы ночью. В разработке его запускает `pnpm dev:up`, на сервере служба `worker` в `compose.prod.yaml` (решение 0028).
- Поиск с опечатками, синонимами и свёрткой письменности идёт через локальный Typesense (`SEARCH_PROVIDER=typesense`, план W6): он отдаёт только идентификаторы, строки читаются через `withActor` под RLS, при любом сбое поиск идёт прежним путём PostgreSQL. По умолчанию `SEARCH_PROVIDER=postgres`. Тесты с базой поднимают Typesense 30.2 сами (`TYPESENSE_IMAGE` задаёт зеркало, `TYPESENSE_TESTS=0` выключает).
- Почему сделано так, а не иначе: `docs/decisions/`.

## Если Docker Hub недоступен

Образ базы можно взять из зеркала. Переменная читается при первом запуске `pnpm dev:up` и запоминается в `.env`:

```bash
PG_IMAGE=mirror.gcr.io/pgvector/pgvector:pg18 pnpm dev:up
```

Typesense для тестов с базой: `TYPESENSE_IMAGE=mirror.gcr.io/typesense/typesense:30.2 pnpm test:integration` (digest тот же, что в `compose.prod.yaml`).

Для сборки образа приложения: `docker build --build-arg NODE_IMAGE=mirror.gcr.io/library/node:26.13.1-slim@sha256:e6bedef217677b276c591795e169840edd9096dbf13f29df8ef8d1856b8820bc .` (тот же digest, что в `Dockerfile`).
