# 0002. Кеш компонентов и оптимизатор изображений выключены

Дата: 20.11.2026. Веха: M0. Статус: принято.

## Контекст

Генератор Next.js 16.4.6 по умолчанию пишет в `next.config.ts` строки `cacheComponents: true` и `partialPrefetching: true`. Портал показывает данные разных организаций из одной базы. Страница, собранная для одного клиента и отданная из кеша другому, это утечка данных (угроза T4 раздела 14 ТЗ).

## Решения

1. `cacheComponents` и `partialPrefetching` в `next.config.ts` не задаются. Директива `use cache` без этой настройки не работает.
2. В коде запрещены: `use cache`, `unstable_cache`, функции `cacheLife` и `cacheTag`, настройки сегмента `revalidate` (кроме 0) и `force-static`, кеш у `fetch`. Это правило 6 раздела 9.4 ТЗ, его проверяет `pnpm check` (файл `scripts/checks/forbidden-apis.mjs`).
3. Все страницы портала динамические и отдаются с заголовком `Cache-Control: private, no-store`.
4. `images: { unoptimized: true }`. Обработчик `/_next/image` не используется: картинки интерфейса лежат в `public` готовыми, вложения клиентов отдаются через собственный обработчик с проверкой прав.
5. `poweredByHeader: false`. Сервер не сообщает, на чём он работает.
6. `output: 'standalone'`. В образ попадают только файлы, нужные при работе.

## Почему так

- Раздел 9.2 ТЗ требует Next.js не ниже 16.4.5: в выпуске от 03.11.2026 закрыта утечка кеша между арендаторами. Ошибка была в самом фреймворке, поэтому надёжнее не включать механизм, чем следить за его исправлениями.
- Оптимизатор изображений принимает адрес картинки от клиента и сам её загружает и обрабатывает. Это лишняя точка входа, которая порталу не нужна.
- Нагрузка этапа 1 небольшая (десятки сотрудников поддержки, сотни клиентов), динамическая отрисовка её выдерживает.

## Что это стоит

- Каждая страница собирается на сервере заново. При росте нагрузки сначала кешируются общие данные без привязки к организации (справочники, опубликованные статьи), и только отдельным решением.
- Картинки нужно готовить нужного размера заранее.
