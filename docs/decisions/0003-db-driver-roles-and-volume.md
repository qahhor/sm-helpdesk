# 0003. База данных: драйвер, роли, миграции, том

Дата: 20.11.2026. Веха: M0. Статус: принято.

## Решения

### Драйвер

Драйвер `pg` и Drizzle ORM поверх него. Тот же драйвер используют pg-boss и Better Auth в следующих вехах: одна библиотека подключения на весь проект.

Relational API Drizzle (`db.query`) не используется. Запросы пишутся явно: `select().from()`, `insert()`, `update()`. Так в коде видно, какие таблицы читает сервис.

### Три роли

| Роль | Кто использует | Что может |
|---|---|---|
| `hub_owner` | Только миграции (`pnpm db:migrate`) | Владеет таблицами и схемами |
| `hub_app` | Сервисы модулей через `withActor` | Таблицы предметной области, политики RLS принудительны |
| `hub_auth` | Библиотека аутентификации (с вехи M1) | Только таблицы аутентификации и идентичности |

Все три роли без прав суперпользователя, без обхода RLS, без создания баз и ролей. Это проверяет тест `tests/integration/db-roles.test.ts`.

Роли и базу создаёт `scripts/db/bootstrap.mjs` под суперпользователем. Сценарий можно запускать повторно. Пароль роли уходит на сервер готовой записью SCRAM-SHA-256: открытого пароля нет ни в тексте команды, ни в журнале сервера. Пароли трёх ролей обязаны различаться.

Схема `public` закрыта для всех ролей, кроме названных явно. Право на каждую таблицу выдаёт миграция, которая её создаёт.

### Миграции

Миграции пишутся руками на SQL и лежат в `drizzle/` (ТЗ 10.3: политики читает человек на ревью). Их применяет `scripts/db/migrate.mjs`:

- только под ролью `hub_owner`, иначе отказ: у суперпользователя политики RLS не действуют, и тесты проверяли бы не то;
- по порядку имён, каждая в своей транзакции;
- под блокировкой: два одновременных запуска идут по очереди;
- журнал `migrations.applied` хранит имя и контрольную сумму файла. Если применённый файл изменён, миграции останавливаются: исправление вносится новым файлом.

`drizzle-kit` не подключён: генератор миграций проекту не нужен. Расхождение между описаниями таблиц в коде и базой ловит тест `tests/integration/schema-drift.test.ts`.

### Служебные колонки

`created_by`, `created_on`, `modified_by`, `modified_on` заполняет триггер `app.stamp_row()`. Значения, присланные сервисом, отбрасываются. Автора и время создания нельзя подделать или переписать, и ни один сервис не может забыть их заполнить.

### Ошибки базы

`withActor` отдаёт сервису исходную ошибку базы с кодом и именем ограничения. Обёртка Drizzle снимается: в её тексте лежат запрос и значения параметров, то есть данные клиентов, которым не место в журнале.

### Том

Том монтируется в `/var/lib/postgresql`. Образ PostgreSQL 18 хранит данные в `/var/lib/postgresql/18/docker`. Набросок раздела 13.3 ТЗ монтирует `/var/lib/postgresql/data`: с образом версии 18 данные оказались бы вне тома и пропали бы при пересоздании контейнера. Проверено на образе `pgvector/pgvector:pg18` (PostgreSQL 18.7, pgvector 0.8.7).

Порт базы в `compose.yaml` открыт только на `127.0.0.1`.

## Что это стоит

- Описание таблицы существует в двух местах: SQL-миграция и файл `schema.ts` модуля. Согласованность держит тест.
- Перенос данных с сохранением исходных дат (импорт из Jira) должен выполняться под `hub_owner` с отключённым триггером служебных колонок. Это задача вехи с импортом.

## Правки к ТЗ версии 1.1

- Раздел 13.3: путь тома `/var/lib/postgresql`.
- Раздел 10.3: функция `app.stamp_row()` и имена по `docs/naming.md`.
