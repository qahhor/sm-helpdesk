# 0013. Личность клиента и адрес email

Дата: 20.11.2026. Веха: M1. Статус: принято.

ТЗ (FR-ID-04, решение 93): личность пользователя задаёт пара "сервер Smartup и идентификатор пользователя", учётные записи по совпадению email не объединяются, email из Smartup считается неподтверждённым. У большинства пользователей Smartup email не заполнен (решение 89). Библиотека входа при этом требует у каждой учётной записи уникальный адрес и без поля email в сведениях вход останавливает. Ниже как это сведено вместе.

## Личность

- Пользователя по сведениям Smartup выбирает функция портала (`resolveSmartupUser`, `src/modules/hdu/core/provision.ts`): есть способ входа с парой "код сервера и `sub`" в `auth.account`, значит это его пользователь. Нет: создаётся новый.
- По email пользователь не ищется никогда. Тот же адрес у другого человека, на другом сервере или у сотрудника Smartup не даёт ни чужой учётной записи, ни прав сотрудника.
- Пара "сервер и `sub`" уникальна на уровне базы (`account_provider_account_u1`).
- Новый пользователь создаётся в транзакции библиотеки входа: если вход сорвётся дальше, пользователь без способа входа не останется, а два одновременных первых входа одного человека не создадут двух пользователей.

## Служебный адрес

- Пока у пользователя нет подтверждённого адреса, в учётной записи стоит служебный вида `u-<uuid>@users.invalid`. Домен `.invalid` зарезервирован и почту не принимает: письмо на такой адрес уйти не может.
- Поле email в сведениях для библиотеки сопоставлено с `sub` (`mapping.email = 'sub'`): так вход проходит и без адреса. Само значение библиотека не использует: учётную запись выбирает функция портала, а сведения пользователя библиотека не переписывает (`profile: 'preserve'`).
- Настоящий адрес из Smartup приходит отдельным полем (`contactEmail`) и запоминается в `claimedEmail`. Для входа он не используется: его подставляет шаг первого входа, а адресом для входа он становится только после подтверждения ссылкой (задача 10).
- Один подтверждённый адрес принадлежит одной учётной записи. Вход по ссылке находит ровно одного человека.

## Организация и членство

- Организация это пара "сервер и идентификатор компании" (`hdu_organizations_u1`). Название и ИНН обновляются при каждом входе, пустой ИНН известное значение не стирает.
- Членство создаётся с источником `smartup`. Роль берётся из соответствия ролей сервера (`role_map`), иначе обычный пользователь. Роль, выданная сотрудником вручную, вход не меняет. Отключённое членство вход не включает. Создание организации, членства и смена роли пишутся в журнал аудита от имени системы.
- Сбой в сведениях (нет компании, слишком длинные значения, неизвестный сервер) вход не ломает: человек входит, но без членства, и попадает на экран "нет организации". В журнал приложения идёт причина и код сервера, без личных данных. Библиотека ошибку этого шага не перехватила бы, поэтому функция ошибок наружу не бросает.
- Что именно Smartup передаёт как компанию, открытый вопрос 43 ТЗ. Ответ меняет только таблицу `SMARTUP_CLAIMS` (`src/modules/hdu/pref.ts`).

## Активная организация

Клиент может состоять в нескольких организациях (FR-ID-05). Актор клиента строится на каждом запросе (`resolveClient`, `src/modules/hdu/api/orgs.ts`):

1. Сотрудник Smartup актора клиента не получает: кабинет отправляет его в рабочее место.
2. Организация берётся только из действующего членства в действующей организации. Колонка сессии `activeOrgId` лишь подсказывает, какую из своих организаций показать: чужая или отключённая там не пройдёт, отключённый участник теряет доступ на следующем запросе.
3. Порядок выбора: активная организация сессии, затем организация последнего входа (`lastOrgId`), затем единственная. Несколько без выбора: экран выбора. Ни одной: экран "нет организации" с кнопкой выхода.
4. Каждый вход через Smartup делает организацию из сведений организацией последнего входа: новая сессия начинается с той компании, под которой человек вошёл в Smartup.
5. Переключение в шапке и выбор на экране выбора записывают организацию в сессию и в `lastOrgId`. Обе колонки меняет только сервер после проверки членства, напрямую в базе (`src/modules/hdu/core/orgs.ts`): кеша сессии в куке нет, следующий запрос видит новое значение.

Шапка кабинета на телефоне: места на название организации нет. При одной организации название читает только программа экранного доступа, при нескольких в шапке значок, который открывает меню выбора. Название продукта "Hub" рядом с логотипом на телефоне тоже скрыто от глаз. С 600 px название организации видно целиком или с многоточием.

## Страница входа

- Клиент общего облака видит одну кнопку "Войти через Smartup". Клиент выделенного сервера один раз вводит адрес своего Smartup, найденный сервер запоминается кукой `hub_server` на год. Список серверов не показывается нигде (FR-ID-03).
- Если запомненный сервер отключён, страница говорит об этом и предлагает сменить сервер. На сервер по умолчанию вход сам не переключается: клиент выделенного сервера попал бы не туда.
- Кнопка входа это ссылка на обработчик `/{язык}/login/smartup`, а не отправка формы. После формы браузер ушёл бы на адрес сервера Smartup, а политика CSP разрешает формам только адрес портала (`form-action 'self'`). В режиме запрета (веха M9) Chrome такой переход заблокировал бы.
- Начало входа ограничено: 30 за 10 минут с одного адреса. Каждое начало оставляет в базе одноразовое значение состояния.
- Ошибка начала входа (сервер не найден, предел частоты) возвращает на страницу входа по адресу портала из настроек (`HUB_URL`): за прокси и в автономной сборке адрес запроса внутренний.
- Ошибку возврата с сервера показывает страница входа портала нейтральным сообщением. Страница ошибок библиотеки снаружи закрыта (решение 0012).
- Для ненайденного адреса страница советует обратиться в поддержку Smartup. Адрес поддержки появится в тексте, когда его зададут в настройках портала (вопрос 38 ТЗ закрыт, адрес задаётся в настройках).

## Ложный сервер Smartup

`scripts/mock-oidc.mjs` поднимает два сервера: `mock` (облако, порт 3190) и `mock-dedicated` (выделенный, порт 3191). Это настоящий поток OpenID Connect с PKCE и подписанным `id_token`, только вместо входа в Smartup страница выбора персоны и форма своей персоны. Выбор персоны привязан к коду авторизации, поэтому одновременные входы друг другу не мешают.

Ложный сервер только для разработки: в образ не входит, в реестр портала его записывает `scripts/dev-up.mjs --prepare` командой `hub`, и только когда портал работает на localhost. В разработке: `pnpm dev:oidc`.
