# 0018. Внешние сервисы в M1: проверка "не робот", письма входа, Telegram

Дата: 20.11.2026. Веха: M1 (часть 2). Статус: принято владельцем продукта вместе с частью 2 плана (пункты 16-19 таблицы решений).

ТЗ (раздел 11.11) требует для каждого внешнего сервиса интерфейс, настоящую реализацию и заглушку, а портал должен запускаться локально без единого внешнего ключа. Ниже как это сделано для сервисов, которые переходят в M1. Новых пакетов нет: сервисы вызываются через `fetch`.

## Проверка "не робот" (пункт 16)

- Cloudflare Turnstile за интерфейсом `BotCheck` (`src/security/bot-check.ts`). Ключи `TURNSTILE_SITE_KEY` и `TURNSTILE_SECRET` задаются парой. Без них проверка выключена и формы работают как раньше.
- Проверяются три формы без входа: запрос ссылки для входа, поиск сервера Smartup по адресу, шаг пароля сотрудника. Действия вошедшего пользователя проверку не проходят: их защищает сессия.
- Сервер обращается к `POST https://challenges.cloudflare.com/turnstile/v0/siteverify` с полями `secret`, `response`, `remoteip`. Поля сверены с документацией Cloudflare (ноябрь 2026): токен не длиннее 2048 знаков, живёт 5 минут и годится на одну проверку.
- Пройдено: `success: true` и `hostname` равен `HUB_DOMAIN`. Токен, полученный на чужом сайте с нашим ключом, не подходит.
- Не пройдено (отказ сервиса, чужой узел, пустой или слишком длинный токен): действие закрывается. Запрос ссылки отвечает тем же нейтральным текстом, поиск сервера отвечает "не найден", вход сотрудника показывает "не удалось подтвердить, что вы не робот".
- Сервис не ответил за 3 секунды, ответил ошибкой 5xx или не JSON: действие не закрывается. В журнал идёт предупреждение без данных посетителя, ограничения частоты продолжают действовать. Клиент должен попасть в портал при аварии (раздел 2.4), а защита от перебора слоёная.
- Проверка стоит первой: робот не расходует счётчик попыток сотрудника и счётчик ссылок на адрес. Поток роботов не блокирует учётную запись сотрудника и не мешает человеку получить ссылку.
- Виджет подключается скриптом `https://challenges.cloudflare.com/turnstile/v0/api.js` с одноразовым кодом страницы. Политика CSP разрешает этот адрес для скриптов и рамок с вехи M0. Токен виджет кладёт в поле `cf-turnstile-response`.
- Токен одноразовый, поэтому после каждого ответа формы (неверный пароль, другой адрес) виджет сбрасывается (`BotCheckRefresh`) и выдаёт свежий токен. Без этого повторная попытка без перезагрузки страницы не прошла бы проверку.
- Язык виджета совпадает с языком страницы. Язык, которого у Turnstile нет, виджет показывает по-английски.
- Известное ограничение: если у посетителя закрыт доступ к `challenges.cloudflare.com` (блокировщик рекламы, корпоративный фильтр), виджет не загружается, токена нет, и форма закрывается как при отказе. Правило "сервис не ответил, вход не закрывается" относится к серверу портала, а не к браузеру посетителя. Клиенту остаётся вход через Smartup (без формы), сотруднику нужен доступ к Cloudflare. Если это станет проблемой, решение пересматривается с владельцем продукта.
- Ограничение проверки: в браузерных тестах ключей нет, виджет не подключается. Работу с настоящим виджетом нужно проверить на staging тестовыми ключами Cloudflare (`1x00000000000000000000AA` и парный секрет всегда проходят).

## Письма входа (пункт 17)

- Настоящая отправка: значение `MAIL_TRANSPORT=resend` (`src/modules/hdn/resend.ts`), четвёртая реализация интерфейса `Mailer`. Нужны `RESEND_API_KEY` (секрет) и `MAIL_FROM` (адрес или вид `Имя <адрес>` с проверенного в Resend домена). Значение разрешено на любом узле, `console` и `file` по-прежнему только на localhost.
- Запрос: `POST https://api.resend.com/emails`, заголовок `Authorization: Bearer <ключ>`, тело JSON `{ from, to: [адрес], subject, text }`, предел времени 5 секунд.
- Письма уходят сразу, без очереди: фонового процесса до M2 нет, а потерянную ссылку человек запрашивает заново. Отправка не задерживает ответ формы (`queueMail`, решение 0016).
- Два повтора с паузами 0,5 и 2 секунды при ошибке сети, истечении времени, ответах 429 и 5xx. Остальные ответы 4xx это ошибка запроса, они не повторяются. Во всех повторах один заголовок `Idempotency-Key` (случайный на письмо): сервис не отправит одно письмо дважды, если первый ответ потерялся по дороге.
- Неудача после повторов: ошибка `MailError` с кодом ответа. В журнал идут вид письма и код ответа, без адреса, темы, текста со ссылкой и ключа.
- Письма в M1 только текстовые. Очередь в одной транзакции с действием (FR-NT-09), оформленные шаблоны с логотипом и Тезом (раздел 8.13) и события доставки остаются в M4.
- Сверка с документацией: сайт Resend из среды сборки недоступен (сетевые правила), поля запроса и заголовок взяты из известного описания API Resend. Перед первым включением ключа на staging отправить одно письмо и проверить доставку и отказ при неверном `MAIL_FROM` (ответ 4xx без повторов).

## Telegram (пункт 18)

Из вехи M4b в M1 переходит личность в Telegram: привязка, отвязка, язык, запасной вход (задача 17). Уведомления об обращениях в Telegram и выбор каналов остаются в M4b.

- Бот за интерфейсом `TelegramBot` (`src/modules/hdn/telegram.ts`): запросы `POST <TELEGRAM_API_URL>/bot<токен>/<метод>` с телом JSON, предел 5 секунд. `TELEGRAM_BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET` задаются парой, без них бот выключен: раздела "Telegram" в профиле и кнопки в шаге первого входа нет. Другой `TELEGRAM_API_URL` допускается только на localhost (ложный Telegram `scripts/mock-telegram.mjs`, порт 3192): туда уходит токен бота.
- Токен бота не попадает ни в журнал, ни в текст ошибок. Имя бота берётся методом `getMe` один раз за жизнь процесса.
- Вебхук `POST /api/webhooks/telegram`: бот выключен 404, заголовок `x-telegram-bot-api-secret-token` сравнивается с секретом за постоянное время (иначе 401), тело больше 64 КБ 413, не по схеме 400. Номер события записывается в `hdn_telegram_updates`: повтор отвечает 200 и ничего не делает. Сбой обработки снимает номер и отвечает 500: Telegram пришлёт событие снова. Вебхук ставится командой `hub telegram:set-webhook` и принимает только `message` и `callback_query`.
- Бот принимает только личный диалог с человеком. Группы и другие боты остаются без ответа.
- Привязка начинается в портале: кнопка ведёт на обработчик `/{язык}/settings/telegram`, он создаёт код и перенаправляет в `t.me/<бот>?start=<код>` (обычная ссылка, а не форма: как у входа через Smartup, решение 0013). Код 43 знака, живёт 10 минут, хранится хешем, прежние неиспользованные коды отменяются, 5 ссылок в час. Бот открывается в новой вкладке: профиль или шаг первого входа остаются открытыми.
- `/start <код>`: аккаунт Telegram, привязанный к другому пользователю, не переходит к нему; прежняя привязка этого пользователя заменяется; запись `telegram.linked` в журнале без идентификатора Telegram. Бот называет учётную запись и организацию и показывает кнопки "Войти", "Язык", "Отвязать" (угроза T30: человек видит новую привязку и отвязывает её одним нажатием). На подтверждённый email уходит письмо о привязке.
- Отвязка: команда `/unlink`, кнопка под сообщением бота или кнопка в профиле. Привязка удаляется (раздел 19.17), запись `telegram.unlinked`, бот подтверждает отвязку в диалоге.
- На любое другое сообщение бот отвечает коротко со ссылкой на портал (FR-NT-16). Кнопки отвечают сразу (`answerCallbackQuery`), чтобы у человека не висело ожидание на кнопке.
- Сотрудники Telegram не привязывают: функции принимают только контекст клиента. Администратор клиента привязок своих участников не видит.
- Сверка с документацией: сайт Telegram из среды сборки недоступен, методы и поля (`getMe`, `sendMessage` с `reply_markup.inline_keyboard`, `setWebhook` с `secret_token` и `allowed_updates`, `answerCallbackQuery`, заголовок `X-Telegram-Bot-Api-Secret-Token`) взяты из известного описания Bot API. Перед включением бота на staging поставить вебхук и пройти привязку настоящим аккаунтом.

## Язык пользователя (пункт 19)

- Учётная запись хранит язык (`auth."user".locale`: ru, uz или en). Его задают выбор языка в портале вошедшим пользователем, команда бота `/lang` и язык из Smartup при первом входе.
- Выбор человека важнее Smartup: язык из сведений Smartup записывается, только пока язык не задан. Язык Smartup берётся по первым двум буквам (`uz-UZ` это `uz`), другой язык не запоминается.
- Сообщения бота идут на языке учётной записи, для непривязанного собеседника на языке из Telegram, иначе по-русски. Письма о привязке тоже на языке учётной записи.

## Запасной вход из бота (пункт 18, задача 17)

- Для клиента, у которого Smartup недоступен, а Telegram уже привязан (FR-ID-14, угроза T30). Команда `/login` или кнопка "Войти" под сообщением бота.
- Бот даёт ссылку, только если аккаунт Telegram привязан и не заблокирован, человек не сотрудник и у него есть действующее негостевое членство в действующей организации. Иначе короткий ответ без ссылки. Не больше 5 ссылок в час на аккаунт Telegram, ответ называет, через сколько минут можно снова.
- Ссылка `<HUB_URL>/{язык учётной записи}/login/tg?token=<43 знака>`: живёт 10 минут, срабатывает один раз, хранится хешем в `hdu_login_codes` (канал `telegram`). Новая ссылка отменяет прежние неиспользованные.
- Открытие страницы ничего не меняет: Telegram открывает ссылки для предпросмотра. Входит только нажатие кнопки "Войти" (как у ссылки из письма, решение 0016). В момент нажатия условия проверяются снова: отвязка Telegram или отключение членства после выдачи ссылки её гасят. Недействительная, просроченная, использованная ссылка и снятый доступ дают один ответ.
- Вход создаёт обычную сессию портала (`createTrustedSession`, способ `telegram`), запись `user.signed_in_telegram` в журнале с адресом запроса. Затем главная страница на языке ссылки.
- Страница входа показывает путь через бота, когда бот включён. Имя бота страница ждёт не дольше 1,5 секунды: если Telegram не ответил, строки о боте нет, остальная страница работает.
