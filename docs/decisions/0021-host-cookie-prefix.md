# 0021. Куки входа с приставкой __Host-

Дата: 21.11.2026. Основание: проверка `main`, пункт S7 плана `docs/plans/M1-hardening.md`. Статус: принято, подтверждено владельцем 21.11.2026.

На https библиотека входа ставит свои куки с приставкой `__Secure-`. Такую куку браузер принимает только с `Secure`, но она может быть задана с `Domain` и путём, поэтому поддомен (например, страница статуса или почтовый сервис на `*.smartup24.com`) может поставить куку с тем же именем и подложить порталу чужую сессию (фиксация сессии). Приставка `__Host-` закрывает это: кука только для этого хоста, без `Domain`, с `Secure` и `Path=/`.

Решение:

- Библиотека умеет только `__Secure-`. Поэтому на https её приставка выключена (`useSecureCookies: false`), а имена всех её кук заданы явно: `__Host-hub.<имя>`, со свойствами `Secure` и `Path=/` (`src/modules/hdu/auth/options.ts`). Список кук в `AUTH_COOKIE_NAMES` (`src/modules/hdu/pref.ts`): сессия, кеш сессии (выключен), "не запоминать", сведения учётной записи, состояние входа через Smartup, ожидание второго фактора, доверенное устройство.
- На http (разработка, тесты) имена без приставки, как раньше: браузер не примет `__Host-` без `Secure`.
- Продление куки сессии в прокси (`session-cookie.ts`) знает новое имя. Прежняя кука `__Secure-hub.session_token` библиотекой больше не читается: после развёртывания все входят заново. Портал до запуска, людей с такими куками нет.
- Если в новой версии библиотеки появится своя кука, тест `auth-instance.test.ts` её не увидит. При обновлении библиотеки список имён сверяется с вызовами `createAuthCookie` в её коде.
