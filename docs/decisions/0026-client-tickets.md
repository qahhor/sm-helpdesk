# 0026. Обращения клиента в вехе M2

Дата: 21.11.2026. Веха: M2 (`docs/plans/M2.md`, таблица решений, пункты 1-6 и 14-17). Статус: принято, план подтверждён владельцем 21.11.2026.

1. Номера обращений начинаются с `SUP-1001`. Номер выдаёт последовательность `hdt_tickets_number_sq`, она принадлежит колонке `number`. Пропуски номеров возможны (откат транзакции).
2. Подсказка решений при вводе (S2, шаг 2) появится в M5, кнопки под ответом помощника (FR-TK-18) в M5b. В M2 форма сразу показывает поля.
3. Срок следующего ответа, автозакрытие через 5 рабочих дней и напоминание (FR-TK-07, FR-TK-10, FR-TK-15) приходят в M3 с расчётом сроков и календарём. Под формой только часы работы сотрудников, без обещания ответа AI (UX-C-04).
4. Ответ клиента на решённое обращение всегда открывает его заново. Определение благодарности (FR-TK-14) приходит в M3 вместе со списком для сотрудников.
5. Причины низкой оценки (FR-TK-11): `slow` "Долго ждал ответа", `not_solved` "Проблема не решена", `unclear` "Ответ непонятен", `other` "Другое". Оценка ставится один раз. Подтверждено владельцем.
6. После срока повторного открытия (14 дней, настройка `tickets.reopen_days`) кнопка "Создать новое по этой теме" открывает форму, новое обращение ссылается на прежнее колонкой `related_ticket_id`.
7. Поле "Модуль" ищется по справочнику `hdr_product_modules`, пока он пуст, поле скрыто. Справочник загружает команда `hub modules:import`.
8. Черновики обращения и ответа хранятся на устройстве (`localStorage`) с ключом по пользователю и очищаются после отправки (UX-C-02).
9. Смена статуса и видимости пишется в историю обращения `hdt_ticket_events` (её видит клиент) и в журнал аудита `hdc_audit_log` (CLAUDE.md).
10. Подписка (FR-TK-09): автор подписан всегда; участник подписывается на обращение своей организации с видимостью `org`. Когда обращение становится личным, подписки коллег снимаются (решение 17 плана), подписки автора и сотрудников остаются. Чужие строки подписок клиент удалить не может, поэтому их снимает фоновая роль сразу после смены видимости и только пока обращение личное; политики RLS не меняются. При возврате видимости `org` прежние подписки не возвращаются молча. Подписки отключённого участника снимет веха M4 вместе с отправкой писем (там же фильтр "письмо только тому, кто видит обращение").
11. Клиентские изменения обращения ограничены триггером `t_hdt_tickets_client_guard`: создать можно только новое обращение без полей сотрудника, менять только колонки своих операций, видимость только автору и администратору клиента. Это защита вторым слоем к правилам сервиса (раздел 10.3). С миграции `0016` клиент создаёт обращение только с приоритетом из влияния, только из каналов портала и виджета и без служебных полей сроков, отложения, известной проблемы и передачи от помощника; прежнее обращение (`related_ticket_id`) и сообщение вложения проверяются парой ключей с организацией и обращением.
12. Дочерние таблицы (`hdt_ticket_messages`, `hdt_ticket_events`, `hdt_ticket_watchers`, `hdt_attachments`) несут `org_id` первой колонкой с внешним ключом на пару `(ticket_id, org_id)` обращения: строка не может принадлежать другой организации, чем её обращение.
13. Ответов в обращениях не больше 60 в час на пользователя. В разделе 14.5 ТЗ предела нет, а без него ответами можно заполнить чужую очередь.
14. Экраны клиента (задача 9 плана): новое обращение `/tickets/new`, список `/tickets` с фильтрами обычной формой GET (организации или мои, статус, тип, поиск), страница `/tickets/SUP-1042`. Действия на странице (подтвердить, открыть снова, оценить, видимость, подписка) обычными формами и работают без скриптов; форма обращения и ответа на серверных действиях с `useActionState`: ошибка показывается у поля, введённое остаётся.
15. Подпись поля темы обращения: "Тема обращения" (`Murojaat mavzusi`, `Subject`). Короткое "Тема" совпадало с кнопкой темы оформления в шапке: два элемента с одним именем путают программу экранного доступа.
16. Черновик подставляется после гидратации (`useDraft` в `src/ui/drafts.ts`): поля формы пересоздаются по ключу с черновиком, а не меняют состояние в эффекте, и гидратация не ломается. Готовая форма отмечена атрибутом `data-ready`. Черновик удаляется только после успешной отправки: страница обращения, открытая с отметкой `?created=1` или `?done=replied`, удаляет его и убирает отметку из адреса. Обрыв сети, ошибка сервера или истёкшая сессия при отправке текст не теряют (FR-TK-16, итоговая проверка M2).
17. Тема из описания считается одной функцией `src/lib/subject.ts` и в браузере, и на сервере: подстановка при вводе совпадает с тем, что сохранит портал.
18. Подсказки первого входа (UX-C-14) хранятся колонкой `hintsSeenAt` в учётной записи (`auth."user"`, миграция `0014_user_hints.sql`, модуль `hdu`), видны после шага первого входа до нажатия "Понятно". На главной три последних своих обращения со ссылкой "Все".
19. Переписка выводится серверным компонентом `Markdown` (react-markdown 10.1.0 без плагинов): HTML из текста пропускается, картинки заменяются подписью, ссылки только http, https и mailto с `target="_blank"` и `rel="noopener noreferrer nofollow"`. Адрес без угловых скобок ссылкой не становится: для этого нужен ещё один пакет (remark-gfm), он не согласован.
20. Справочник модулей загружает команда `hub modules:import --file <путь> --admin <адрес>`. Политики RLS дают менять справочник только администратору портала, и они не ослабляются: команда консоли находит действующего администратора по адресу и выполняет загрузку от его имени, журнал аудита (`modules.imported`) называет его. Модули добавляются и обновляются по коду, отсутствующие в файле получают `passive`, родитель ставится вторым проходом; повтор кода, родитель вне файла и круг родителей отклоняют файл целиком.
21. Действия с обращением организации (итоговая проверка M2, отложенное замечание 5; правило поставил исполнитель по поручению владельца "делай всё", владелец может его поменять). Подтвердить решение и тем закрыть обращение могут автор и администратор клиента: коллега не закрывает чужое обращение. Открыть снова может любой участник, который видит обращение: вопрос мог вернуться у него. Оценку ставит только автор: она одна и отражает его опыт. Ответ коллеги на решённое обращение по-прежнему открывает его заново (пункт 4).
