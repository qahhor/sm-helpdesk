# 0035. Приём писем, неопознанные отправители и гости

Дата: 22.11.2026. Веха: M4 (`docs/plans/M4.md`, задачи 7-11). Статус: принято, план подтверждён владельцем 22.11.2026.

1. Вебхук только проверяет подпись, пишет `hdn_email_inbound` (повтор по `provider_id` ничего не делает) и ставит задачу `email.inbound`. Текст, заголовки и вложения фоновый процесс берёт у Resend. Исходное письмо портал не хранит. То же письмо под другим `provider_id` (письмо на два адреса поддержки) узнаётся по `Message-ID` и второй раз не разбирается.
2. Порядок разбора: проверочное письмо адреса поддержки, список отклонённых как спам, автоответ и недоставка (сохраняются без обращения и без ответа), затем обращение по подписанному адресу ответа, по `In-Reply-To` и `References` из `hdn_email_threads`, по `[SUP-n]` в теме от участника обращения; иначе новое обращение. Адрес ответа с неверной подписью без другого адреса приёма: письмо отброшено.
3. Адрес ответа `reply+<номер>.<id пользователя base32>.<20 hex HMAC>@REPLY_DOMAIN`, строчными буквами, проверка за постоянное время.
4. Опознание отправителя только по DMARC: учитывается верхний заголовок `Authentication-Results` с идентификатором `INBOUND_AUTHSERV_ID`, `dmarc=pass` и совпадение `header.from` с доменом From. Переменная не задана: опознанных нет. Ошибка настройки делает портал строже, а не слабее.
5. От имени клиента публикуется только письмо с его адреса, с DMARC, пока он видит обращение (членство действующее, политики RLS). Иначе внутренняя заметка "Письмо на проверке" с адресом отправителя; вложения непроверенного отправителя не скачиваются. Благодарность на решённое обращение его не открывает; закрытое в пределах срока повторного открытия открывается, закрытое дольше становится новым обращением.
6. Новое обращение: тип `question`, влияние `minor`, P3 без подтверждения, источник `email`. Подтверждённый пользователь с DMARC: обращение в его последней организации, письмо "создано" с номером и ссылкой, коллеги в копии становятся наблюдателями. Домен организации с DMARC: гость в этой организации, личное обращение, отметка "Отправитель не подтверждён". Иначе гость служебной организации "Неопознанные". Неопознанному только номер, не чаще раза в час; сверх 10 новых обращений в час с адреса письма сохраняются как `rate_limited`.
7. Служебная организация с закреплённым идентификатором `app.service_org_id()`, её обращения всегда личные (ограничение базы). Гость: учётная запись с искусственным адресом входа, адрес письма в `claimedEmail`, членство `guest`; войти гость не может. Строку организации создаёт код при первом письме: под принудительным RLS миграция вставить её не может.
8. Привязка из "Неопознанных" (роли, которые ведут обращения): обращение переходит в организацию клиента с видимостью "организация", сообщения, события, подписки и вложения переходят каскадом внешних ключей (миграция 0037), событие `bound` и журнал. Гостю членство `guest` в организации и приглашение с отметкой гостя (создаёт система после проверки роли, письмо на русском). Сбой приглашения не отменяет привязку, повтор кнопкой "Пригласить отправителя" оставляет одно приглашение. "Это не клиент" и "Спам" закрывают обращение из любого статуса без письма, "Спам" вносит адрес в список отклонённых.
9. Владение адресом доказывает принятие приглашения любой учётной записью с этим адресом или подтверждение адреса в профиле: записывается `hdu_guest_merges`. Задача раз в минуту передаёт пользователю обращения, сообщения, вложения и подписки гостя, членства гостя становятся `passive`. События истории остаются за гостем. Автора сообщения меняет только система: право на колонку `author_id` и триггер.
10. "Неопознанные" не попадают в очередь "Новые": у ссылки на очередь свой счётчик. Домены почты организации задают care и администратор на карточке организации, домены общих почтовых служб не принимаются, домен принадлежит одной организации.
