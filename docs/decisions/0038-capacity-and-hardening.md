# 0038. Запас по нагрузке и защите: волна 1 плана аудита

Дата: 23.11.2026. План: `docs/plans/W1.md`. Источник: `docs/audit/2026-11-23-technical-audit.md`, раздел 9, волна 1. Статус: принято; владелец поручил вести разработку по плану аудита без остановок 23.11.2026.

## Нагрузка

1. **Тесты планов запросов.** Набор `tests/integration/query-plans.test.ts` заливает 50 тысяч обращений и проверяет, что список клиента, счётчики и первая страница очередей и запросы задачи раз в минуту идут по индексам. В плане было 200 тысяч: 50 тысяч уже достаточно, чтобы планировщик отказался от полного просмотра, а набор выполняется за секунды.
2. **Счётчики очередей** считаются только по открытым обращениям и по "Моим". У очереди "Все" счётчика нет: считать её значило бы просматривать всю таблицу при каждом открытии рабочего места. Очередь "Все" по умолчанию отсортирована по последнему изменению.
3. **Листание по ключу не сделано.** Первые страницы очередей идут по индексам (миграция 0043). Далёкие страницы (сотая и дальше) очереди "Все" по-прежнему стоят пропорционально смещению. Причина: ключи сортировки со значениями "пусто в конце" делают листание по ключу сложным, а далеко очередь не листают, в ней ищут. Вернуться, если журнал медленных запросов покажет такие страницы.
4. **Задача раз в минуту** разбита на три запроса с частичными индексами: отложенные, решённые, расхождение паузы SLA. Неразобранные письма ищутся по своему индексу.
5. **Сроки хранения** (миграция 0044): отправленные и пропущенные строки очереди исходящих удаляются через 30 суток, разобранные входящие письма через 90 суток. Удаляет только ночная очистка под системным актором, политика базы не даёт удалить ждущие и не отправленные строки. **Журнал аудита не чистится:** срок его хранения решает владелец с юристом.
6. **Уведомления без транзакций внутри транзакции.** Роли получателей, привязка Telegram и каналы читаются одним запросом на всех получателей. Событие с 20 наблюдателями делает не больше 4 транзакций под ролью входа вместо 22. Возврат на первую линию больше не держит второе соединение внутри транзакции.
7. **Задача "настройки один раз на запрос" сокращена.** Измерение показало: страница обращения сотрудника открывает 4 транзакции приложения и 2 входа, страница очередей 6, обращение клиента 4, список клиента 1. Это много меньше оценки аудита (15). Сделано: боковая панель очередей одной транзакцией (страница очередей: 4 вместо 6) и тесты бюджета транзакций, которые падают при росте числа. Память настроек на запрос и общий загрузчик страницы не делались: они ломают границы модулей ради малой выгоды.

## Защита

8. **Замена ключа шифрования без простоя.** Прежний ключ задаётся в `ENCRYPTION_KEY_PREVIOUS`. Шифрует всегда текущий ключ, открывает текущий, а если не подошёл, прежний. Команда `hub secrets:reseal` перешифровывает секреты серверов Smartup и токен бота дежурных текущим ключом и называет секреты, которые не открылись. Идентификатор ключа в формат секрета не добавлен: AES-GCM отвергает чужой ключ, поэтому ключ определяется пробной расшифровкой, формат `v1` и данные не меняются. Шаги: `docs/runbooks/incident.md`.
9. **Замена секрета подписи адресов ответа.** `REPLY_HMAC_SECRET_PREVIOUS`: ответы на уже отправленные письма принимаются по обеим подписям, новые адреса подписываются новым секретом. Прежний секрет держат 30 суток.
10. **Входы клиентов в журнале аудита.** Каждый вход клиента пишет `user.signed_in` со способом (`smartup`, `email_link`, `invitation`, `telegram`) и адресом запроса. Пишет перехватчик создания сессии: один на все способы. Прежняя запись `user.signed_in_telegram` оставлена, поэтому вход из бота даёт две записи. Сбой записи вход не отменяет: сессия уже создана, ошибка идёт в журнал процесса.
11. **Чтение сотрудниками в журнале аудита.** Открытие обращения сотрудником пишет `ticket.viewed_by_staff` не чаще раза в час на пару сотрудник и обращение (время последней записи: колонка `view_logged_on`, миграция 0045). Каждая выданная сотруднику ссылка на файл пишет `attachment.downloaded_by_staff`, без имени файла. Запись идёт на сервере в транзакции чтения и от скриптов страницы не зависит. Цена: одна запись в базу на каждое открытие обращения сотрудником.
12. **Выгрузка журнала аудита за пределы сервера не сделана.** Нужен внешний сервис, по правилам проекта это решение владельца. Журнал попадает в шифрованную копию базы.
13. **Контейнеры.** Портал, фоновый процесс и задачи базы работают без привилегий ядра (`cap_drop: ALL`, `no-new-privileges`). Caddy оставляет только право занять порты 80 и 443. У PostgreSQL и ClamAV привилегии не сброшены: запуск их образов меняет владельца каталогов и пользователя; новых привилегий они получить не могут. Три сети вместо одной: `edge` (Caddy и портал), `data` (портал, фоновый процесс, задачи базы, PostgreSQL; без выхода в интернет), `scan` (фоновый процесс и антивирус). Антивирус не достаёт до базы и портала, Caddy не достаёт до базы. Проверено на настоящих контейнерах.
14. **Образ портала закрепляется по идентификатору** (`sha256:...` из `docker image inspect`), а не по метке: образ собирается на сервере, реестра и digest реестра нет.
15. **Общий сетевой слой исходящих запросов** `src/security/outbound.ts`: запрос поверх `node:https`, имя узла разрешается и проверяется в момент соединения (тем же вызовом, который отдаёт адрес сокету), переадресации не выполняются. Через него идут проверка связи с сервером Smartup и скачивание вложений писем. Новых пакетов нет.
16. **Остаток находки S14.** Запросы самой библиотеки входа (обмен кода на токен, ключи подписи, сведения о пользователе) идут через общий `fetch` и защищены проверкой адреса при записи сервера в реестр. Подменить запрос библиотеки без нового пакета нельзя. Сценарий требует администратора портала и подмены DNS; закрыть его можно пакетом `undici` (решение владельца о новой зависимости).
17. **Вложения писем** скачиваются только с доверенных узлов: `INBOUND_DOWNLOAD_HOSTS`, по умолчанию `resend.com` и его поддомены. Переадресацию разбирает портал: до 3 переходов, каждый адрес `https` и из того же списка. Справочник Resend из среды сборки недоступен; узел `inbound-cdn.resend.com` взят из поиска по справочнику. Проверка на staging: шаг в `docs/runbooks/launch.md`.
18. **Частые пароли сотрудников** отклоняются (FR-ID-09 дополнен). Три правила: пароль целиком складывается из частых слов, рядов клавиатуры, последовательностей и повторов, в том числе с заменой букв цифрами; частое слово от шести букв с добавкой до 8 знаков ("MyPassword123", "Summer2026!!"); один ряд или повтор занимает две трети пароля. Список встроенный, запросов в сеть нет. Случайный пароль с частым словом внутри проходит. Имя и адрес самого сотрудника в проверку не входят.
19. **Заметки "Письмо на проверке":** не больше 5 в час на обращение (сверх прежних 20 в час на адрес). Адреса из текста непроверенного письма заменяются отметкой с именем узла, а все знаки разметки Markdown экранируются: заметку показывает Markdown, и без этого ссылка собиралась из частей. Письма сверх предела сотруднику не видны до экрана очереди писем (M8).
20. **Запросы GET не меняют предметные данные.** Код привязки Telegram создаётся только по переходу самого человека (заголовки Fetch Metadata): запрос с чужого сайта и предзагрузка попадают на страницу настроек. Отметку "просмотрено" ставит действие страницы после показа, а не чтение страницы на сервере. Браузер без заголовков Fetch Metadata пропускается.

21. **Границы рабочих дней запоминаются** в расчёте рабочего времени. Замер приёмки на 200 тысячах обращений показал 78-81 мс на страницу очереди при запросах в 1-4 мс: расчёт фазы срока шёл по дням от создания обращения и на каждый день форматировал дату. Память ограничена 20 тысячами значений и сбрасывается при переполнении.
22. **Ссылки страницы очередей** считают сортировку по умолчанию для очереди, в которую ведут: у "Все" это последнее изменение, у остальных срок. Выбранная сотрудником сортировка переносится между очередями, взятая по умолчанию нет.
23. **Выкладка версии с изменённым `compose.prod.yaml`** требует перезапуска всех служб (`hubc up -d`): записано в памятке запуска.

## Что не входит

Включение GitHub Actions, staging, внешний сервис сбора ошибок, непрерывный архив базы, выгрузка журнала аудита наружу: решения владельца (вопросы в `docs/HANDOFF.md`).
