# 0039. Рост и восстановление: волна 2 плана аудита

Дата: 23.11.2026. План: `docs/plans/W2.md`. Источник: `docs/audit/2026-11-23-technical-audit.md`, раздел 9, волна 2. Статус: принято; владелец поручил вести разработку по плану аудита без остановок 23.11.2026. Запись пополняется по мере выполнения задач волны.

1. **Миграции вне транзакции.** Файл миграции, первая строка которого `-- hub:no-transaction`, выполняется вне транзакции, по одной команде. В нём допускаются только `CREATE [UNIQUE] INDEX CONCURRENTLY IF NOT EXISTS` и `DROP INDEX CONCURRENTLY IF EXISTS`: отката вне транзакции нет, а эти команды безопасно повторить. Файл проверяется до первой команды запуска. Запись о применении ставится после последней команды; сбой посреди файла оставляет его не применённым. Недостроенный индекс (недействительный после сбоя) при повторе удаляется и строится заново. Причина: обычный `CREATE INDEX` держит запись в таблицу на всё время построения (замечание F12 проверки волны 1). Правило: индекс на таблице, которая растёт с числом обращений, сообщений или писем, добавляется таким файлом.
2. **Очередь исходящих отправляется до опустошения.** Один запуск берёт пачки по 50 строк и шлёт до 4 писем одновременно, пока очередь не опустеет или не выйдет бюджет времени 50 секунд (задача идёт раз в минуту). Раньше запуск отправлял одну пачку по одному письму: потолок был 3000 писем в час. Адрес получателя, чат Telegram и настройки (адрес поддержки, дежурные) читаются один раз на запуск; изменение адреса или настройки подхватывает следующий запуск, то есть не позже чем через минуту. Строки, взятые в пачку, но не начатые до конца бюджета, возвращаются в очередь без потраченной попытки и без отсрочки. Одновременность 4 выбрана с запасом под пределы частоты почтового сервиса; число меняется в одном месте.
3. **Одно обновление строки обращения на действие сотрудника.** Действие копит изменения (первый ответ, исполнитель, статус, приоритет, линия) и пишет их одной командой вместе с пересчётом сроков. Раньше первый ответ на новое обращение давал четыре обновления строки. Событие смены статуса пишется до обновления: по его времени ставится начало паузы срока. Пересчёт сроков без изменений строку не переписывает. Остаются два обновления: ответ клиента, который снимает паузу (сроки клиент менять не может, их вторым обновлением считает система), и поднятие приоритета до P1 (отметка "дежурные оповещены" ставится после постановки сообщения в очередь).
4. **Индексы таблицы обращений: 19 вместо 20, обычная строка входит в 13 вместо 17.** Индекс по сроку решения убран: срок ищется только у открытых обращений, для них есть частичный индекс. Индексы по подписи ошибки, основному обращению дубля и связанному обращению стали частичными (только заполненные значения): внешние ключи и поиск по значению работают как раньше. Миграция 0046 идёт вне транзакции.
5. **Поиск от трёх знаков.** Текст короче трёх знаков не ищется ни в списке клиента, ни в очередях сотрудника, ни среди организаций и людей: страница показывает подсказку. Номер обращения ищется при любой длине. Имя и адрес человека ищутся по триграммным индексам (миграция 0047); у таблицы пользователей политик RLS нет, поэтому индексы работают.
6. **Находка волны: под политиками RLS поиск по тексту не идёт по индексу.** PostgreSQL выполняет раньше условий политики только операторы, отмеченные как безопасные (`leakproof`). Оператор `ILIKE` так не отмечен, поэтому триграммные индексы на таблицах с RLS не используются вовсе: ни прежние индексы по теме и описанию обращения и названию организации, ни новые. Замер на машине сборки: поиск по тексту в очереди "Все" на 200 тысячах обращений 902 мс против 11 мс без RLS; поиск организации на 100 тысячах организаций 95-119 мс против 4 мс. В открытых очередях и у клиента поиск сначала сужается индексом (очередь, организация) и остаётся быстрым. Аудит эту находку не содержал.
   Исправление: один раз под суперпользователем отметить функцию оператора как безопасную (`ALTER FUNCTION texticlike(text, text) LEAKPROOF` в начальной настройке базы). Функция не выдаёт данных строки в сообщениях об ошибках, а запросы пишет только портал, не клиент. Это меняет порядок, в котором база применяет условия политик, для всех таблиц, поэтому по правилам проекта **требует согласования владельца** и в волне не сделано. Индексы по ИНН и идентификатору компании не добавлялись: без этого изменения они не работали бы. До решения: поиск по тексту в очереди "Все" на больших объёмах медленный, порог неудобства около 100 тысяч обращений.
7. **Файлы письма кладутся в хранилище до транзакции разбора.** Порядок как у загрузки из браузера: строка вложения без обращения, файл в карантин, затем в транзакции разбора строка прикрепляется к обращению и сообщению. Раньше файл клался в хранилище под блокировкой обращения и письма. Если письмо за это время разобрал другой процесс или разбор упал, загрузки убираются сразу; при сбое процесса строку без обращения вместе с файлом убирает очистка загрузок через сутки. Ответ письмом теперь тоже пишет строку обращения один раз (отметки ответа, статус и сроки вместе).
8. **История обращения читается частями.** Страница обращения клиента и сотрудника читает последние 50 записей (сообщения и события вместе, по времени); ссылка "Показать раньше" добавляет ещё 50, предел 1000. Окно задаётся числом последних записей, а не отметкой времени: у записей с одинаковым временем нет границы, на которой запись теряется или показывается дважды. Окно считается под политиками актора: клиент не получает внутренних записей ни в одной части. Версия страницы для предупреждения "пока вы писали" (FR-AG-12) считается по всей истории. Вложения обращения по-прежнему читаются все. Цена: чтобы дойти до начала переписки в 500 сообщений, нужно 9 нажатий; поиск внутри обращения ищет только в показанной части.
9. **Присутствие одной командой.** Отметка "открыл" или "печатает" и список коллег на обращении идут одной командой в одной транзакции; имена читаются, только когда на обращении есть кто-то ещё. Раньше каждые 10 секунд на вкладку шли три транзакции. Вкладка в фоне не отмечается, как и раньше.
10. **Слои модулей.** Зависимость идёт в одну сторону: `hdc` ни от кого не зависит, `hdn` и `hdr` берут только `hdc`, `hdu` ещё `hdn`, `hdt` все четыре. Раньше `hdu` и `hdn` брали api друг друга. Общие понятия, которые нужны нижним модулям от верхних, объявлены в `hdc`: справочник контактов ("куда писать человеку": адрес почты, чат Telegram) и контекст сотрудника со свежестью входа. Реализацию справочника даёт `hdu`, соединяет их файл `src/wiring.ts`, который импортирует каждая точка входа: сервер Next.js, фоновый процесс, команда консоли, настройка тестов с базой. Без подключения первое же уведомление заканчивается ошибкой с названием причины. Правило слоёв проверяет линтер, перечень точек входа проверяет тест. Отступление от плана: письма входа и приглашений `hdu` по-прежнему отправляет через api `hdn` напрямую. Это разрешённое направление, второй интерфейс в `hdc` ничего бы не дал. Константы (`pref`) слоями не ограничены: `hdr` берёт перечень типов обращений из `hdt`.
11. **Модуль не называет таблицу другого модуля.** Проверка правил находит имя чужой таблицы в коде модуля (приставка модуля в имени таблицы, схема `auth` вне `hdu`). Убраны четыре места: журнал аудита брал имена авторов и организаций подзапросами из таблиц `hdu` (теперь имена добавляет `hdu`, функция `listAuditNamed`); уведомление читало организацию из таблицы обращений (теперь её передаёт вызывающий, без неё уведомление об обращении не ставится); напоминание о праздниках читало таблицу уведомлений из `hdt` (теперь функция в api `hdn`).
12. **Непрерывный архив средствами PostgreSQL, без pgBackRest.** ТЗ 13.7 называло pgBackRest; он и любой другой инструмент архива это новая зависимость на сервере. Сделано проще: `archive_command` копирует готовый сегмент журнала в каталог на сервере, сценарий `wal-ship.sh` раз в минуту шифрует сегменты открытым ключом `age` и выгружает в бакет копий, `base-backup.sh` раз в неделю делает шифрованную базовую копию, `restore-pitr.sh` готовит каталог данных, восстановленный на момент времени. Потеря данных при гибели сервера: до 10 минут (сегмент закрывается раз в 5 минут). Архив выключен по умолчанию и включается переменной `PG_ARCHIVE_MODE=on`: включение на сервере ждёт решения владельца о переносе из M9. Сегмент лежит на диске сервера незашифрованным до минуты: это тот же диск, на котором лежит сама база. Отступление от ТЗ записано для ТЗ 1.2. Цена: нет сжатия и проверки целостности архива, которые даёт pgBackRest; при росте базы до десятков гигабайт к вопросу стоит вернуться.
13. **Сигнал о сбое архива.** `ops.watch` читает состояние архива у сервера базы и шлёт дежурным сигнал, если архив включён, а последняя попытка сохранить сегмент неудачна. Остановку выгрузки в бакет (сценарий на сервере) портал не видит: её ловит внешняя проверка по возрасту отметки `last-shipped`.
14. **Репетиция восстановления на момент времени** проведена 23.11.2026 на PostgreSQL 18.7 во временном контейнере настоящими сценариями и настоящим `age`: запись до заданного момента на месте, запись после него отсутствует. Запись в журнале проверок `docs/runbooks/restore.md`. На staging репетицию нужно повторить на данных настоящего размера.
