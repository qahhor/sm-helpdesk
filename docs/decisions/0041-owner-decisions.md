# 0041. Решения владельца от 24.11.2026: волна 4

Дата: 24.11.2026. План: `docs/plans/W4.md`. Источник: ответы владельца на открытые вопросы раздела 5 `docs/HANDOFF.md`; остальные вопросы владелец поручил решить исполнителю. Статус: принято. Запись пополняется по мере выполнения задач.

1. **Письмо дежурным о P1 без темы обращения (вопрос 6, решил исполнитель).** В письме номер обращения, организация и ссылка. Тема это текст клиента: в служебной почте и чате дежурных он не нужен, а письмо читают люди вне портала. Сообщение в чат дежурных темы не несло и раньше.
2. **Шаблоны писем остаются без React Email (вопрос 7), три решения M4 по почте остаются (вопрос 8), пакет `puppeteer` не добавляется (вопрос 11), новая узбекская латиница не вводится (вопрос 14).** Решил исполнитель по поручению владельца. Скорость рабочего места меряет Playwright. К латинице вернёмся, когда на неё перейдёт сам Smartup.
3. **Поиск по тексту идёт по индексу (вопрос 19, разрешил владелец).** Начальная настройка базы отмечает функцию оператора `ILIKE` (`texticlike`) как безопасную для выполнения раньше условий политик RLS. Миграция 0052 строит триграммные индексы по теме и описанию обращения, названию, ИНН и идентификатору компании организации. Условие, при котором отметка честна: шаблон поиска собирает только код портала с экранированием знаков шаблона. Тогда ошибки "шаблон кончается знаком экранирования", по которой можно было бы судить о строке, которую человек не видит, не бывает; данных строки функция в ошибках не выдаёт. Условие держит правило проверки `like-pattern` в `pnpm check`: файл с поиском по шаблону без функции экранирования не проходит. Правило нашло одно место без экранирования (проверка приёма почты), оно исправлено. Цена: по времени ответа поиска человек может судить, есть ли в базе текст, которого он не видит; это свойство любого поиска по индексу.
4. **Журнал аудита хранится 3 года (вопрос 16, решил владелец).** Ночная очистка удаляет записи старше 3 лет пачками по 5000. Миграция 0053: роль приложения получила право удаления, политика пускает только системного актора и только записи старше срока; чтобы удалить строку, система видит её (и только такие строки). Запись моложе 3 лет не удаляет и не читает никто, кроме администратора портала, который читает журнал как раньше. Изменять записи по-прежнему нельзя никому. В наборе изоляции строка журнала теперь разрешает роли приложения удаление: это следствие решения владельца, а запрет на свежие записи проверяют тесты `retention.test.ts` и `audit.test.ts`.
5. **Журнал аудита раз в сутки уходит в бакет резервных копий (вопрос 17, решил владелец).** Сценарий `scripts/ops/audit-export.sh` выгружает новые записи журнала в подкаталог `audit` того же бакета, куда идут копии базы. Файл шифруется открытым ключом получателя до записи на диск. Каждый запуск берёт записи с отметки прошлой удачной выгрузки, отметка сдвигается только после выгрузки: сбой суток не теряет. Нового внешнего сервиса нет. Цена: записи последних суток до выгрузки есть только в базе и в архиве журнала базы; кто владеет ключом выгрузки, может стереть файлы в бакете, если у бакета не включён запрет удаления (строка в памятке запуска).
6. **GitHub Actions включён (вопрос 10, решил владелец).** Файл настройки возвращён в `.github/workflows/ci.yml`: на каждую отправку и запрос на слияние идут пять задач (типы, линтер, правила ТЗ и модульные тесты; тесты с базой; браузерные тесты с бюджетом скриптов; поиск секретов и уязвимых пакетов; сборка образа). Решение 0011 отменено. Ручной прогон перед коммитом остаётся правилом работы.
