# 0041. Решения владельца от 24.11.2026: волна 4

Дата: 24.11.2026. План: `docs/plans/W4.md`. Источник: ответы владельца на открытые вопросы раздела 5 `docs/HANDOFF.md`; остальные вопросы владелец поручил решить исполнителю. Статус: принято. Запись пополняется по мере выполнения задач.

1. **Письмо дежурным о P1 без темы обращения (вопрос 6, решил исполнитель).** В письме номер обращения, организация и ссылка. Тема это текст клиента: в служебной почте и чате дежурных он не нужен, а письмо читают люди вне портала. Сообщение в чат дежурных темы не несло и раньше.
2. **Шаблоны писем остаются без React Email (вопрос 7), три решения M4 по почте остаются (вопрос 8), пакет `puppeteer` не добавляется (вопрос 11), новая узбекская латиница не вводится (вопрос 14).** Решил исполнитель по поручению владельца. Скорость рабочего места меряет Playwright. К латинице вернёмся, когда на неё перейдёт сам Smartup.
3. **Поиск по тексту идёт по индексу (вопрос 19, разрешил владелец).** Начальная настройка базы отмечает функцию оператора `ILIKE` (`texticlike`) как безопасную для выполнения раньше условий политик RLS. Миграция 0052 строит триграммные индексы по теме и описанию обращения, названию, ИНН и идентификатору компании организации. Условие, при котором отметка честна: шаблон поиска собирает только код портала с экранированием знаков шаблона. Тогда ошибки "шаблон кончается знаком экранирования", по которой можно было бы судить о строке, которую человек не видит, не бывает; данных строки функция в ошибках не выдаёт. Условие держит правило проверки `like-pattern` в `pnpm check`: файл с поиском по шаблону без функции экранирования не проходит. Правило нашло одно место без экранирования (проверка приёма почты), оно исправлено. Цена: по времени ответа поиска человек может судить, есть ли в базе текст, которого он не видит; это свойство любого поиска по индексу.
4. **Журнал аудита хранится 3 года (вопрос 16, решил владелец).** Ночная очистка удаляет записи старше 3 лет пачками по 5000. Миграция 0053: роль приложения получила право удаления, политика пускает только системного актора и только записи старше срока; чтобы удалить строку, система видит её (и только такие строки). Запись моложе 3 лет не удаляет и не читает никто, кроме администратора портала, который читает журнал как раньше. Изменять записи по-прежнему нельзя никому. В наборе изоляции строка журнала теперь разрешает роли приложения удаление: это следствие решения владельца, а запрет на свежие записи проверяют тесты `retention.test.ts` и `audit.test.ts`.
5. **Журнал аудита раз в сутки уходит в бакет резервных копий (вопрос 17, решил владелец).** Сценарий `scripts/ops/audit-export.sh` выгружает новые записи журнала в подкаталог `audit` того же бакета, куда идут копии базы. Файл шифруется открытым ключом получателя до записи на диск. Каждый запуск берёт записи с отметки прошлой удачной выгрузки, отметка сдвигается только после выгрузки: сбой суток не теряет. Нового внешнего сервиса нет. Цена: записи последних суток до выгрузки есть только в базе и в архиве журнала базы; кто владеет ключом выгрузки, может стереть файлы в бакете, если у бакета не включён запрет удаления (строка в памятке запуска).
6. **GitHub Actions включён (вопрос 10, решил владелец).** Файл настройки возвращён в `.github/workflows/ci.yml`: на каждую отправку и запрос на слияние идут пять задач (типы, линтер, правила ТЗ и модульные тесты; тесты с базой; браузерные тесты с бюджетом скриптов; поиск секретов и уязвимых пакетов; сборка образа). Решение 0011 отменено. Ручной прогон перед коммитом остаётся правилом работы.
7. **Пакет `undici` и проверка адреса при соединении для запросов библиотеки входа (вопрос 18, решил владелец).** Библиотека входа ходит к серверу Smartup общим `fetch` и своего сетевого слоя не принимает. Общий `fetch` Node.js берёт диспетчер запросов процесса, поэтому проверка стоит в нём (`src/security/outbound-dispatcher.ts`). Она действует только на узлы серверов Smartup из реестра: имя, которое в момент соединения разрешилось во внутренний адрес, отклоняется. Хранилище, почтовый сервис и Telegram идут как раньше: им внутренний адрес бывает положен. Версия пакета 8.12.4, та же, что встроена в Node.js 26: диспетчер процесса у них общий. Остаток находки S14 закрыт. Цена: при обновлении Node.js версию пакета надо держать той же старшей версии, что встроенная.
8. **Итоговая проверка ветки: что изменено.** Проверяющий с отдельным контекстом дал вердикт "готово после исправлений": утечек данных и способа удалить свежую запись журнала не найдено. Исправлено:
   - шаблон поиска собирает один помощник `src/db/contains.ts`; вызов `ilike` и `like` и оператор в тексте запроса в остальном коде запрещает правило `like-pattern`. Прежнее правило пропускало запрос с оператором в тексте и файл, где экранирование упомянуто один раз;
   - миграции сообщают, если отметки оператору поиска в базе нет: её ставит только начальная настройка базы, в дамп и в обновление старшей версии PostgreSQL она не переносится. Без отметки поиск правильный, но медленный. Шаг добавлен в памятку запуска;
   - выгрузка журнала аудита берёт верхнюю границу с отставанием 15 минут: время записи журнала это начало её транзакции, и запись долгой транзакции иначе не попала бы ни в один файл;
   - в памятке правила хранения бакета разделены по каталогам: одно правило "старше 60 суток" стёрло бы копии журнала аудита, которым положено 3 года;
   - на удаление журнала аудита поставлена ещё и ограничивающая политика (миграция 0054): срок в 3 года держится, какую бы разрешающую политику ни добавили позже;
   - задача браузерных тестов в GitHub Actions переписана: с вехи M0 она расходилась с тем, как тесты готовят окружение.

   Оставлено, с ценой:
   - **По времени ответа поиска клиент может судить о тексте чужих обращений.** Поиск клиента ограничен своей организацией, но индекс по тексту общий: время ответа зависит от того, сколько строк во всей базе подошло под шаблон. Перебором это позволяет уточнять содержимое чужих обращений по знаку. Практически это трудно, но канал между организациями существует. Закрывается пределом частоты на поиск клиента или индексом по организации; это отдельная задача (`docs/HANDOFF.md`, вопрос 22);
   - тема обращения остаётся в строке очереди исходящих для письма дежурным (в само письмо не попадает); строка удаляется через 30 суток;
   - о сбое выгрузки журнала никто не узнает, кроме файла журнала cron: отметки для внешней проверки, как у копии базы, нет;
   - диспетчер запросов не отклоняет переадресацию от сервера Smartup сам: это делает библиотека входа, её обновление может это изменить;
   - цена записи индекса по описанию обращения не измерена: каждое изменение обращения заново вносит его текст в индекс.

9. **Предел частоты на поиск клиента по тексту (ответ владельца 24.11.2026 на вопрос 22: делать).** Поиск клиента по тексту обращений считается: 30 в минуту на пользователя и 300 в час на организацию. Сверх предела запрос к обращениям не выполняется, список пуст, страница просит подождать. Список без поиска и поиск по номеру не считаются: они не идут по общему индексу текста. Это закрывает оставленное в пункте 8: перебор шаблонов ради замера времени ответа при таких пределах занимает месяцы на одно слово. Цена: клиент, который за минуту сделал больше 30 поисков или листал результаты поиска дальше 30 страниц, ждёт минуту. Если неверно: предел меняется одной строкой в `src/modules/hdc/pref.ts`.
