## Решения, которых нет в ТЗ

1. **Ключ только у фонового процесса и отдельной схемой окружения.** Переменные `ANTHROPIC_API_KEY`, `AI_MODEL_FAST`, `AI_MODEL_QUALITY` и `AI_STUB` разбирает `parseAiEnv`, а не схема портала: `getEnv()` их не содержит, даже если они попали в окружение веб-процесса. Разбирает её только фабрика клиента и запуск фонового процесса (неверный набор останавливает его сразу). В `compose.prod.yaml` контейнер `worker` получает необязательный файл `.env.worker`, у портала его нет. Цена ошибки: если `.env.worker` не положить, решения работают без AI.
2. **Имён моделей в коде нет** (решение 4 плана). С ключом обе переменные моделей обязательны; рекомендованные `claude-haiku-5-5` и `claude-sonnet-5-5` (ТЗ, раздел 9) записаны в `.env.example` и в памятке запуска. Поручение координатора просило значения по умолчанию из документации: выбрано правило подтверждённого плана. Цена ошибки: одна строка в `.env.worker`.
3. **Заглушка в разработке и браузерных тестах** включается `AI_STUB=1`, только когда портал на localhost и без ключа. Без ключа и без заглушки модели нет: задачи ведут себя как при выключенной AI-обработке.
4. **Вход модели очищается целиком, а не только email и телефоны.** Невидимые знаки (`cleanUserText` и одиночные соединители, селекторы вариантов), адреса почты, телефоны с разделителями и любые числа от 7 цифр подряд (ИНН, ПИНФЛ, номера документов) заменяются метками `[email]`, `[phone]`. Точка разделителем телефона не считается: даты и версии остаются. Имена участников переписки (целиком и по словам) заменяются на "Клиент" и "Сотрудник", название и ИНН организации на "Организация". Угловые скобки экранируются: текст клиента не закрывает `<ticket>`. Вход обрезан до 8000 знаков (проверка на AI-инъекции, пункт 5). Цена ошибки: имя, которого нет в профиле (например, третьего лица), уходит в модель; его просит убрать промпт 11.10, а остатки ловит проверка FR-SOL-04 черновика.
5. **Что уходит в черновик:** тема, описание и публичные сообщения клиента и сотрудников. Не уходят: внутренние заметки, сообщения системы, автоматические ответы правил, вложения (в выборке их нет вовсе). Проверки до вызова: обращение решено или закрыто, AI-обработка организации включена; иначе отказ без вызова и без строки журнала.
6. **Журнал `hda_runs`:** организация (у перевода пусто: текст решения не данные организации), объект (статья, без внешнего ключа), цель, модель из ответа API, токены, стоимость, время, итог (`ok`, `invalid_response`, `failed`, `limited`) и код сбоя без текста. Пишет только система, читают сотрудники, клиент не читает, строки не меняются. Стоимость по ценам уровня модели в `src/modules/hda/pref.ts` (быстрая как Haiku, качественная как Sonnet): при смене модели цену меняют там.
7. **Суточный предел** считает вызовы за сутки по Ташкенту (отказы по пределу не считаются), значение в `hdc_settings` (`ai.daily_limit`, по умолчанию 300, от 0 до 10 000), меняет администратор со свежим входом с записью в журнал. Подсчёт и вызов не в одной транзакции: две одновременные задачи могут превысить предел на единицы. Цена ошибки: несколько лишних вызовов в сутки.
8. **Сбой модели не ломает страницу.** Нет ответа или ответ не прошёл схему: строка журнала и ошибка задаче фонового процесса, pg-boss повторяет. Страницы о вызове не знают: они показывают состояние задачи (задачи 6 и 7).

## Не проверено

- **Настоящий API Anthropic не вызывался ни разу:** в среде нет ключа и выхода к `api.anthropic.com`. Формат запроса (`POST /v1/messages`, заголовки `x-api-key` и `anthropic-version: 2023-06-01`, тело `model`, `max_tokens`, `system`, `messages`) и ответа (`content[].text`, `stop_reason`, `usage`) взят из описания Messages API и проверен юнит-тестом с подменой запроса (`tests/unit/hda-anthropic.test.ts`). Весь договор в одном файле `client/anthropic.ts`. Первый запуск с ключом: один черновик и один перевод на тестовом решении, затем строки `hda_runs` (модель, токены).
- Цены за токены не сверены с текущим прайсом Anthropic.
