## Решения, которых нет в ТЗ

1. **Запрос 11.6 уточнён.** Полнотекстовый список ищет любое из слов запроса (`plainto_tsquery`, где `&` заменено на `|`), а не все сразу: описание клиента длиннее заголовка решения, и требование "все слова" почти ничего бы не находило. Ранг `ts_rank`, а не `ts_rank_cd`: в замере `ts_rank_cd` занимал 75 из 200 мс. Триграммы: более короткая строка (запрос или заголовок) ищется как часть более длинной (`word_similarity`), порог 0.5. Смысл: косинусное расстояние меньше 0.45. Каждый список до 20 мест, очки 1/(60 + место).
2. **Уверенность (решение 17):** точное совпадение сигнатуры всегда и первым; остальное, если документ в двух списках из трёх, или в нём все слова запроса (не меньше двух), или смысловое расстояние не больше 0.25. Запрос из одного слова не ищется вовсе (кроме точного совпадения): по слову "склад" находится всё подряд. Модуль формы даёт множитель 1.1. Пороги начальные, подбираются на наборе задачи 11. Цена ошибки: лишняя или пропущенная подсказка до замера.
3. **Языки (FR-SOL-10):** ищутся все три языка цепочки сразу; одно решение показывается один раз, строкой с большей оценкой, при равной языком, стоящим раньше в цепочке. Страница решения сама выбирает язык по цепочке.
4. **Сигнатура:** клиент сигнатуру не передаёт, её считает сервер (`signatureFromText`, пока задачи 8 нет, всегда пусто). Иначе клиент накручивал бы число организаций любой сигнатуры. Путь точного совпадения работает, когда сигнатура передана кодом (тест, виджет M6), в том числе при пустой таблице сигнатур. Сигнатуру читает система, видимость решения проверяет политика актора: внутреннее и архивное решение клиенту точным совпадением не показывается. Организация клиента записывается в `hdk_signature_orgs` при показе подсказки с существующей сигнатурой, `org_count` пересчитывается; клиенту уходит только число и только от трёх, строка числа собирается на сервере.
5. **Сессия формы (решение 12):** идентификатор выдаёт страница `/tickets/new` при каждом открытии; после "Не помогло" на странице решения он возвращается в адресе (`?s=`, `open=1`). Строка исходов создаётся при первом показе, при следующих показах заменяются показанные решения и HMAC запроса. Чужая сессия (другой пользователь или организация) не меняется. Показ решения в сессии увеличивает его счётчик один раз. Исходы: `helped` и `not_helped` со страницы решения (задача 4), `not_helped` кнопкой в блоке, `ticket_created` с идентификатором обращения после отправки формы, после него исход не меняется. HMAC: ключ выведен из `ENCRYPTION_KEY` (HMAC с меткой `hdk:deflection-query`), запрос приводится к нижнему регистру и одиночным пробелам.
6. **Поля формы (экран 8.3):** пока подсказка показана, поля под описанием свёрнуты (`hidden`, введённое не теряется) и раскрываются кнопкой "Не помогло, отправить обращение". Если клиент уже перешёл в поля до прихода подсказки, они не сворачиваются: форма не прячет то, что человек заполняет. Ошибка отправки поля раскрывает. Описание после возврата со страницы решения берётся из черновика на устройстве (UX-C-02).
7. **Предел частоты и короткий запрос:** сверх предела и короче 3 знаков блок просто не показывается, форма работает; длиннее 500 знаков отклоняется (страница отправляет первые 500). Любая ошибка подсказки на странице даёт пустой блок.
8. **Сбой сервиса векторов (решение 5):** вектор запроса ждём 150 мс, затем поиск по сигнатуре, словам и триграммам; событие `kb.suggest_embedder_unavailable` с причиной и временем, без текста. Отдельной системы метрик в портале нет: событие журнала и есть метрика.
9. **Связанные решения (FR-AG-05):** поиск по теме и сигнатуре обращения тем же запросом, аудитории `internal` и `clients`, без пределов и без исходов. Ссылку в ответ (адрес портала на языке обращения) можно вставить только на решение для клиентов; у внутреннего пометка "перескажите своими словами".
10. **Бюджет скриптов:** клиентский код подсказки около 2 КБ, страница нового обращения на телефоне по-прежнему 158 КБ из 170 (`tests/e2e/budget.spec.ts`).

## Замер FR-SOL-14

Машина разработчика: 4 ядра, 15 ГБ, PostgreSQL 18 в контейнере testcontainers, портал в процессе теста (пул 10 соединений), векторы заглушки (в процессе, без сети). Набор: 200 000 обращений (`seedBulkTickets`), 1000 решений на трёх языках (3000 строк индекса, 10% внутренних, `seedBulkSolutions`). Полный путь `suggestForClient`: два предела частоты (сняты по величине, но считаются), вектор, гибридный запрос, запись исхода.

| Что | Значение |
|---|---|
| По одному запросу, после прогрева | 56-97 мс |
| 1000 запросов за 20 с, 49,9 в секунду | p50 72 мс, **p95 107 мс**, p99 161 мс, максимум 235 мс |
| Запросов с подсказкой | 625 из 1000 |
| До правок запроса (`ts_rank_cd`, триграммы в обе стороны, соединение с `unnest`) | 150-220 мс по одному, при 50 в секунду очередь к пулу дольше 5 с |

Цель 95% не дольше 500 мс выполнена с запасом на стуб-векторах. С настоящим TEI к ответу прибавится время вектора: не больше 150 мс по решению 5, итого в худшем случае около 260 мс на p95. Под политиками RLS операторы поиска не помечены безопасными, PostgreSQL просматривает 3000 строк индекса без индексов i3-i5 (план в замере); на 1000 решений это 3 мс просмотра, самое дорогое триграммы (38 мс из 83). Запрос подсказки не читает обращения вовсе (интеграционный тест записывает все запросы функции), поэтому от числа обращений время не зависит. Повторить: `pnpm exec vitest run --project perf --silent=false`.
