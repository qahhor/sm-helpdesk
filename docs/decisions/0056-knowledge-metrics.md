## Решения, которых нет в ТЗ

1. **Границы модулей.** Показатели знаний считает модуль `hdk` своим слоем api, страница показателей собирает их рядом с показателями поддержки `hdt`; период берётся тот же, что выбран на странице (начало и конец из `getMetrics`). `hdk` берёт у `hdt` только правило срезов `canSeeBreakdown`, у `hdu` названия организаций.
2. **Доля самостоятельно решённых** это сессии формы с исходом "Помогло" среди всех сессий с показом подсказки (решение 12: строка на сессию, исход один). Ушедшие без действия (`left`) в долю не входят: неизвестно, решилась ли проблема; их число показано отдельно, рядом доля сессий, закончившихся обращением. Голоса "Помогло" со страницы решения без подсказки в долю не входят (решение 0049, пункт 9): они видны в счётчиках решения. Период по времени первого показа; период без показов даёт строку "подсказка не показывалась" вместо нулевых карточек (браузерный тест пустого периода ждёт, что карточек нет). Цена ошибки: если владелец считает "ушёл без обращения" решённым, доля меняется одной строкой.
3. **Права как у страницы M8 (решение 14):** сводку подсказки и частые ошибки видят все сотрудники (в них нет данных организаций: пример текста очищен, число организаций без названий), срез исходов по организациям видят Customer Care, продукт, администратор и руководители линий. "Создать решение" только у ролей черновиков (решение 10); `product` видит список без ссылки. Клиент не получает ничего.
4. **Частые ошибки без решения (FR-MET-05):** сигнатура без решения или с решением в архиве, встречалась у клиентов в выбранном периоде (`last_seen_on`), порядок по числу организаций, затем по числу встреч, первые 20. Числа за всё время, а не за период: отдельного учёта встреч по дням нет, а обращения модуль знаний не читает. "Создать решение" открывает новое решение с этой сигнатурой: после создания она привязывается сразу (решение 0055, пункт 8).
5. **Пересмотр (решение 18)** одной чистой функцией и тем же условием в SQL списка: исходов не меньше 10 и "не помогло" строго больше 40%, без округления (40% ровно не в списке). В списке решений у каждой строки показы, "помогло", "не помогло", фильтр "На пересмотр" в форме фильтров; "Мои задачи" держат решения автора на пересмотре, как и раньше. Счётчик "использовано AI-помощником" появится с помощником (M5b).
6. **`pnpm eval:search` на testcontainers,** а не на базе разработки: прогон начинается с пустой базы, публикует решения набора обычным путём (черновик, публикация, задача индекса) и не оставляет следов в `hub`. Тот же контейнер и настройка, что у интеграционных тестов (Docker обязателен). Запросы идут через `searchSolutions` от имени клиента, аудитория `clients`, сигнатура из текста запроса, как в подсказке; пределы частоты и запись исходов не участвуют (это не поиск). Векторы по `EMBEDDINGS`, по умолчанию заглушка. Отчёт по умолчанию не проваливает прогон; `EVAL_STRICT=1` даёт код 1 при непройденном пороге.
7. **Подсчёт 15.4:** правильное решение среди показанных (не больше трёх) по каждому языку; ложный показ: у запроса без решения показано хоть одно решение, доля среди запросов без решения. У английского порога в ТЗ нет, доля печатается для сведения. Набор из одного языка на решение: переводы решения в наборе не описываются, цепочка языков поиска (FR-SOL-10) работает как в подсказке.
