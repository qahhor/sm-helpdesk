# 0058. Виджет: реестр, токен контекста, заголовки встраивания

Дата: 25.11.2026. Веха: M6, задачи 1-3. План: `docs/plans/M6.md` (решения 1-17 подтверждены владельцем 25.11.2026). Статус: принято исполнителем. Здесь только то, чего нет ни в ТЗ, ни в решениях плана.

## Реестр (задача 1)

- Колонки `hdu_servers`: `context_issuer`, `context_key_mode`, `context_jwks_url`, `context_secret`, `embed_key`, `embed_origins` (миграция `0078_hdu_widget_registry.sql`). Права `hub_app` на колонки не расширены: ни одна новая колонка ему не нужна, секрет закрыт так же, как секрет OAuth.
- `context_issuer` обязателен и уникален (`hdu_servers_u5`). Новый сервер без явного значения получает адрес сервера входа триггером `t_hdu_servers_context_issuer`, действующие серверы получили его миграцией. Издатель сравнивается с `iss` буква в букву, поэтому сохраняется как введён, без приведения адреса.
- `embed_key`: 32 шестнадцатеричных знака. В базе нет pgcrypto, значение по умолчанию берётся из `sha256` двух случайных `uuid` (в каждом 122 случайных бита). Ключ не меняется: смена сломала бы подключённый Smartup Web.
- Режим `secret`: секрет создаёт портал (32 случайных байта, base64url), показывает администратору один раз и хранит запечатанным с местом `hdu_servers:<код>:context`, отличным от места секрета OAuth: строки нельзя подставить одну вместо другой. `hub secrets:reseal` перешифровывает оба секрета сервера. Кнопка "Создать новый секрет" заменяет прежний сразу.
- Сохранение режима `jwks` без адреса ключей отклоняется (и проверкой `hdu_servers_c13` в базе). Адрес ключей проверяется по правилам T16 (`assertPublicUrl`).
- Адреса встраивания: до пяти, ровно схема, узел и порт (сверка с `URL.origin`), https; http только при портале на localhost и только для `localhost` и `127.0.0.1` (решение 0015). Адрес Smartup Web разрешён всегда и в список не пишется.
- Журнал: `server.widget_updated` с именами изменённых полей и `server.context_secret_created` без значений.
- Таблица `hdu_context_token_uses` под ролью `hub_auth`, только актор system. Изменения строки нет ни у кого, удалить можно только строку с вышедшим сроком (ограничивающая политика): иначе удаление открыло бы повтор токена.

## Токен контекста и токен виджета (задача 2)

- `jose` 6.2.17 (MIT) прямой зависимостью, та же версия, что уже стояла через `better-auth` (решение 3 плана). Функции `createRemoteJWKSet`, `customFetch`, `jwksCache` и вложенные пути пакета запрещены правилом `no-restricted-syntax` во всём репозитории: ключи скачивает только `safeFetchJson` поверх `src/security/outbound.ts` (`src/modules/hdu/core/context-keys.ts`).
- Кеш открытых ключей в памяти процесса: 10 минут, повторная загрузка по неизвестному `kid` не чаще раза в минуту на сервер (отсчёт от прошлой такой загрузки, а не от обычной). Открытые ключи серверов это настройки реестра, а не данные клиентов, поэтому правило "не кешировать данные клиентов" их не касается.
- Токен с заголовками `jku`, `jwk`, `x5u`, `x5c` отклоняется сразу, ещё до проверки подписи: ключ берётся только из реестра.
- Сведения токена контекста переводятся в тот же вид, что сведения OAuth, через общую таблицу `SMARTUP_CLAIMS` и идут в общий `provisionFromSmartup`. Учётная запись: та же пара "код сервера и `sub`" в `auth.account`; если её нет, обмен создаёт пользователя и способ входа так же, как первый вход OAuth. Сотрудник (строка в `hdu_staff`) получает 403, и организация для него не создаётся.
- Предел неудачных обменов (20 за 10 минут с адреса) проверяется до разбора запроса новой функцией `peekRateLimit` (`hdc`): она смотрит счётчик, не увеличивая его; неудача учитывается после отказа. После 20 неудач закрыт и верный токен с этого адреса до конца окна.
- Запрос обмена принимается только как JSON со страницы портала (`isSameOriginJson`): страница виджета и `/m/report` работают на адресе портала. Чужая страница получает 403.
- `EMBED_TOKEN_SECRET` (не короче 32 знаков, не равен `BETTER_AUTH_SECRET` и `ENCRYPTION_KEY`) обязателен в production на настоящем адресе, как остальные секреты; на localhost без него портал запускается (проверка образа в CI), а обмен отвечает 503. Издатель токена виджета: `HUB_URL`.
- Ложный выпуск: `POST /context-token?persona=&platform=` у `mock` (ES256, ключи `/context-jwks.json`) и `mock-dedicated` (HS256). Секрет `mock-dedicated` создаёт портал на карточке сервера, ложному серверу его передают переменной `MOCK_CONTEXT_SECRET`, как настоящим разработчикам Smartup. Ответы ложного сервера разрешают чтение любой странице (CORS `*`): демонстрационная страница (задача 9) работает на другом адресе.
