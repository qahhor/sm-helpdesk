Пробный прогон правил не замерялся: в списке задачи 4 его нет.

1. **Порог строки "держится":** p95 по одному вызову не выше цели, p95 восьми одновременных не выше сигнала тревоги аудита (раздел 4.3), запросов к базе не больше 25. У показателей и похожих идей сигнала тревоги нет ни в ТЗ, ни в аудите: восемь одновременных только записаны. Цель запроса очереди (50 мс) сравнивается со временем функции целиком (5-6 запросов и код), а не одного запроса: строже аудита.
2. **Похожие идеи судятся по FR-SOL-14 (500 мс), а не по странице клиента (300 мс).** Это тот же гибридный запрос, что подсказка, и он идёт, пока клиент печатает. Время растёт вместе с числом строк индекса идей: на 21 300 строк 474 мс, при восьми одновременных 1,05 с. Причина в запросе 11.6: под RLS триграммы, полнотекстовый и смысловой списки считаются по каждой строке вида (индексы i3-i5 не используются, решение 0054), самое дорогое `word_similarity` (около 220 мс). Цена: доска с тысячами идей отвечает на похожие идеи медленнее подсказки. Вопрос владельцу ниже.
3. **Поиск сотрудника по тексту: 61 мс при цели 50, ниже сигнала тревоги 200.** План (EXPLAIN): триграммный индекс `hdt_tickets_i21` находит 112 строк за 30 мс, потому что слово "обращение" есть в теме каждого из миллиона обращений набора и списки частых триграмм длинные. В жизни частые слова ("ошибка", "отчёт") дают то же. Исправление (полнотекстовый поиск по словам вместо триграмм для запросов из нескольких слов) меняет поиск FR-AG-10 и в задачу не входит. Цена: на базе в миллион обращений поиск по частому слову около 60 мс.
4. **Числа набора искусственные там, где это сказано.** У `seedBulkTickets` номер организации зависит от остатка номера обращения, поэтому у каждой организации набора один статус и одна видимость; организация А клиента замера получает около 1000 обращений вразброс. Открытые обращения разнесены на два года, как и закрытые, поэтому очередь "В разработке" содержит давние обращения со сроком впереди (так и была найдена проблема пункта 7). С ключом `finished` первый ответ через 20 минут после создания и завершение через два часа: иначе время ответа каждого обращения считалось бы рабочими минутами за месяцы.
5. **Проект `perf` поднимает базу с памятью из `compose.prod.yaml`** (`tests/perf/global-setup.ts`, переменная `PG_SETTINGS` в общей настройке тестов; без неё всё как раньше). С настройками образа по умолчанию (shared_buffers 128 МБ) тот же набор меряет чтение с диска, которого на сервере не будет. Цена: замер на машине с меньше чем 2 ГБ свободной памяти не запустится.

### Исправления (каждое с тестом, без новых индексов; бюджет индексов таблицы обращений не менялся, 25)

6. **Гибридный поиск соединяет со списками только найденное** (`src/modules/hdk/core/search.ts`): выдача строится от объединения трёх списков (до 60 строк, CTE `hits`), а не от всех документов вида с проверкой "есть ли в списке". Планировщик соединял каждый документ с каждым списком вложенным циклом: 40 из 110 мс запроса подсказки. Векторы больше не копируются в общую CTE `docs` (она читается четырежды и на 21 тысяче строк уходила во временный файл 16 МБ); смысловой список читает те же строки индекса с теми же условиями сам. Выдача та же (тесты подсказки, похожих идей и проверочный набор поиска без изменений). Подсказка на 1000 решений при 50 запросах в секунду: p95 1837 мс до правки, 197 мс после (настройки образа по умолчанию), 113 мс с памятью `compose.prod.yaml`. Тест плана: `query-plans.test.ts`, "гибридный поиск соединяет со списками только найденные документы".
7. **Состояние срока в очереди не проходит календарь за годы** (`slaPhase` в `src/modules/hdt/core/sla.ts`): "скоро" значит, что всего рабочего времени срока больше `left / 0,2`; счёт рабочих минут теперь останавливается на этой границе (`workingMinutesBetween` с пределом, `src/modules/hdt/sla.ts`). Результат тот же, тест `sla.test.ts` "рабочие минуты с пределом". Очередь "В разработке": 103 мс до правки, 24 после.
8. **Сводка, источники и каналы показателей одним просмотром** (`sourceCountersTx`, `combineCounters`): было три просмотра одних и тех же 130 тысяч строк периода по 130-200 мс. Средняя оценка теперь сумма оценок на их число, а не `avg()` базы: значение то же с точностью до последнего знака двоичной дроби. Тест `hdt-metrics.test.ts`. Страница за 90 дней: p95 1853 мс до правки, 1351 после. Восемь одновременных показов 4,5 с: каждый показ читает период шесть раз (сводка, завершённые, решённые, ответы, низкие оценки, два среза).

### Вопросы владельцу

- **Похожие идеи на тысячах идей (пункт 2).** Варианты: отметить операторы поиска безопасными для выполнения раньше политик, как `ILIKE` (решение 0041), чтобы индексы i3-i5 работали под RLS; либо смысловой список через индекс HNSW (приблизительный поиск, выдача может немного отличаться). Пока идей сотни, ответ около 20-40 мс, решение можно отложить до роста доски.
- **Поиск по тексту на миллионе обращений (пункт 3):** принять 60 мс при частом слове или заказать поиск по словам.

## Копия и восстановление (задача 5)

9. **Проверка копии идёт интеграционным тестом** `tests/integration/restore-roundtrip.test.ts`, а не только репетицией: копия `pg_dump -Fc` под суперпользователем (как `backup.sh`), второй сервер PostgreSQL, `bootstrap` (шаг 2 памятки), `pg_restore --clean --if-exists --exit-on-error` (шаг 4), `migrate` (шаг 6, применять нечего). Сверяются строки каждой таблицы схем `public`, `auth`, `app`, `pgboss`, `migrations`, `ops`, флаги RLS, политики, владельцы и права функций, таблиц, колонок и схем, права по умолчанию, триггеры, ограничения, индексы, последовательности, расширения, членство ролей. Потом портал работает на восстановленной базе: списки и страница обращения клиента и сотрудника, голос идеи через функции `hub_hdi_counter`, задача pg-boss под `hub_app`, запечатанный секрет открывается тем же ключом. Тест идёт в обычном прогоне `pnpm test:integration` (около 12 секунд, из них копия и восстановление 2,4 с): копия проверяется при каждой новой миграции. Набор "строки во все таблицы" вынесен из теста изоляции в `tests/integration/isolation/seed-everything.ts`, тест изоляции не изменился.
10. **`pg_dump` выполняется внутри второго контейнера** и ходит к первому через шлюз сети Docker: клиент PostgreSQL на машине сборки версии 16 и копию сервера 18 не снимет. Цена: тест требует, чтобы контейнер видел порты машины (обычная сеть Docker).
11. **Права сравниваются действующие, проверки без скобок.** После восстановления у схемы `ops` пустой список прав вместо явного "только владелец" (`REVOKE ALL ... FROM PUBLIC` в `bootstrap`): pg_dump не пишет права, равные умолчанию, смысл тот же; тест сравнивает `coalesce(acl, acldefault(...))`. Проверки с `BETWEEN` внутри `AND` после разбора текста копии теряют пару скобок; тест сравнивает их текст без скобок. Расхождений по существу копия не дала.
12. **Отметка `ILIKE` безопасным (bootstrap) в копию не входит**: она живёт в `pg_catalog`. Её ставит `bootstrap` до восстановления, тест это проверяет. Памятка уже ставит `bootstrap` шагом 2.
13. **Репетиция восстановления на момент времени повторена** на PostgreSQL 18.7 с настоящими `age`, `base-backup.sh`, `wal-ship.sh` и `restore-pitr.sh`; `docker compose` и `rclone` заменены прокладками (контейнер базы вместо стека, каталог вместо бакета), отметку копии писала собранная команда `hub` (`dist/hub.mjs`). Сценарий репетиции в репозиторий не добавлен: он повторяет шаги памятки на машине разработки, на staging их выполняют по памятке. Итог в журнале проверок `docs/runbooks/restore.md`. Неверных шагов памятки репетиция не показала, поэтому памятка не менялась (кроме журнала); проверка владельца функций идей в шаге 7 из плана задачи 5 перенесена в общую правку памяток задачи 8.
