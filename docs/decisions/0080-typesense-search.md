## Проверено на контейнере 30.2 (digest `sha256:610f2d34...e110` совпал с планом)

1. Поле с `locale: uz` принимается. `stem: true` для `uz` сервер отклоняет: "The `locale` value of the field is not supported for stem". Свой словарь (`stem_dictionary`) для поля `uz` и для поля без языка принимается. Узбекская латиница с `ʻ` остаётся одним словом (`oʻzbek`), запрос `ozbek` его не находит: свёртка в поля `*_fold` нужна.
2. Ключ с областью из портала совпадает с примером документации. Вложенный `filter_by` соединяется с условием запроса через "и": запрос с чужой организацией получает пусто. Вложенный `include_fields: id` запрос не переопределяет. Просроченный ключ даёт 401.
3. Ключ поиска с перечнем коллекций сверяется с именем в запросе, то есть с псевдонимом: клиентский ключ на `hub_tickets`, `hub_solutions`, `hub_ideas` не ищет в `hub_ticket_texts`. Ключ записи с коллекциями `hub_.*` создаёт коллекции, псевдонимы, наборы синонимов и курирования и словарь `hub_*`, а коллекцию `other` создать не может (401). Ключ поиска не пишет (401).
4. Закреплённый правилом курирования внутренний документ клиенту не приходит при `filter_curated_hits: true` в ключе.
5. **Синонимы без `locale` действуют только на поля без `locale`.** Поэтому запись синонимов уходит копией на каждый язык полей (`ru`, `en`, `uz`) и копией со свёрнутыми словами без языка для полей `*_fold` (`expandSynonyms`).
6. **Словарь стемминга коллекция берёт при создании.** Импорт в тот же словарь добавляет пары к прежним; новые пары не действуют ни на новые документы, ни после повторной записи. Действуют в коллекции, созданной после замены словаря. Смена словаря: словарь удаляется и импортируется заново, затем переиндексация решений и идей (решение 0082).
7. Пустой словарь импортировать нельзя ("Invalid dictionary format"): в пустой словарь кладётся служебная пара `hubhub`.

## Решения, которых нет в плане

1. **Два ключа поиска, а не один.** Решение 0070 (пункт 3): переписку видит только сотрудник. Один ключ поиска на все `hub_*` позволил бы ключу с областью клиента искать в переписке своей организации, включая внутренние заметки. `TYPESENSE_SEARCH_KEY` (клиентский) не видит `hub_ticket_texts`, `hub_orgs`, `hub_people`; `TYPESENSE_STAFF_SEARCH_KEY` видит всё. Оба только `documents:search`. Цена: три секрета вместо двух.
2. **Текст на поле своего языка.** У поля один `locale`, поэтому `title_ru`, `title_en`, `title_uz` и так далее; документ заполняет поле своего языка. Цена: в запросе 6-8 полей.
3. **Заглушка ищет по свёрнутым словам** с опечатками по длине слова, как Typesense по умолчанию. Это проверка порядка работы, а не качества: качество проверяет набор на контейнере.
4. **`SEARCH_PROVIDER=stub` только на localhost.** Индекс заглушки живёт в памяти одного процесса: портал и фоновый процесс не делят его.
5. **Отключённый поиск откатом не считается:** `SEARCH_PROVIDER=postgres` не пишет событий и не растит счётчик сигнала `search_unavailable`.
