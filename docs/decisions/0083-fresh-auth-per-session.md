# 0083. Недавний вход считается от проверки личности в сессии

Дата: 26.11.2026. Продолжение решения 0067 (пункты 10 и 11). Одобрено владельцем: закрыть обход обычным входом через Smartup. Статус: принято исполнителем.

## Что было

Недавний вход (15 минут, `FRESH_SIGN_IN_SEC`) считался от создания сессии. Обычный вход через Smartup (без `reauth=1`) проходит по открытой сессии Smartup Web без пароля, и его сессия тоже считалась недавней. Человек за чужим незаблокированным компьютером с открытым Smartup Web входил в портал и сразу менял адрес для входа или завершал другие сессии владельца.

## Что решено

1. **Колонка `auth.session."freshAuthAt"`** (миграция `0090_session_fresh_auth.sql`): когда в этой сессии человек подтвердил личность. Пишет её только перехватчик создания сессии (`src/modules/hdu/auth/hooks.ts`); в настройках библиотеки поле `input: false`, продление сессии его не трогает.
2. **Кто ставит.** Ссылка из письма, ссылка из бота Telegram и приглашение (одноразовая ссылка на почту): время входа. Сотрудник: пароль и код второго фактора (и сессия одного пароля, которая открывает только подключение второго фактора). Вход через Smartup: только возврат после "Войти заново" (`prompt=login`, `max_age=0`), прошедший проверку `auth_time`. Если `auth_time` в `id_token` нет, время всё равно ставится, раз `prompt=login` запрошен, и в журнал идёт `auth.reauth_unverified`, как раньше. Обычный вход через Smartup оставляет пусто.
3. **Кто проверяет.** `isRecentSignIn` (смена адреса для входа, завершение другой своей сессии и всех других) и `isFresh` (настройки сотрудников) считают окно от `freshAuthAt`; пусто значит "не недавний". Завершение своей текущей сессии (выход) по-прежнему без проверки. Контексты `ClientContext` и `StaffContext` несут `freshAuthAt` вместо `sessionCreatedAt`.
4. **Брошенный вход заново.** Обычное начало входа через Smartup убирает куку `hub_reauth`: иначе обычный вход в течение 10 минут после брошенного "Войти заново" считался бы входом заново без `prompt=login`.
5. **Действующие сессии при выкладке.** Сессиям сотрудников время переносится из `secondFactorAt`: они открыты паролем с кодом. Клиентским не переносится, способ их входа по строке не узнать: клиент, которому нужно сменить адрес или завершить сессии, один раз входит заново.
6. **Одно хранилище входа заново на процесс** (`src/modules/hdu/auth/reauth.ts`, `globalThis`). Экземпляр библиотеки входа общий для процесса, а Next.js собирает модуль в несколько слоёв: хранилище, заведённое обработчиком возврата одного слоя, перехватчики экземпляра из другого слоя не видели. Браузерный тест показал, что вход заново тогда не ставил `freshAuthAt`; по той же причине в сборке могла не срабатывать и проверка `auth_time` из решения 0067, пункт 11 (интеграционные тесты идут одним слоем и этого не ловят).
7. **Шаг первого входа.** Новый клиент после обычного входа через Smartup на шаге "Укажите email" получает "Войти заново"; после входа заново шаг открывается снова с тем же адресом. Пропуск шага и привязка Telegram проверки не требуют.

## Цена

Клиент, вошедший через Smartup обычной кнопкой, для смены адреса для входа и завершения других сессий всегда проходит "Войти заново", даже если вошёл минуту назад. Защита по-прежнему держится на том, что сервер Smartup выполняет `prompt=login` и `max_age=0`: если он их пропускает и `auth_time` не ставит, вход заново проходит по открытой сессии Smartup Web (вопрос в `docs/questions.md`, ASVS V7.5.1, V7.5.2 остаются "частично").

Тесты: `tests/integration/fresh-auth.test.ts`, `tests/integration/client-fresh-sign-in.test.ts`, `tests/e2e/sessions.spec.ts`, `tests/e2e/login-link.spec.ts`.
