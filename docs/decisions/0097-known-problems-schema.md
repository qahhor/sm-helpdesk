# 0097. Таблицы известных проблем

Дата: 27.11.2026. План M5c, задача 1; FR-KP-01, 02, 10, раздел 10.5, 15.2. Принято исполнителем по общему поручению владельца. Статус: принято исполнителем.

## Что решено

1. **Модуль `hdp` и имена** (решение 1 плана): `hdp_problems`, `hdp_problem_translations`, `hdp_problem_signatures`, представление `hdp_problems_public`, миграция `0098_hdp_problems.sql`. Номер `KP-n` из последовательности `hdp_problems_number_sq`.
2. **Клиент только через представление** (решение 2). У таблиц нет ни одной политики для клиента. `hdp_problems_public` (`security_barrier`, владелец `hub_owner`, политики `*_owner_select`) отдаёт номер, статус, модуль, идентификатор обходного пути, момент исправления, язык, публичные название и описание. Строки: признак показа, статус не `closed`, `fixed` не старше 30 суток, текст сотрудника или принятый машинный перевод с непустыми названием и описанием. Без актора и под `hub_auth` пусто. Текст обходного пути клиент читает только из `hdk_published` по идентификатору.
3. **Кто пишет** (решение 3). `app.hdp_can_write()`: система, `agent_l2`, `care`, `admin`. Политика `hdp_problems_linker_update` пускает сотрудника, который ведёт обращения, обновить строку проблемы при привязке обращения, а триггер `t_hdp_problems_guard` разрешает ему менять только счётчики.
4. **Счётчики считает база.** `ticket_count`, `org_count`, `first_seen_on`, `last_seen_on` пересчитываются триггером при каждом обновлении строки проблемы по `hdt_tickets.known_problem_id`; присланное значение отбрасывается. После отвязки всех обращений моменты появления остаются прежними. Моменты `fixed_on` и `closed_on` ставит база при смене статуса; из `closed` перехода нет.
5. **Сигнатура уникальна среди активных** (решение 7): колонка `is_active` у сигнатуры ставится триггером по статусу проблемы, частичный уникальный индекс `hdp_problem_signatures_u1 (signature) where is_active`. Возврат исправленной проблемы в работу отклоняется, если её сигнатура уже у другой активной.
6. **Внешний ключ** `hdt_tickets_f7` (`known_problem_id`) добавляется `NOT VALID` с проверкой, частичный индекс `hdt_tickets_i28` создаётся вне транзакции отдельной миграцией `0099_hdt_known_problem_index.sql`. Из-за неё миграции задач 3, 5, 6 сдвинуты на номер: `0100`, `0101`, `0102`.
7. **Задача разработки** не колонка проблемы: её даёт привязка `hdw_dev_task_links.known_problem_id` задачи 8 (решение 25).

## Цена

Без актора (миграции, суперпользователь в тестах) триггер не пересчитывает счётчики и пропускает любые поля, кроме номера: подготовка данных в тестах проще, у `hub_app` без актора доступа к строкам нет. Пересчёт идёт при каждом обновлении строки проблемы: для десятков проблем с сотнями обращений это дёшево (частичный индекс по `known_problem_id`).
