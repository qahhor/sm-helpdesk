# 0101. Рассылка обновления и закрытие известной проблемы

Дата: 27.11.2026. План M5c, задача 5; FR-KP-06, 07, 11.14, FR-NT-12, 14, T23, S9, строка M5c 16.2. Принято исполнителем по общему поручению владельца. Статус: принято исполнителем.

## Что решено

1. **Таблица** `hdp_broadcasts` (миграция `0101_hdp_broadcasts.sql`): автор, вид `update` или `closing`, язык автора, `body` по языкам (то, что уйдёт клиентам), `machine` (машинные переводы только для окна подтверждения), `recipient_ids` (получатели на момент подтверждения), счётчики, статусы `draft`, `queued`, `sending`, `done`. Статус `draft` добавлен к плану: черновик окна подтверждения живёт строкой, а не в браузере. Подтверждённую рассылку триггер не даёт менять, кроме хода отправки. Клиент не читает ни одной строки.
2. **Колонка** `hdt_ticket_messages.broadcast_id` с проверкой "только публичное сообщение сотрудника" и частичным уникальным индексом `hdt_ticket_messages_u2 (ticket_id, broadcast_id)` плюс индекс по внешнему ключу; оба создаются вне транзакции отдельной миграцией `0102_hdt_broadcast_message_index.sql`. Поэтому миграция объявлений задачи 6 получила номер `0103`.
3. **Порядок 11.14** (решение 17): подготовка проверяет текст (`checkPublicText` с названиями и ИНН организаций привязанных обращений), считает получателей (привязанные обращения `new`, `in_progress`, `waiting_customer`, `in_development`, не объединённые) и ставит `problems.translate` на каждый язык получателей. Экран подтверждения `/agent/problems/[n]/broadcast/[id]`: текст автора, поле на каждый язык с машинным переводом как предложением, "Получат: N обращений, M организаций", флажок "текстом оригинала". Уходит то, что стоит в поле при подтверждении: машинный перевод без просмотра сотрудником не уходит. Окно сделано страницей, а не всплывающим окном: работает без скриптов и на телефоне.
4. **Отправка без дублей** (решение 18): задача `problems.broadcast` (ключ одиночки по рассылке) идёт по получателям подтверждения, по одному обращению за транзакцию: блокировка обращения, проверка "всё ещё привязано и открыто", вставка сообщения `on conflict do nothing`, письмо и сообщение бота только после удачной вставки. Привязанное после подтверждения и закрытое во время рассылки сообщения не получают. Сбой посреди рассылки бросается, повтор доставляет оставшимся. По окончании `done` и число доставленных по самим сообщениям.
5. **Сообщение** (решение 19): публичное сообщение от имени автора рассылки, только из текста рассылки на языке обращения (иначе оригинал); ставит первый ответ и снимает "клиент ждёт", не меняет исполнителя, очередь и статус. Событие для правил автоматизации не пишется: массовая операция не должна запускать правила "сотрудник ответил" на десятках обращений. В портале помечено "Обновление по известной проблеме".
6. **Закрытие** (решение 20): окно закрытия с обязательным итоговым текстом; подтверждение той же транзакцией ставит проблеме `closed` (сигнатуры перестают притягивать сразу) с записью журнала. Задача после итогового сообщения переводит обращение в "Решено" разрешёнными переходами ("Новое" через "В работе"), каждый переход с событием истории и журналом аудита, итог `solved`. Итог `fixed_in_version` с версией задачи разработки появится в задаче 8.
7. **Письмо и Telegram** (решение 21): шаблон `problem_update` (номер и статус проблемы, текст рассылки, ссылка на обращение), вид уведомления `problem_update`, сообщение бота общим путём M4b ("Обновление по известной проблеме KP-n"). Получатели и каналы те же, что у ответа сотрудника: автор и подписчики, кто видит обращение.

## Цена

Рассылка не меняет распределение работы: обращение, которое ждало сотрудника, после рассылки уходит из "клиент ждёт", хотя сотрудник ему лично не отвечал. Правила "сотрудник ответил" на сообщения рассылки не срабатывают.
