# 0160. Язык профиля после входа; часовой пояс дат у клиента остаётся вопросом владельцу

Дата: 28.11.2026. Сверка с ТЗ, волна 7, находка T5 (FR-I18N-06, FR-I18N-08).

1. **Язык (сделано).** Язык страницы без языка в адресе выбирался по куке устройства и языку браузера; язык профиля (`auth.user.locale`: выбор в портале или язык из Smartup при первом входе) после входа не участвовал. Теперь страница после входа клиента (`/welcome`, через неё идёт вход через Smartup) переводит на язык пользователя: сначала язык, выбранный на этом устройстве (кука), затем язык профиля, затем язык страницы входа. Адрес возврата `next` получает тот же язык. Чистые функции `signedInPath` и `relocalize` в `src/i18n/resolve-locale.ts`, тест `tests/unit/i18n/resolve-locale.test.ts`.
2. **Почему кука раньше профиля.** Кука ставится только явным выбором в переключателе языка на этом устройстве; вошедшему пользователю тот же выбор пишется и в профиль. Профиль без куки: новое устройство или первый вход, где язык пришёл из Smartup.
3. **Вход сотрудника** идёт мимо `/welcome` и язык профиля не применяет: интерфейс рабочего места открывается на языке страницы входа или куки. Сделать то же для сотрудников можно тем же вызовом в оболочке рабочего места.
4. **Часовой пояс (не сделано, пометка владельцу).** FR-I18N-08 требует даты и время в часовом поясе пользователя, кроме сроков обращения (календарь поддержки, FR-SLA-08). Сейчас все даты на страницах клиента считаются по `Asia/Tashkent` (`src/i18n/format.ts`). Страницы клиента серверные и пояса браузера не знают. Варианты: (а) кука с поясом браузера, которую ставит маленький скрипт при первом заходе, и формат дат по ней; (б) пояс в профиле пользователя с выбором в настройках; (в) оставить Ташкент для этапа 1, пока все клиенты пилота в Узбекистане, и подписывать пояс у дат. Нужен выбор владельца: вариант (а) меняет вывод каждой даты кабинета и требует проверки бюджета скриптов. До ответа требование FR-I18N-08 в перечне требований отмечено перенесённым в этой части.
