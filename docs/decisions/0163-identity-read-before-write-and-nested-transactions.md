# 0163. Сведения о получателях читаются до транзакции записи; вложенные транзакции ловит тест

Дата: 28.11.2026. Проверка качества, волна 7b, находки Q2, Q3, Q11, Q12.

1. **Что нашли.** Транзакция записи обращения (роль `hub_app`) внутри себя спрашивала таблицы идентичности: роли получателей, привязку Telegram, название организации. Каждый такой вопрос открывал вторую транзакцию на пуле `hub_auth`. Первая держала соединение и блокировку обращения, пока вторая ждала свободное соединение. Под нагрузкой это очередь на двух пулах сразу.
2. **Решение для получателей (Q2).** Вызывающий читает сведения до своей транзакции и выполняет её внутри `withIdentitySnapshot` (`src/modules/hdu/api/identity-snapshot.ts`). Функции `replyRoles`, `telegramLinkedMany` и `organizationName` сначала смотрят в снимок и идут в базу только за тем, чего в нём нет. Для обращения снимок собирает `src/modules/hdt/core/notice-identity.ts`: автор, подписчики, организация. Обёртки стоят на создании обращения (клиент, сотрудник за клиента, письмо), ответе сотрудника, смене статуса, объединении, сообщениях Теза, рассылке по известной проблеме, передаче в разработку, разборе событий автоматизации, правилах "нет активности", автозакрытии и напоминании клиенту.
3. **Это не кеш.** Снимок живёт одну операцию, читается прямо перед транзакцией и никому больше не виден. Правило "не кешировать данные клиентов" не затронуто. Окно между чтением ролей и записью уведомления было и раньше; теперь оно на несколько миллисекунд шире. Цена ошибки: участник, отключённый в это окно, получит одно лишнее уведомление по обращению, которое видел секунду назад.
4. **Запасной путь остаётся.** Получатель, которого нет в снимке (подписчик добавлен между чтением и транзакцией), читается из базы изнутри транзакции, как раньше. Уведомление не теряется.
5. **Настройки одной выборкой (Q3, Q11).** `readSettings(codes)` в `src/modules/hdc/settings.ts`. `aiConfig()` открывал 11 транзакций при пуле в 10 соединений, теперь одну; `readTimings` четыре, теперь одну; модели всех целей читаются одним чтением; список адресов поддержки читает отметки проверок один раз. Суточный предел AI читается до транзакции проверки пределов.
6. **Правило против новых вложенных транзакций (Q12).** Находка предлагала правило в `scripts/checks`. Проверка по тексту не видит вызов через две функции и ломается от переименований, поэтому сделано иначе: `withActor` и `withIdentity` отмечают открытую транзакцию в `AsyncLocalStorage`, и транзакция, открытая внутри другой, сообщается тестам. Каждый интеграционный тест (`tests/integration/setup/each.ts`) падает, если встретил место, которого нет в списке известных `tests/integration/setup/nested-tx-allowed.ts`. Список это долг с поимённым перечнем; новое место в него не добавляется. В работе событие пишется в журнал уровнем debug (`db.nested_tx`), без текста запросов.
7. **Что осталось долгом.** Места из списка известных (чтение настроек и справочников внутри транзакций других модулей, руководители линии для уведомлений сотрудникам). Страница обращения сотрудника по-прежнему открывает шесть параллельных чтений (`loader.ts`): это разные модули, свести их в одну выборку без нарушения границ модулей нельзя.
