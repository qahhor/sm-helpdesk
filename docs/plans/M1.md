# Веха M1 "Идентичность и изоляция": план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** в портал можно войти. Клиент входит через Smartup (в разработке через ложный сервер OIDC) и по ссылке на подтверждённый email, организация и членство создаются сами. Сотрудник входит по паролю и коду второго фактора. Кабинет и рабочее место закрыты для посторонних, а база не отдаёт чужую строку даже при ошибке в коде (ТЗ, раздел 16.2, строка M1).

**Архитектура:** вход ведёт библиотека Better Auth на отдельном подключении роли `hub_auth` и в отдельной схеме `auth`. Наружу у библиотеки открыт один адрес: возврат с сервера Smartup. Все остальные операции входа выполняют серверные действия Next.js через модуль `hdu`. Серверы Smartup лежат в реестре портала, секрет клиента OAuth хранится зашифрованным. Таблицы идентичности защищены политиками RLS для обеих ролей приложения: `hub_app` их только читает, `hub_auth` меняет от имени актора. Каждое изменение прав пишет строку журнала аудита в той же транзакции.

**Стек:** как в M0 (Next.js 16.4.6, React 19.3.1, TypeScript 5.9.3, Drizzle ORM 0.45.4, `pg` 8.23.1, PostgreSQL 18, Zod 4.6.7, next-intl 4.15.1, Vitest 5.1.0, Playwright 1.63.0). Новое: `better-auth` 1.7.22, `@better-auth/sso` 1.7.22, `kysely` 0.29.9, `uqr` 0.1.3, для разработки `oauth2-mock-server` 9.3.0 и `rolldown` 1.2.19.

**ТЗ:** `docs/TZ.md` версии 1.1 от 20.11.2026. Разделы для этой вехи: 5, 7.1 (FR-ID-01..14), 7.10 (FR-ADM-01..03, 07 в части записи), 9.3, 9.4, 10.1, 10.2, 10.3, 10.5 (`invitations`, `audit_log`, `rate_limits`), 11.1, 11.2, 11.3, 12, 13.5, 14.2 (T1, T10, T11, T16), 14.3, 14.5, 15.2, 15.3 (сценарии 1 и 2), 16.2. Имена объектов: `docs/naming.md`.

## Предусловия

1. **Ветка.** Работа идёт в ветке `claude/smartup-customer-portal-iszbit`. Запрос на слияние создаётся по команде владельца продукта.
2. **Проверки.** GitHub Actions выключен (решение 99). Перед каждым коммитом задачи выполняются `pnpm check` и `pnpm test`, в конце задачи с базой `pnpm test:integration`, в конце вехи полный набор.
3. **Среда.** Node.js 26.13.1, pnpm 12.21.0, Docker. В облачной сессии: `dockerd` запускается вручную, `PG_IMAGE=mirror.gcr.io/pgvector/pgvector:pg18`, `TESTCONTAINERS_RYUK_DISABLED=true`.
4. **От разработчиков Smartup ничего не ждём.** Настоящие параметры OAuth (вопрос 3) и смысл `company_id` (вопрос 43) нужны к концу вехи для staging, но не для сборки: вход проверяется на ложном сервере. Имена полей из Smartup собраны в одном файле (`src/modules/hdu/pref.ts`), ответ на вопрос 43 меняет только его.

## Общие ограничения

Каждая задача неявно включает этот список. Значения взяты из ТЗ дословно.

- Актор строится только на сервере из проверенной сессии. Ни одно его поле не берётся из тела запроса, адреса или заголовков (раздел 11.1).
- К базе ходят только сервисы модулей и только внутри `withActor` или `withIdentity`. Подключение `hub_auth` видит только модуль `hdu` и слой `src/db`.
- Каждая точка входа (страница, серверное действие, обработчик): проверка сессии, прав и данных схемой Zod (раздел 9.4, правило 7).
- Каждая новая таблица: миграция с `ENABLE` и `FORCE ROW LEVEL SECURITY`, политики написаны руками, строка в наборе проверок изоляции, комментарий к таблице и каждой колонке.
- Каждое изменение прав и состояния (роль, приглашение, сотрудник, сервер, подтверждение email): запись в `hdc_audit_log` в той же транзакции. В журнале нет паролей, токенов и текстов обращений.
- Сессия клиента 30 дней с продлением при активности. Сессия сотрудника 12 часов (FR-ID-10).
- Ссылка для входа живёт 15 минут и срабатывает один раз. Приглашение живёт 7 дней (FR-ID-05, FR-ID-08).
- Пароль сотрудника не короче 12 знаков. Второй фактор TOTP обязателен. Вход по ссылке и через OAuth для сотрудников закрыт (FR-ID-09).
- Ответ формы входа по email одинаков для существующего и несуществующего адреса (FR-ID-06).
- Личность пользователя: пара "сервер Smartup + идентификатор пользователя". Учётные записи по совпадению email не объединяются. Email из Smartup считается неподтверждённым (решение 93).
- Ограничения частоты (раздел 14.5): запрос ссылки для входа 5 в час на адрес и 20 в час на IP; попытка входа сотрудника 10 в 15 минут на учётную запись, затем блокировка на 15 минут; проверка кода второго фактора 5 попыток. Счётчики хранятся в PostgreSQL.
- Куки сессии: `HttpOnly`, `Secure`, `SameSite=Lax`, без атрибута `Domain`. Одноразовые ссылки хранятся в базе в виде хеша. Адрес возврата после входа: только относительный путь на портале (раздел 14.3).
- Действия администратора (смена роли) требуют свежего входа и пишутся в журнал аудита (раздел 14.3).
- Адреса серверов Smartup вводит только администратор, схема только `https`, адрес не может указывать на внутреннюю сеть (угроза T16).
- Данные клиентов не кешируются: `use cache` и `unstable_cache` запрещены. Страницы с данными отвечают с `Cache-Control: private, no-store`.
- Строки интерфейса и писем лежат в `messages/*.json` на трёх языках. Цвета, размеры и радиусы только токенами. Тез и логотип только через `TezMark` и `Logo`.
- Символы U+2014 и U+2013 запрещены везде. Слова "dala", "Smartup ERP" запрещены в текстах.
- Новые пакеты: точная версия, опубликована не менее 7 дней назад, без сценариев установки (решение 98). Перед использованием API библиотеки сверка с установленной версией.
- Секреты не попадают в репозиторий, в аргументы команд и в журнал. `.env.example` содержит все имена без значений.

## На что смотреть при проверке

Пять случаев, которые ТЗ подразумевает, но прямо не описывает. Тест каждого стоит в задаче, которая владеет кодом.

1. **Smartup не передал email** (так у большинства пользователей, решение 89): вход проходит, пользователь и организация создаются, портал один раз предлагает указать адрес, шаг можно пропустить. Задачи 8 и 10.
2. **Один email у двух людей или у клиента и сотрудника:** тот же адрес приходит с другого сервера, от другого пользователя того же сервера или совпадает с адресом сотрудника. Учётные записи не объединяются, чужая сессия не выдаётся, права сотрудника не появляются. Задача 8.
3. **Ссылку из письма первым открыл почтовый сканер:** ссылка не сгорает, вход выполняет только нажатие кнопки человеком. Повторное нажатие даёт понятное сообщение, а не ошибку сервера. Задачи 10 и 11.
4. **Доступ отозван посреди сессии:** членство или организация отключены, сотрудник заблокирован, сессия завершена с другого устройства. Доступ пропадает на следующем запросе, а подставленная в сессию чужая организация не открывается. Задачи 6, 9, 13.
5. **Подменённый адрес возврата после входа** (`next=https://evil.example`, `next=//evil.example`, `next=/\evil.example`, адрес с управляющими символами): переход только внутри портала. Задача 6.

## Проверенные свойства Better Auth 1.7.22

Проверено запуском на Node.js 26.13.1 и PostgreSQL 18 (20.11.2026). Исполнитель опирается на этот список и перепроверяет только то, что помечено "не проверено".

- **База.** `database: { dialect: new PostgresDialect({ pool }), type: 'postgres', schemaName: 'auth', transaction: true }`. `PostgresDialect` импортируется из `kysely`, поэтому пакет нужен как прямая зависимость. При работе библиотека таблиц не создаёт, но при первом вызове сверяет схему и на любом вызове бросает `SchemaMismatchError`, если не хватает таблицы или колонки. Лишние колонки, индексы и тип `uuid` вместо `text` допускаются.
- **Идентификаторы.** `advanced.database.generateId: 'uuid'`: библиотека не передаёт `id` при вставке и ждёт значение по умолчанию от колонки.
- **DDL.** `import { getMigrations } from 'better-auth/db/migration'`, затем `(await getMigrations(options)).compileMigrations()` печатает DDL, которого не хватает базе. Команда `pnpm exec auth generate` из пакета `auth` даёт то же самое, в проект её не ставим.
- **Создание экземпляра** не открывает соединение. Телеметрия выключена по умолчанию.
- **Пароль.** `auth.api.signInEmail({ body: { email, password }, headers })`. При включённом втором факторе возвращает `{ twoFactorRedirect: true }`, сессию не оставляет и ставит куку `hub.two_factor` на 10 минут. Саморегистрация: `EMAIL_PASSWORD_SIGN_UP_DISABLED`.
- **Второй фактор.** `auth.api.enableTwoFactor({ body: { password }, headers })` возвращает `{ totpURI, backupCodes }` и требует сессию. `user.twoFactorEnabled` становится `true` только после первого `auth.api.verifyTOTP({ body: { code }, headers })`. Обязательность второго фактора библиотека не обеспечивает: это делает портал.
- **Блокировка кода.** `twoFactor({ accountLockout: { enabled: true, maxFailedAttempts: 5, durationSeconds: 900 } })`: пятый неверный код блокирует пользователя на 15 минут, дальше любой код отвечает 429 `ACCOUNT_TEMPORARILY_LOCKED`. Счётчик общий на пользователя, верный код его обнуляет.
- **Доверенное устройство** выключить настройкой нельзя. Запрет: `hooks.before` отклоняет запрос, если `ctx.path` начинается с `/two-factor/verify-` и в теле есть `trustDevice`.
- **Ссылка для входа.** `magicLink({ expiresIn: 900, disableSignUp: true, storeToken: 'hashed', sendMagicLink })`. `sendMagicLink({ email, url, token, metadata }, ctx)` вызывается и для неизвестных адресов. `auth.api.signInMagicLink({ body: { email, metadata }, headers })` всегда отвечает `{ status: true }`. `auth.api.magicLinkVerify({ query: { token }, headers })` без `callbackURL` возвращает `{ token, user, session }`, с `callbackURL` бросает ошибку с кодом 302. Токен в базе лежит хешем.
- **Опасное свойство ссылки.** Вход по ссылке пользователя с `emailVerified = false` удаляет все его способы входа и сессии. Поэтому ссылка отправляется только на подтверждённый адрес.
- **Вход через сервер OIDC.** `sso({ defaultSSO: [{ providerId, domain, oidcConfig }], providersLimit: 0, resolveUser, provisionUser, provisionUserOnEveryLogin: true })`. Сервер из настроек работает при пустой таблице `ssoProvider`. Строка `account`: `providerId` равен `providerId` сервера, `accountId` равен `sub`. Начало входа: `auth.api.signInSSO({ body: { providerId, callbackURL, errorCallbackURL }, headers })` возвращает `{ url }` и ставит куку `hub.state`. Экземпляр можно пересоздать между началом входа и возвратом.
- **Вход без email.** Без поля email библиотека останавливает вход до вызова `resolveUser` (`missing_user_info`). Обход: `oidcConfig.mapping.email: 'sub'`. Функция `resolveUser` обязана сама создать пользователя со служебным адресом и вернуть `{ action: 'link', userId, profile: 'preserve' }`. Вернуть "continue" для неизвестного пользователя нельзя: появится учётная запись с адресом, равным `sub`.
- **Сведения о компании.** `provisionUser({ user, userInfo, provider })` вызывается при каждом входе. В `userInfo` только сопоставленные поля, поэтому поля Smartup перечисляются в `mapping.extraFields`. Имя пользователя библиотека при повторном входе не обновляет.
- **Доверенные адреса.** Адрес каждого сервера OIDC должен входить в `trustedOrigins`, иначе `discovery_untrusted_origin` или `discovery_private_host`.
- **Перехватчики** `hooks.before`, `hooks.after` и `databaseHooks` срабатывают и при прямых вызовах `auth.api.*`. В `databaseHooks.session.create.before` поле `ctx.path` равно `/sign-in/email`, `/two-factor/verify-totp`, `/magic-link/verify` или `/sso/callback/:providerId`.
- **Срок сессии сотрудника.** Отдельной настройки нет. `session.create.before` возвращает `{ data: { ...session, expiresAt } }`, `session.update.before` не даёт продлить срок.
- **Отзыв сессии** действует на следующем запросе: кеш сессии в куке выключен по умолчанию и не включается.
- **Ограничение частоты библиотеки** не действует на прямые вызовы `auth.api.*`. Портал считает сам.
- **Пользователь.** `(await auth.$context).internalAdapter.updateUser(userId, { email, emailVerified: true })` работает. Занятый адрес даёт ошибку базы с кодом `23505`.
- **Хеш пароля.** `import { hashPassword } from 'better-auth/crypto'`. Строка `account` с `providerId = 'credential'`, `accountId` равным идентификатору пользователя и этим хешем в `password` принимается входом по паролю.
- **Куки.** Вызов `auth.api.*` с параметром `returnHeaders: true` возвращает заголовки ответа вместе с результатом, в них лежат строки `Set-Cookie`. Портал переносит их в ответ сам (задача 6) и плагин `nextCookies()` не использует: внутри Next.js 16 он не проверялся, а при отрисовке страницы куку не ставит и он.
- **Не проверено.** Разбор строки `Set-Cookie` функцией `parseSetCookieHeader` из `better-auth/cookies`: наличие и вид результата сверяются с установленной версией в задаче 6. Запасной путь: свой разбор имени, значения и атрибутов.

Правила:

- **Приглашение сотрудника.** Строка `hdu_invitations` с пустым `org_id`. Роль `agent_bot` не приглашается. Запись аудита `staff.invited`.
- **Принятие.** Одна транзакция `withIdentity` от актора `system`: приглашение действует; пользователь с таким email либо создаётся (`emailVerified = true`), либо уже является сотрудником; адрес клиента (есть членство или вход через Smartup) отклоняется с `email_taken`; строка `account` с `providerId = 'credential'` и хешем от `hashPassword`; строка `hdu_staff`; `accepted_on`; аудит `staff.created`. Повторное принятие того же токена: `link_invalid`.
- **Сброс.** Удаляет пароль, строку второго фактора и все сессии сотрудника, ставит `twoFactorEnabled = false`, создаёт новое приглашение. Аудит `staff.reset`.
- **Вход.** Один экран в три шага: email и пароль, затем код. Если второй фактор ещё не подключён, действие входа само вызывает `enableTwoFactor` (пароль у него в руках) и возвращает ключ и рисунок QR для шага подключения: пароль дважды не спрашивается и нигде не хранится. Рисунок QR строит сервер (`uqr`), браузер получает матрицу и рисует SVG. Резервные коды не показываются.
- **Счётчик.** `rateKey('staff-login:account', email)` с правилом `staffLoginPerAccount` проверяется до пароля, для любого адреса одинаково. Успешный вход с кодом сбрасывает счётчик.
- **Сообщения.** Неверный адрес и неверный пароль дают один код `invalid_credentials`. Блокировка даёт `rate_limited` с числом минут. Неверный код: `code_invalid`, блокировка кода: `code_locked`.
- **Допуск в рабочее место.** `resolveStaff`: сессия есть; пользователь действующий сотрудник; `twoFactorEnabled` истинно; с создания сессии прошло не больше 12 часов (иначе сессия отзывается). Проверка стоит в раскладке `(agent)` и в каждой странице рабочего места.
- **Аудит входа.** Успешный вход сотрудника пишет `staff.signed_in` с IP.
- **Повторный вход.** Вход с уже действующей сессией в этом браузере (свежий вход перед действием администратора) создаёт новую сессию и отзывает прежнюю.
- **Витрина компонентов** переезжает на `/{язык}/dev/ui`: она открывается без входа и только при `HUB_SHOWCASE=1`.
- **Куки.** Серверные действия получают `RequestInfo` от `nextRequest()`. Интеграционные тесты передают свой `RequestInfo`, который складывает куки в память и подставляет их в следующий запрос: так проверяется вся цепочка "пароль, затем код" без браузера.

- Секрет клиента OAuth берётся из переменной `HUB_OAUTH_CLIENT_SECRET` или вводится без отображения. В аргументах его нет: команда с аргументом `--client-secret` завершается с кодом 2 и подсказкой.
- Адреса сервера (`baseUrl`, `issuer`, адреса из `endpoints`): схема `https`; узел не `localhost`, не IP из частных, локальных и служебных диапазонов (IPv4 и IPv6), не имя с окончанием `.local`, `.internal`, `.localhost`; имя разрешается в адреса, и ни один из них не частный. Исключение `allowLoopback`: узел `localhost` и `127.0.0.1` со схемой `http` допускаются, только если сам портал запущен на localhost.
- Секрет шифруется `getSecretBox().seal(secret, 'hdu_servers:' + code)`.
- `server:add` для существующего кода обновляет имя, адреса и секрет (код не меняется). Признак `--default` снимает его с прежнего сервера в той же транзакции.
- `server:disable` ставит `state = 'passive'`: начать вход через этот сервер нельзя, начатый вход не завершается.
- Каждая команда изменения пишет аудит от актора `{ type: 'system', job: 'cli' }`: `staff.invited`, `staff.reset`, `server.added`, `server.disabled`.
- `staff:create` и `staff:reset` печатают ссылку `<HUB_URL>/ru/staff/setup?token=...` и срок. Токен нигде больше не выводится.
- Сборка: `rolldown`, вход `src/cli/main.ts`, платформа Node.js, формат ESM, псевдоним `@` на `src`, модуль `server-only` заменён пустым, внешним остаётся только `pg-native`. **Интерфейсы:**

- Даёт:
  - `type ClientContext = { actor: ClientActor; user: { id: string; name: string; hasVerifiedEmail: boolean; onboarded: boolean }; org: { id: string; name: string }; orgCount: number }`.
  - `resolveClient(session: SessionData | null): Promise<ClientContext | { denied: 'no_session' | 'staff' | 'no_organization' | 'choose_organization' }>`: ядро без Next.js.
  - `requireClientActor(): Promise<ClientContext>`: перенаправляет по причине отказа: на `/{язык}/login?next=...`, в `/agent`, на `/no-organization` или `/select-organization`.
  - `requireSignedInClient(): Promise<{ userId: string; name: string }>`: для страниц группы `(gate)`.
  - `listMyOrganizations(userId: string): Promise<{ orgId: string; name: string; role: ClientRole }[]>` (только действующие членства в действующих организациях).
  - `switchOrganization(session: SessionData, orgId: unknown): Promise<void>`: бросает `HduError('not_member')`.
  - Серверные действия: `switchOrganizationAction(formData)`, `signOutAction()`.

Правила выбора организации в `resolveClient`:

1. Пользователь из `hdu_staff`: отказ `staff`.
2. `session.activeOrgId` указывает на действующее членство в действующей организации: она и есть активная.
3. Иначе `user.lastOrgId` с тем же условием: записать в сессию и использовать.
4. Иначе ровно одно действующее членство: записать и использовать.
5. Иначе несколько: `choose_organization`. Ни одного: `no_organization`.

Членство проверяется на каждом запросе по подключению `hub_auth` от актора `{ type: 'system', job: 'identity.actor' }`. Поле `activeOrgId` меняет только сервер: `internalAdapter.updateSession(token, { activeOrgId })`. Переключение записывает и `lastOrgId` пользователя.

Оболочка кабинета: в шапке название активной организации. Если организаций больше одной, оно открывает переключатель. Меню пользователя: имя, "Настройки", "Организация" (только администратору клиента, страница появится в задаче 11), "Выйти". Данные для шапки приходят из `ClientContext`, а не из запроса браузера.

Одинаковые проверки в пределах одного запроса объединяет функция `cache` из React: это память одного запроса, между запросами она не живёт (записать в решение 0014).

Продление сессии (FR-ID-10). Срок сессии в базе библиотека продлевает сама при обращении, но при отрисовке страницы куку поставить нельзя. Поэтому `src/proxy.ts` на запросе страницы заново ставит куку сессии с тем же значением и сроком 30 дней: имя `hub.session_token` (на https `__Secure-hub.session_token`), `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` на https. Прокси в базу не ходит и сессию не проверяет: действительность сессии определяет только база.

- **Ответ не ждёт почту.** Отправка не задерживает ответ формы: по времени ответа нельзя отличить существующий адрес.
- **Ссылка.** `<HUB_URL>/{язык}/login/link?token=...&next=...`. Страница открывается запросом `GET` и ничего не меняет: на ней кнопка "Войти". Нажатие вызывает `magicLinkVerify`. Недействительная, просроченная и использованная ссылка дают одно сообщение и кнопку "Получить новую ссылку".
- **Подтверждение адреса.** Токен в `hdu_email_tokens`, срок 60 минут, одноразовый, прежние неиспользованные токены пользователя отменяются. Страница подтверждения тоже с кнопкой. Подтверждение в одной транзакции: адрес записывается в `auth."user".email`, `emailVerified = true`, `claimedEmail` очищается, токен помечается использованным, аудит `user.email_confirmed`. Если адрес уже подтверждён другой учётной записью: `email_taken`, и человек видит это только после нажатия по ссылке из письма, то есть после доказательства, что ящик его.
- **Внутренний вход** `signInByProvenEmail`: вызывает `signInMagicLink` с `metadata: { internal: <случайное значение> }`. Функция `sendMagicLink` для такого значения, заранее положенного в память процесса, письмо не отправляет, а отдаёт токен вызывающему, который сразу вызывает `magicLinkVerify`. Снаружи передать `metadata` нельзя: адрес библиотеки закрыт, а действие портала это поле не принимает.
- **Первый вход** (FR-ID-07): страница `/welcome` показывается после входа, пока `onboardedAt` пуст. Поле адреса заполнено значением `claimedEmail`. Кнопки "Отправить ссылку" и "Пропустить".
