# Отчёт по вехе M5c "Известные проблемы и кандидаты"

Дата: 27.11.2026. Ветка `claude/smartup-customer-portal-iszbit`. План `docs/plans/M5c.md` подтверждён общим поручением владельца 26.11.2026 и повторно 27.11.2026. Решения вехи: `docs/decisions/0097`-`0108`. Журнал исполнителя: `.superpowers/sdd/M5c/progress.md`.

## Итог

Массовая ошибка стала одной работой. Вторая линия создаёт известную проблему из обращения одним нажатием, остальные обращения привязываются вручную, массово, по сигнатуре при создании или правилом. Клиент с той же ошибкой видит "Мы знаем об этой проблеме" в виджете, над формой нового обращения и в своём обращении, нажимает "Меня это тоже затронуло", видит страницу `/problems`. Тез при привязанной показанной проблеме отвечает её публичным описанием без вызова модели и передаёт обращение сотруднику; при действующем объявлении "сбой" сообщает о сбое. Одно обновление сотрудника доходит до каждого затронутого ровно один раз, закрытие проблемы переводит обращения в "Решено" (с версией задачи разработки, если она известна). Customer Care публикует объявления. AI готовит из закрытых обращений кандидатов в решения, склеивает похожие, сотрудник превращает их в черновики решений, объединяет или отклоняет; решение из кандидата публикуется только после отметки каждой находки недоверенного текста.

Всё сделано на заглушках модели и векторов. С настоящим ключом Anthropic и настоящими векторами BGE-M3 ничего не проверено: их нет.

## Независимая проверка

Проведена координатором свежим проверяющим по разделу "На что смотреть при проверке" плана (доступ клиента к проблемам и рассылке, данные для модели и кандидаты). Нарушений изоляции, данных клиентов в тексте для модели и показа клиенту внутренних полей проверка не нашла. Найдено шесть замечаний, все исправлены одним проходом, каждое тестом, который сначала упал:

1. **Проблему без открытых привязанных обращений нельзя было закрыть** (важное): подтверждение закрытия отказывало `no_recipients` до перехода в "Закрыто", а смена статуса вручную закрытия не даёт. Теперь закрывающая рассылка без получателей закрывает проблему в той же транзакции с журналом аудита, итоговый текст остаётся в истории рассылок; обновление без получателей по-прежнему отклоняется, у отказа есть текст на трёх языках. Тест: `hdp-broadcasts` "закрытие без открытых привязанных обращений закрывает проблему с журналом; обновление без получателей отклоняется".
2. **"Меня это тоже затронуло" опережало задачу первой линии** (важное): обращение создавалось и ставило `ai.first_line`, а явная привязка к проблеме шла отдельной транзакцией после. Теперь известная проблема передаётся созданию обращения параметром сервера (не из тела запроса) и привязывается сразу после сигнатуры, до постановки помощника. Тест: `hda-first-line` "\"Меня это тоже затронуло\" без сигнатуры: привязка видна задаче первой линии в момент постановки, ответ проблемой без модели" (очередь проверяет привязку в момент постановки).
3. **Закрытие прямо из активного статуса оставляло `fixed_on` пустым**, и проблема не попадала в "исправлено за период". Миграция `0108_hdp_problems_fixed_on_on_close.sql` заменяет функцию триггера: переход в "Закрыто" без момента исправления ставит его; уже закрытые получают момент закрытия. Тест: `problems-metrics` "закрытие прямо из \"Исправляем\": база ставит момент исправления, проблема считается исправленной за период".
4. **Ночная склейка кандидатов не блокировала исходного кандидата**: решённый сотрудником между выборкой и склейкой кандидат терял источники. Теперь строка блокируется (`FOR UPDATE`) и проверяется заново в транзакции склейки, решённый пропускается. Тест: `hda-candidates` "ночная склейка: кандидат, решённый сотрудником между выборкой и склейкой, не трогается".
5. **Принятые переводы устаревали после правки оригинала**: клиенты на других языках видели старый принятый перевод. Теперь правка текста на языке оригинала (проблема и объявление) снимает принятие машинных переводов с журналом аудита, клиент получает текст оригинала до принятия свежего перевода (решение `0109`). Тесты: `hdp-client` "правка публичного текста на языке оригинала снимает принятие машинного перевода: клиент на uz видит новый текст", `hdp-announcements` "правка текста оригинала снимает принятие машинного перевода: клиент видит новый текст оригинала, а не старый перевод".
6. **Список массовой привязки не был ограничен схемой**: предел 100 проверялся после удаления повторов. Теперь `.max(100)` в схеме входа, длинный список отклоняется `too_many` до работы. Тест: `hdp-links` "массовая привязка: 101 обращение отклоняется целиком, до 100 итог по каждому" (добавлен случай 101 одинакового номера).

Проверки после исправлений: `pnpm check` без замечаний (линтер с `--ignore-pattern '.claude/**'`), модульные 1392, интеграционные 1563 (180 файлов), `pnpm eval:ai` 75 из 75 атак без нарушений, сборка, браузерные 498 пройдено, 0 упало, 361 пропущено.

Мелкие замечания: отложены.

- **Гонка дневного предела кандидатов** (проверка и запись не атомарны): сейчас задания кандидатов идут одним обработчиком фонового процесса, и превышение возможно только при нескольких обработчиках одновременно. Исправление запланировано вместе с ключом одиночного задания pg-boss (singleton key) при настройке параллельности обработчиков.
- **Счётчики объединённых обращений**: обращение, объединённое в другое, остаётся в числе обращений и организаций проблемы. Это показатель для сотрудников, клиент его не видит, рассылка объединённые не получает; правильное правило счёта (исключать объединённые или считать по основному) нужно согласовать вместе с показателями объединения обращений.
- **Предел частоты для поиска проблемы в подсказке**: поиск проблемы идёт до предела частоты самой подсказки и своего предела не имеет. Он не вызывает модель и поиск по базе знаний: это вычисление сигнатуры из текста и один запрос по индексу сигнатур, ответ только для показанной активной проблемы. Отдельный предел добавим вместе с общим пределом частоты действий формы обращения.

## Решения 1-30 плана для владельца

Все приняты по рекомендованному варианту; отклонения записаны в журнале (`Ruling:`) и в решениях 0097-0108. Главные:

1. Номера миграций и решений сдвинуты на два от плана.
2. Счётчики и моменты появления проблемы пересчитывает триггер базы в транзакции привязки (решения 3, 9).
3. Баннер на портале стоит над формой нового обращения (решение 13); аудитория "модуль" видна всем клиентам на главной (решение 24).
4. Рассылка останавливает срок первого ответа и не меняет исполнителя и статус (решение 19); у рассылки есть статус черновика окна подтверждения.
5. Тез определяет известную проблему по привязке обращения от имени автора, а не повторным сравнением сигнатуры; при проблеме и сбое модель не вызывается совсем, разбор не ставится (решения 22, 23). Ответ проблемой останавливает срок первого ответа, сообщение о сбое нет.
6. Версию задачи разработки для итога закрытия `hdp` получает через источник, который регистрирует сборка процесса (`hdw` стоит над `hdp`).
7. При недоступных векторах повторяется только запрос вектора, а не вызов модели; ночная склейка удаляет опустевший нерешённый кандидат.
8. Отметки недоверенного текста привязаны к отпечатку текста версии, правка их снимает (решение 30).
9. Меню: "Известные проблемы" и "Объявления" всем сотрудникам, "Кандидаты" ролям с правом черновика решения.
