# Веха M5c "Известные проблемы и кандидаты": план реализации

Статус: подтверждён владельцем общим поручением от 26.11.2026 (выполнять вехи по порядку без остановки)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** массовая ошибка становится одной работой. Вторая линия создаёт известную проблему из обращения одним нажатием, остальные обращения привязываются вручную, массово или сами по сигнатуре; клиенты с той же ошибкой сразу видят "Мы знаем об этой проблеме" в виджете, на форме нового обращения и в своём обращении, Тез отвечает публичным описанием проблемы без вызова модели. Одно обновление сотрудника получают все затронутые, закрытие проблемы переводит обращения в "Решено". Customer Care публикует объявления о плановых работах, сбоях и новостях. AI готовит из закрытых обращений кандидатов в решения, склеивает похожие, сотрудник превращает их в черновики решений или отклоняет.

**Архитектура:** новый модуль `hdp` (известные проблемы, рассылки, объявления) по `docs/naming.md` и разделу 10.3 ТЗ; кандидаты в модуле `hda`. Клиент читает проблемы только через представление `hdp_problems_public` без внутренних полей (образец `hdu_user_profiles`, миграция 0005). Автоматическая привязка по сигнатуре идёт сразу после записи сигнатуры нового обращения через интерфейс в `hdc`, реализацию даёт `hdp`, соединяет `src/wiring.ts` (образец `TicketSignatureRecorder`). Тез при привязанной публичной проблеме и при действующем объявлении "сбой" отвечает ссылкой на текст сотрудника (`ai_payload` вида `known_problem` и `outage`), модель не вызывается. Рассылка идёт фоновой задачей по одному обращению за транзакцию, повтор не создаёт дублей благодаря уникальной паре "обращение, рассылка" у сообщения. Кандидаты строятся тем же путём, что черновик решения (`assembleDraftData`, `draftSchema`), склейка по векторам BGE-M3 (`queryVector` модуля `hdk`), кандидат не попадает в поисковый индекс, пока не опубликован как решение обычным порядком.

**Стек:** как в вехах M5-M8 и M5b. Новых пакетов и внешних сервисов нет. Claude вызывает только фоновый процесс, векторы считает тот же сервис BGE-M3 (`EmbeddingProvider`), задача разработки идёт через существующий `DevTracker`.

**Источник:** `docs/TZ.md` версии 1.2: 7.15 (FR-KP-01..13), 7.16 (FR-CAND-01..09), 7.18 (FR-ANN-01..04), FR-AG-20 (часть "привязать к известной проблеме", отложенная решением 0031), UX-A-10, FR-AI-02, FR-AI-14, FR-KP-12 в шаге 4 порядка 7.13, FR-NT-12, FR-NT-14, FR-ADM-12, FR-AUTO-03 и 04 (условия "наличие сигнатуры", "привязка к известной проблеме", действие "привязать к известной проблеме"), FR-DEV-06 (привязка задачи к проблеме), FR-MET-08, FR-MET-09, FR-SOL-04, 05, 10.5 (таблицы известных проблем, кандидатов, объявлений), 10.3 (модули `hdp`, `hda`), 8.3 и 8.12 (известная проблема в виджете, карточка проблемы, список кандидатов), 8.13 (состояние "Внимание"), 11.12 (шаг 1), 11.14, 12.1 (`/problems`, `/announcements`), 14.3 (раздел "AI"), 14.5 (предел "Меня это тоже затронуло"), 15.2 (строки об известных проблемах и кандидатах), 15.3 (сценарий 13), угрозы T23 и T33, строка M5c раздела 16.2, сценарий S9.

## Общие ограничения

- Правила `CLAUDE.md`: сначала тест; `pnpm check`, `pnpm test`, `pnpm test:integration` перед каждым коммитом; каждая новая таблица с FORCE RLS и строкой в наборе изоляции (`tests/integration/isolation/tables.ts`); каждое изменение статуса, признака показа и прав с записью в журнал аудита в той же транзакции; тексты интерфейса только в `messages/*.json` на ru, uz, en; значения оформления только из токенов `src/ui/tokens.css`; Zod на каждой точке входа; база только через `withActor`; организация и пользователь только из актора.
- В Claude уходит только перечень 14.3: для кандидата публичные сообщения закрытого обращения (тема, описание, публичные ответы клиента и сотрудников) после очистки `assemble.ts`; для перевода тексты известных проблем, рассылок и объявлений, написанные сотрудником. Никогда: внутренние заметки, вложения, имена, контакты, названия и ИНН организаций, обращения организаций с выключенной AI-обработкой, тексты других обращений.
- Клиент видит текст проблемы, рассылки и объявления только в том виде, в каком его сохранил сотрудник. Машинный перевод клиенту не показывается, пока сотрудник его не принял (правило "всё общедоступное публикует сотрудник", раздел 2 ТЗ). Шаги обходного пути клиент видит только из `hdk_published`.
- Клиент не видит: внутреннее название, владельца, счётчики, разбивку по организациям, сигнатуры, задачу разработки, проблему без признака показа, кандидатов вообще. В сообщении рассылки нет текста одного клиента для другого (угроза T23): сообщение собирается только из текста рассылки.
- Кандидат не используется подсказкой и помощником (FR-CAND-06): его нет в `hdk_search_documents`, Typesense и входе первой линии; он начинает работать только после публикации решения обычным порядком.
- Каждый внешний сервис за интерфейсом с настоящей реализацией и заглушкой: Claude (`AiClient`), векторы (`EmbeddingProvider`), таск-менеджер (`DevTracker`), почта и Telegram (существующие). Локально и в тестах всё работает без ключей.
- Группа маршрутов `(public)` не получает баннеров: там нет сессии и актора, кроме public.

## Решения, принятые по рекомендации

1. **Имена таблиц.** `known_problems` → `hdp_problems`, `known_problem_translations` → `hdp_problem_translations`, `known_problem_signatures` → `hdp_problem_signatures`, `known_problem_broadcasts` → `hdp_broadcasts`, `known_problems_public` → представление `hdp_problems_public`, `announcements` → `hdp_announcements`, `announcement_translations` → `hdp_announcement_translations`, `solution_candidates` → `hda_solution_candidates`, `solution_candidate_sources` → `hda_candidate_sources`. Причина: префиксы и примеры `docs/naming.md` (`hdp_problems`, `hdp_broadcasts`, `hdp_announcements`), кандидаты в `hda` по таблице модулей 10.3.
2. **Доступ клиента к проблеме только через представление.** У `hdp_problems` и `hdp_problem_translations` нет ни одной политики для клиента; представление `hdp_problems_public` (`security_barrier`, владелец `hub_owner`, политика `hdp_problems_owner_select` для владельца, как у `hdu_memberships`) отдаёт номер, статус, модуль, обходной путь, язык, публичные название и описание, момент исправления и только строки с `show_to_clients` и статусом не `closed`, а `fixed` не старше 30 суток. Причина: роль `hub_app` общая у клиента и сотрудника, права на колонки не разделяют акторов, а представление закрывает внутренние поля для клиента базой, а не кодом.
3. **Кто ведёт и кто привязывает.** Создают, меняют, рассылают и закрывают проблемы `agent_l2`, `care`, `admin` (FR-KP-03, функция базы `app.hdp_can_write()`). Привязать и отвязать обращение может любой сотрудник, который ведёт обращения (`STAFF_WRITE_ROLES`, функция `app.staff_can_write_tickets()`). Причина: первая линия первой видит повторы, а запись проблемы остаётся за второй линией.
4. **Создание из обращения одним нажатием** (FR-KP-03). Переносятся: внутреннее название из темы, модуль, сигнатура обращения, первое появление; обращение сразу привязано, владелец создатель. Публичные название и описание пустые, признак показа выключен. Причина: текст клиента не должен уйти другим клиентам (T23); публичный текст пишет сотрудник.
5. **Признак показа включается только с публичным текстом.** Нужны публичные название и описание хотя бы на одном языке портала и пройденная проверка текста (решение 6). Смена признака пишется в журнал аудита и историю проблемы. Причина: клиент не должен увидеть пустой баннер.
6. **Проверка публичного текста.** Публичное описание, текст рассылки и объявление проверяются той же функцией `findInText`, что решения (телефоны, почта, ИНН, ПИНФЛ, длинные числа, ссылки вне разрешённых доменов), плюс названия и ИНН организаций привязанных обращений. Находка блокирует сохранение публичного текста и отправку. Причина: угроза T23, сотрудник может по привычке вставить название клиента.
7. **Сигнатура уникальна среди активных проблем** (10.5). В `hdp_problem_signatures` колонка `is_active`, её ведёт триггер при смене статуса проблемы; частичный уникальный индекс по `signature` при `is_active`. Активные статусы: `investigating`, `cause_found`, `fixing`; `fixed` и `closed` не активны. Причина: исправленная проблема не должна притягивать новые обращения с той же ошибкой, это может быть новый сбой.
8. **Автоматическая привязка по сигнатуре** (FR-KP-04). Сразу после `recordTicketSignature`, до `startAssistant`, во всех каналах создания (портал, виджет, письмо опознанного клиента, сотрудник от имени клиента, привязка из "Неопознанных"). Интерфейс `KnownProblemLinker` объявлен в `hdc` (`src/modules/hdc/known-problems.ts`), реализацию даёт `hdp`, соединяет `src/wiring.ts`. Привязываются только обращения настоящих организаций (не служебной организации "Неопознанных") и только к активной проблеме; признак показа на привязку не влияет. Сбой привязки обращение не отменяет и пишется в журнал работы без текста. Причина: так же устроена запись сигнатуры, `hdt` не зависит от `hdp`.
9. **Одно обращение, одна проблема** (FR-KP-04). Привязка к другой проблеме у уже привязанного обращения отклоняется (`already_linked`), сотрудник сначала отвязывает. Привязка закрытого обращения отклоняется. Каждая привязка и отвязка: событие истории вида `known_problem` (внутреннее), запись журнала аудита, пересчёт `last_seen_at` и счётчиков проблемы в той же транзакции. Причина: явное действие вместо тихого перескока между проблемами.
10. **Массовая привязка** (FR-AG-20). Действие `link_problem` в `bulkAction`: до 100 обращений, каждое своей транзакцией той же функцией, что одиночная привязка, итог по каждому (`done`, `refused` с кодом). Причина: порядок решения 19 из 0031.
11. **Правила автоматизации.** Условия `signature` (`is`: есть или нет) и `known_problem` (`is`: привязано или нет) принимаются схемой; действие `link_known_problem` с номером проблемы (только активной, проверка ссылки при сохранении и при выполнении). Причина: FR-AUTO-03 и 04, названные в M8 и не принимавшиеся без данных.
12. **Сроки привязанных обращений продолжают считаться** (FR-KP-13). Привязка не ставит паузу и не меняет статус. В показателях и списках есть фильтр "без известных проблем". Причина: требование ТЗ дословно.
13. **Баннер в виджете и на форме портала** (FR-KP-08). Ответ подсказки дополняется полем `knownProblem` (номер, публичное название, статус, обходной путь) при совпадении сигнатуры из контекста или текста с активной публичной проблемой. Подсказку и проблему собирает обработчик маршрута (`/api/suggest` и серверное действие формы), вызывая `hdk` и `hdp` по отдельности. На портале баннер стоит над формой нового обращения, форма остаётся ниже (на портале нет "вместо формы": клиент мог прийти не с ошибкой). Причина: модуль знаний не должен знать о проблемах, а виджет и портал идут одним путём.
14. **"Меня это тоже затронуло"** (FR-KP-08, 14.5). Создаёт обращение тем же `createWidgetTicket` или `createTicket`: тип `bug`, влияние `major`, тема из публичного названия на языке клиента, описание из текста клиента в форме, а если оно пустое, из текста ошибки контекста; привязка по сигнатуре сработает как обычно, а если сигнатуры нет, обращение привязывается явно. Не больше одного нажатия на проблему на пользователя: второе нажатие показывает номер уже созданного обращения. Причина: предел 14.5, без лишних полей.
15. **Блок "Известная проблема" в обращении клиента** (FR-KP-05): публичное название, статус, обходной путь ссылкой на `/help/a/[ref]`, только если обходной путь опубликован для клиентов. Состояние Теза "Внимание" (поза "Вираж", раздел 8.13) только через `TezMark`. Проблема без признака показа клиенту не видна, блока нет.
16. **Страница `/problems`** (FR-KP-09): активные и исправленные за последние 30 суток публичные проблемы, без счётчиков и организаций; ссылка с главной клиента. Без кеша.
17. **Рассылка** (FR-KP-06, 11.14). Сотрудник пишет текст на своём языке, задача `problems.translate` готовит машинные переводы на языки получателей (языки привязанных открытых обращений), сотрудник видит "Получат: N обращений, M организаций", принимает или правит каждый перевод и подтверждает. Без принятого текста на каком-то языке отправка недоступна, можно отправить этим получателям текст на языке оригинала одним флажком. Получатели: привязанные обращения в статусах `new`, `in_progress`, `waiting_customer`, `in_development`, созданные до подтверждения. Причина: публикует человек, перевод не уходит клиенту без просмотра.
18. **Как рассылка идёт и почему без дублей** (11.14, строка M5c 16.2). Подтверждение пишет строку `hdp_broadcasts` со статусом `queued` и ставит задачу `problems.broadcast` с ключом одиночки по рассылке. Задача берёт по одному обращению без сообщения этой рассылки и в одной транзакции пишет публичное сообщение от имени автора с `hdt_ticket_messages.broadcast_id`, письмо в очередь (FR-NT-09) и событие. Частичный уникальный индекс `(ticket_id, broadcast_id)` не даёт второй строки даже при двух одновременных задачах; конфликт пропускается. По окончании статус `done` и `delivered_count`. Причина: идемпотентность держит база, а не порядок задач.
19. **Сообщение рассылки в сроках и статусах.** Это публичный ответ сотрудника: останавливает срок первого ответа и снимает "клиент ждёт с" (FR-SLA-04), но не меняет исполнителя, очередь и статус. Помечено в переписке "Обновление по известной проблеме KP-n". Причина: клиент получил ответ по существу, а распределение работы не должна ломать массовая операция.
20. **Закрытие проблемы** (FR-KP-07). Закрытие требует итогового текста и идёт той же рассылкой вида `closing`: в каждом привязанном открытом обращении итоговое сообщение и переход в `resolved` по разрешённым переходам (`new` через `in_progress`, двумя событиями в одной транзакции) с итогом `fixed_in_version` и версией из задачи разработки, если она известна, иначе `solved`. Дальше обычный порядок: клиент подтверждает или возвращает в работу. Статус проблемы `closed` ставится в транзакции подтверждения закрытия, сигнатуры перестают быть активными сразу.
21. **Письмо и Telegram** (FR-NT-12, FR-NT-14). Отдельный шаблон письма `problem_update` (статус проблемы, текст, ссылка на обращение), вид уведомления в портале `problem_update`, короткое сообщение бота общим путём M4b. Каналы и настройки получателя те же, что у ответа по своему обращению. Причина: требование отдельного вида письма, без отдельной логики канала.
22. **Тез и известная проблема** (FR-KP-12, шаг 4 порядка 7.13). Если обращение привязано к активной публичной проблеме, `matchKnownProblem` возвращает её, помощник пишет сообщение `ai_payload` вида `known_problem` (номер проблемы и язык; название, статус и обходной путь рисуются при показе из `hdp_problems_public`), модель не вызывается, решения не ищутся. Затем передача с новой причиной `known_problem` в той же транзакции. Ответ проблемой останавливает срок первого ответа, как ответ решением. При P1 вслед за ответом передача с причиной `p1` (FR-AI-07: точное совпадение сигнатуры). Причина: обращение по массовой ошибке ведёт вторая линия рассылками, помощнику нечего добавить.
23. **Тез и объявление "сбой"** (FR-ANN-03, FR-AI-02). Если действует объявление вида `outage` с аудиторией "все", с сервером организации обращения или с модулем обращения, помощник пишет сообщение вида `outage` (ссылка на объявление, текст при показе из `hdp_announcement_translations`) и передаёт с причиной `outage`, модель не вызывается. Сообщение о сбое не останавливает срок первого ответа. Проверка сбоя идёт после известной проблемы и до поиска решений. Причина: во время сбоя решения из базы вводят в заблуждение, а сбой по модулю не подтверждает, что дело именно в нём.
24. **Объявления** (FR-ANN-01..04). Пишут `care` и `admin`: вид, период показа (начало и конец обязательны, не длиннее 90 суток), аудитория `all`, `server` (сервер Smartup) или `module`, текст на языке автора и принятые переводы (машинный перевод задачей `announcements.translate`, как у проблем). Клиент видит действующие объявления своей аудитории: `server` только клиенты организаций этого сервера; `module` на главной и странице `/announcements` всем клиентам с названием модуля, а над формой и в виджете только при выбранном или известном из контекста модуле. Закрытие баннера хранится в таблице `hdp_announcement_dismissals` (пользователь, объявление), а не в браузере: панель виджета живёт в `iframe` с разделённым хранилищем. Архив `/announcements`: закончившиеся за 90 суток. Причина: у портала нет данных о том, какими модулями пользуется клиент, а скрывать сбой модуля от всех хуже, чем показать лишний баннер на главной.
25. **Задача разработки у проблемы** (FR-KP-11, FR-DEV-06). Колонка `hdw_dev_task_links.known_problem_id`, в строке ровно одно из обращения, идеи, проблемы. Смена статуса задачи при синхронизации `DevTracker` даёт владельцу проблемы уведомление в портале и письмо `staff_problem_dev_task` ("обновите статус проблемы"); клиентам ничего не уходит, статус проблемы сам не меняется.
26. **Кандидат появляется после закрытия.** Задача `ai.candidates_sweep` раз в 15 минут находит обращения, закрытые за последние 7 суток, с итогом `solved` или `workaround`, без `solution_id` и без источника решения в `hdk_article_sources`, у организаций с включённой AI-обработкой, без строки `hda_runs` цели `candidate` с итогом `ok` или `invalid_response`, и ставит задание `ai.candidate` на каждое. Не больше 50 вызовов в сутки (настройка `candidates.daily_limit`), в общем месячном пределе расходов M5b. Модель `claude-haiku-5-5` (уровень `fast`): черновик всё равно проверяет человек. Выключатель `candidates.enabled`. Причина: обращение закрывает и задача по молчанию, событие закрытия есть не всегда, а обход идемпотентен по журналу вызовов.
27. **Черновик кандидата и его очистка** (FR-CAND-01, 07, 09). Вход и схема ответа те же, что у черновика решения (`assembleDraftData`, `draftSchema`). `confident: false`: кандидата нет, в журнал пишется решение `skipped`. Ссылки вне разрешённых доменов вырезаются до записи; телефоны, почта, команды и код остаются и подсвечиваются. Текст кандидата хранится только в `hda_solution_candidates`, видят его сотрудники.
28. **Склейка** (FR-CAND-02, 03, 05). Вектор заголовка и проблемы через `queryVector`. Сходство с опубликованным решением любой аудитории (`hdk_search_documents.embedding`) не ниже `candidates.published_similarity` (начально 0,88): кандидата нет, у решения растёт новая колонка `hdk_articles.staff_useful_count`. Иначе сходство с кандидатом в статусе `new` или `rejected` не ниже `candidates.merge_similarity` (начально 0,85): источник добавляется к лучшему, `source_count` и `org_count` пересчитываются, текст остаётся у первого. Отклонённый кандидат возвращается в `new`, когда `source_count - rejected_at_source_count >= 5`, с записью журнала аудита. Векторов нет (сервис недоступен): задание повторяется до трёх раз, затем кандидат создаётся без склейки, ночная задача `ai.candidates_embed` досчитывает векторы и склеивает. Решение о склейке принимает чистая функция `candidateMergeDecision` с модульными тестами (строка таблицы прослеживаемости ТЗ "Модульные тесты склейки"). Пороги начальные, подстройка на настоящих векторах заблокирована.
29. **Действия с кандидатом** (FR-CAND-04, 06, 09). "Сделать черновиком решения": новое решение-черновик модуля `hdk` с аудиторией `internal` (сотрудник сам меняет на `clients` перед публикацией), текстом кандидата в шаблоне, всеми обращениями-источниками в `hdk_article_sources` и признаком `hdk_articles.is_untrusted`; кандидат `accepted`. "Объединить с решением": кандидат `merged`, источники добавляются к решению, `staff_useful_count` растёт на число источников. "Отклонить" с причиной из списка (`duplicate`, `too_specific`, `not_a_solution`, `wrong_data`, `other`) и комментарием, `rejected_at_source_count = source_count`. Делают роли с правом черновика решения (`app.kb_can_write()`), каждое действие с записью журнала аудита. Причина: публикация остаётся обычным порядком FR-SOL-04, 05.
30. **Отдельное подтверждение недоверенного текста** (FR-CAND-09, T33). У решения с `is_untrusted` находки "телефон", "почта", "команда", "код" при публикации блокируют кнопку, пока сотрудник не отметит каждую "Проверено"; отметки хранятся в версии (`hdk_article_versions.untrusted_confirmed`, список отпечатков находок), смена текста их сбрасывает. Команды и код находит новая проверка `findCommands` в `checks.ts` (строки с `sudo`, `rm`, `curl`, `wget`, `powershell`, `cmd`, SQL `drop`, `delete`, `update ... set`, `truncate`, обратные кавычки и блоки кода). Экран проверки показывает исходные обращения рядом с черновиком (`solutionSourceThreads`, поправка 101).

## На что смотреть при проверке

1. Клиент видит лишнее о проблеме: внутреннее название, владельца, счётчики, организации, сигнатуры, задачу разработки, проблему без признака показа или закрытую. Проверяется запросом напрямую в базу под ролью `hub_app` к таблицам и представлению.
2. Текст одного клиента попадает к другому: создание проблемы из обращения переносит тему в публичное поле; рассылка содержит название организации или ИНН; сообщение рассылки собрано не только из текста рассылки; машинный перевод ушёл клиенту без принятия сотрудником.
3. Рассылка дублируется или теряется: повтор задачи, две задачи одновременно, сбой на середине, обращение привязано после подтверждения, обращение закрыто во время рассылки. После любого повтора у каждого получателя ровно одно сообщение и одно письмо.
4. Закрытие проблемы ломает статусы: переход вне таблицы 7.2, `new` без `in_progress`, объединённое или уже закрытое обращение, обращение без записи журнала аудита.
5. Привязка: обращение в двух проблемах; автопривязка к исправленной или закрытой проблеме; служебная организация "Неопознанных"; клиент сам задаёт `known_problem_id`; сбой привязки отменяет создание обращения.
6. Тез: при известной проблеме вызывается модель или ищутся решения; клиент получает слово модели; P1 с проблемой не уходит дежурным; объявление "сбой" другого сервера или модуля меняет ответ.
7. Кандидаты: кандидат находится подсказкой, помощником или поиском клиента до публикации; кандидат из организации с выключенной AI-обработкой; в модель ушло лишнее (заметка, вложение, имя, название организации); ссылка вне разрешённых доменов осталась; решение из кандидата опубликовано без отметки находок.
8. Права: первая линия создаёт или закрывает проблему, `product` что-то меняет, клиент читает `hda_solution_candidates`, `hda_candidate_sources`, `hdp_broadcasts`, чужие закрытия баннеров.
