# Веха M6 "Виджет": план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** пользователь Smartup Web, у которого случилась ошибка, нажимает "Сообщить", видит подходящее решение и, если оно не помогло, отправляет обращение с уже приложенным контекстом, не вводя логин и пароль; там же видит свои обращения. Мобильное приложение открывает ту же форму во встроенном браузере. Портал нельзя встроить ни на какой сайт, кроме адресов серверов Smartup из реестра.

**Архитектура:** загрузчик `hub-widget.js` без зависимостей рисует кнопку и `iframe` с домена портала и передаёт в него токен контекста и подсказки через `postMessage` со строгой проверкой источника. Страница в `iframe` обменивает токен контекста на токен виджета (`POST /api/embed/session`) и держит его только в памяти; кук у страниц виджета нет. Каждый запрос виджета несёт токен в заголовке `Authorization`, по нему сервер строит актора клиента и проверяет членство в базе. Форма, подсказка, загрузка файлов и список обращений используют общие модули `hdt`, `hdk`, `hdu`; своей логики сроков, прав и ответов у виджета нет.

**Стек:** как в вехах M3-M5. Новое: пакет `jose` прямой зависимостью (решение 3, нужно согласие), скрипт сборки загрузчика на Node.js без сборщика.

**Источник:** `docs/TZ.md` версии 1.2: сценарий S1, разделы 7.6 (FR-WG-01..10), FR-ID-03, FR-SOL-15, FR-MET-03, FR-MET-10, экран "Панель виджета внутри Smartup" (8.3), 8.9, UX-S-09, UX-C-02, 03, 09, 16, 11.4, 11.5, 11.9, 12.1, 12.2, 13.4, 13.5 (`EMBED_TOKEN_SECRET`), 14.2 (T8, T9), 14.3, 14.4, 14.5, 15.2 (строка "Токен виджета пользователя А с номером обращения Б"), 15.3 (сценарий 6), строка M6 раздела 16.2, раздел 17 (задачи 4-8, 15), вопросы 17, 43, 44 раздела 20. Решения 0010, 0013, 0021, 0054, 0055.

## Предусловия

- Веха M5 слита в `main` (готова на ветке, ждёт слияния). Ветка M6 заводится от `main` после слияния M5.
- Разработчики Smartup **не выпускают** токен контекста и не подключили скрипт (раздел 17, задачи 4-8, 15; вопрос 2 в `docs/HANDOFF.md`: письма не отправлены). Веха идёт на ложном выпуске токена и демонстрационной странице, настоящий выпуск нужен к приёмке (строка M6 в `docs/plans/README.md`).
- Ответы на вопросы 17 (способ подписи), 43 (что такое `company_id`) и 44 (коды модулей) не получены. Решения 2, 5 и 10 построены так, чтобы любой ответ менял настройку, а не код.

## Общие ограничения

- Правила `CLAUDE.md`: сначала тест; `pnpm check`, `pnpm test`, `pnpm test:integration` перед каждым коммитом; каждая новая таблица с RLS и строкой в наборе изоляции; запись в журнал аудита в той же транзакции; тексты только в `messages/*.json` на трёх языках, в том числе тексты загрузчика; значения оформления только из токенов; Zod на каждой точке входа; база только через `withActor` (и `withIdentity` для учётной записи).
- Организация и пользователь виджета берутся только из проверенного токена контекста, а затем из проверенного токена виджета. Подсказки (модуль, экран, ошибка, версия) не подписаны и влияют только на предзаполнение, поиск и поля контекста обращения, никогда на права.
- Страницы виджета не читают сессию портала и не ставят кук. Токен виджета не пишется в `localStorage`, `sessionStorage` и куки.
- Ни одно сообщение `postMessage` не уходит на адрес `*` и не принимается без проверки `event.origin` и `event.source`.
- Виджет показывает только то, что видит клиент в портале: те же проекции и политики RLS. Внутренние заметки, сотрудники, сигнатуры, теги и внутренние решения ему недоступны.
- Данные клиентов не кешируются. Кешируются только открытые ключи серверов Smartup и список адресов встраивания (это настройки реестра, не данные клиентов, решение 6).
- Секрет подписи токена сервера (упрощённый вариант 11.4) хранится зашифрованным, колонка закрыта правами от `hub_app`, как секрет OAuth (решение 0014).

## Решения вехи, которых нет в ТЗ (нужно подтверждение)

1. **Сессия виджета без кук.** Токен виджета (15 минут) живёт только в памяти страницы `iframe`, как требует 11.4. Куки с атрибутом `Partitioned` отклонены: Safari их до сих пор ограничивает, а куки сессии портала под чужим сайтом создали бы вторую поверхность для CSRF. Storage Access API отклонён: требует нажатия и прежнего посещения портала в той же вкладке верхнего уровня. Цена: перезагрузка `iframe` теряет сессию, страница сразу просит у хозяина новый токен контекста, пользователь ничего не видит.
2. **Два режима подписи на сервер реестра.** `jwks`: ES256, EdDSA или RS256, ключи только по адресу `context_jwks_url`, введённому администратором. `secret`: HS256 общим секретом, который портал создаёт и показывает администратору один раз. Режим задаёт допустимые алгоритмы: токен с HS256 у сервера в режиме `jwks` и любой токен с `none` отклоняются (подмена алгоритма). Рекомендация разработчикам Smartup: `jwks` (вопрос 17).
3. **Пакет `jose` прямой зависимостью.** Он уже стоит в дереве через `better-auth` (6.2.17, MIT). Используются только `jwtVerify`, `createLocalJWKSet`, `SignJWT`; `createRemoteJWKSet` запрещён правилом линтера, потому что ходит в сеть мимо `outbound.ts`. Ключи скачивает `outbound.ts`. Своя проверка подписи на `node:crypto` отклонена: в ней легко ошибиться. Цена отказа: та же работа своими руками и отдельная проверка безопасности.
4. **Проверки токена контекста** по 11.4: `iss` совпадает с `context_issuer` сервера (уникален в реестре, по умолчанию равен `issuer` OAuth), `aud = smartup-hub`, `exp - iat` не больше 300 секунд, `iat` не в будущем дальше 60 секунд, допуск часов 60 секунд, `jti` одноразовый на пару "сервер + jti" (таблица `hdu_context_token_uses`, строки старше `exp + 60 с` удаляет ночная очистка), `platform` из `web`, `android`, `ios`, `sub` и `company_id` непустые. Сервер `disabled` отклоняется. Любой отказ даёт один ответ `401 invalid_context` без причины, причина пишется в журнал работы.
5. **Кто такой пользователь виджета.** Учётная запись находится по паре "сервер + `sub`", тем же путём, что вход OAuth (раздел 17: `sub` один и тот же). Организация по паре "сервер + `company_id`" через `provisionFromSmartup`, то есть токен сервера A никогда не даёт организацию сервера B. Отключённый участник и отключённая организация получают `403`. Если ответ на вопрос 43 покажет, что `company_id` это организация из переключателя, меняется только сопоставление в `provisionFromSmartup`, общее для OAuth и виджета.
6. **Адреса встраивания по ключу сервера, а не списком всех серверов.** 14.4 ставит в `frame-ancestors` адреса всех активных серверов, но такой заголовок раскрыл бы каждому, кто является клиентом выделенного сервера (FR-ID-03). Поэтому адрес страницы виджета содержит `embed_key` сервера (128 случайных бит, не секрет, его видит администратор и передаёт разработчикам Smartup), а политика перечисляет только адреса этого сервера: начало `base_url` и до пяти дополнительных адресов `embed_origins` (только https; http только при портале на localhost, как в решении 0015). Неизвестный или отключённый ключ даёт `frame-ancestors 'none'`. Прокси берёт список из памяти процесса, которая обновляется из базы раз в 60 секунд и сразу после правки реестра в этом процессе. Цена: отключённый сервер может встраивать портал ещё до 60 секунд; токены его при этом уже не принимаются.
7. **Адреса страниц с языком:** `/{locale}/embed/report`, `/{locale}/embed/tickets`, `/{locale}/embed/tickets/{number}`, `/{locale}/m/report` вместо `/embed/report` и `/m/report` из 12.1. Прокси и так перенаправляет адрес без языка, а тексты берутся из того же `next-intl`. Язык выбирает загрузчик из `init({ locale })`.
8. **Протокол `postMessage` версии 1.** Каждое сообщение `{ hub: 1, type, ... }`, схема Zod с обеих сторон, неизвестный тип молча отбрасывается. Хозяин в `iframe`: `init` (токен, подсказки, тема, язык), `token`, `hints`. `iframe` хозяину: `ready`, `need-token`, `close`, `ticket-created` (только номер). Загрузчик принимает сообщение, только если `event.origin` равен адресу портала и `event.source` это его `iframe`. Страница принимает, только если `event.source === window.parent` и `event.origin` входит в адреса встраивания сервера; отправляет на точный адрес хозяина, проверенный по тому же списку (`location.ancestorOrigins`, где он есть, иначе адрес из параметра загрузчика, сверенный со списком).
9. **Загрузчик собирается скриптом без сборщика.** Исходник `src/widget/loader.js` (проверка типов `checkJs`), команда `pnpm widget:build` подставляет тексты из `messages/*.json` (пространство `widget.loader`) и значения цветов из токенов и пишет `public/widget/v1/hub-widget.js`; `pnpm check` падает, если файл устарел. Кнопка и уведомление рисуются в закрытом Shadow DOM, стили хозяина не задевают. Бюджет 15 КБ в сжатом виде проверяет модульный тест. Кеш файла 5 минут (данных клиентов в нём нет), несовместимые изменения выходят как `v2`.
10. **Модуль не входит в сигнатуру и в виджете.** 11.5 считает сигнатуру из кода, текста и модуля, но решение 0055 убрало модуль на портале. Если виджет добавит модуль, одна и та же ошибка из портала и из виджета даст разные сигнатуры и точное совпадение пропадёт. Код модуля из подсказки пишется в `context.moduleCode`, выбирает модуль обращения, если код есть в справочнике, и даёт подсказке множитель 1.1. Цена: одинаковый текст ошибки в разных модулях даёт одну сигнатуру; пересматривается после ответа на вопрос 44 и корпуса ошибок.
11. **Подсказки ограничены.** `module`, `form` до 64 знаков `[A-Za-z0-9_.:-]`, `appVersion` до 32, `errorCode` до 64, `errorText` до 2000, тема `light` или `dark`. Текст проходит `cleanUserText`, на экранах выводится только текстом, никогда как HTML или ссылка. Неверная подсказка отбрасывается, форма работает без неё.
12. **Источник обращения.** Из виджета `widget_web`, из `/m/report` `widget_mobile`, по `platform` проверенного токена. Режим B (новая вкладка портала) ставит `widget_web`, если форма открыта с признаком виджета: это влияет только на показатели. Подсказки режима B передаются после `#`, чтобы текст ошибки не попал в журнал Caddy.
13. **"Мои обращения" в виджете:** список обращений пользователя в этой организации, страница обращения с перепиской, ответом, вложениями и подтверждением решения. Остальное (подписки, видимость, оценка с причиной) по ссылке "Открыть в портале" в новой вкладке с обычным входом. Цена: часть действий требует входа в портал.
14. **Пределы.** Обмен токена 30 в минуту на пользователя (14.5) и 120 в минуту на адрес до проверки подписи; неудачные обмены 20 в 10 минут на адрес. Подсказка, создание обращения, ответы и загрузки: те же правила и счётчики, что в портале, по пользователю. Отдельных пределов для виджета нет.
15. **Журнал аудита.** Новая сессия виджета (обмен без действующего токена виджета) пишется событием `client.embed_session` с сервером и платформой, как вход клиента. Продление по таймеру пишется только в журнал работы: иначе журнал аудита получал бы запись каждые 15 минут на пользователя. Правка настроек токена и адресов встраивания пишется в журнал аудита как остальные правки реестра.
16. **Токен виджета:** HS256 на `EMBED_TOKEN_SECRET`, `aud = hub-embed`, поля пользователь, организация, сервер, платформа, `jti`, срок 15 минут. Состояния в базе нет, но каждый запрос заново проверяет членство, состояние организации и сервера, так что отключение действует сразу. Сотрудник токен виджета получить не может: актор всегда `client`.
17. **Ложный выпуск токена.** `scripts/mock-oidc.mjs` получает у серверов `mock` (режим `jwks`, ES256, ключи на `/context-jwks.json`) и `mock-dedicated` (режим `secret`) адрес `POST /context-token?persona=`. Демонстрационная страница `scripts/mock-smartup-host.mjs` на `http://127.0.0.1:3192` (другой сайт, чем `localhost:3000`) имитирует Smartup Web: меню "Помощь", кнопка "Вызвать ошибку", переключатель темы и языка, режим без `getContextToken`. В образ оба не входят (решение 0013).

## На что смотреть при проверке

1. Встраивание чужим сайтом: любая страница портала, кроме `/embed/*` с ключом сервера, отдаёт `frame-ancestors 'none'`; статический заголовок `next.config.ts` не противоречит политике прокси (два заголовка CSP применяются оба); `/m/report` и `/api/embed/*` не встраиваются; адреса других серверов в заголовке не видны.
2. Подделка и повтор токена контекста: чужая подпись, `alg: none`, HS256 у сервера `jwks` с открытым ключом как секретом, просроченный, слишком долгий, будущий `iat`, другой `aud`, повторный `jti`, `iss` отключённого сервера, `kid`, которого нет у сервера, адрес ключей из самого токена.
3. Путаница серверов: токен сервера A с `company_id` организации сервера B даёт организацию сервера A или отказ, но не B; одинаковый `sub` на двух серверах это два разных человека.
4. Утечка между организациями: токен виджета пользователя А с номером обращения Б даёт "Не найдено"; подсказка не находит текста обращений; подсказки из `postMessage` не меняют организацию и права.
5. Подмена `postMessage`: сообщение с чужого адреса или из другого окна игнорируется в обе стороны; токен не уходит на адрес `*` и на адрес вне списка.
6. Куки: ответы страниц и API виджета не ставят ни одной куки, прокси не продлевает сессию портала на `/embed`, сессия портала в виджете не используется даже при её наличии.
7. XSS через контекст: `errorText` с HTML и `javascript:` на странице виджета, в карточке сотрудника и в письме выводится текстом.
8. Виджет не показывает данных только для сотрудников: внутренние заметки, имена сотрудников сверх клиентской проекции, сигнатуры, теги, внутренние решения.
9. Токен в адресе: `#ctx=` убирается из адресной строки сразу, не попадает в журнал сервера, `Referer` и историю.
