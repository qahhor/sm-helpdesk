# Веха M8c "Знания из кода": план реализации

Статус: подтверждён общим распоряжением владельца от 26.11.2026 (выполнять вехи по порядку без остановки); выполнен 27.11.2026, отчёт `M8c-report.md`

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** Hermes Agent раз в неделю сканирует репозитории Smartup на своей стороне и передаёт порталу отчёт установленного вида: карту модулей и экранов и каталог ошибок. Портал хранит только выводы, не код: отчёт с фрагментом длиннее 10 строк или с регулярным выражением отклоняется целиком. Записи приходят черновиками в очередь "Знания из кода", вторая линия утверждает, правит или отклоняет; новые и изменившиеся выделены. Утверждённый шаблон сообщения даёт точную сигнатуру: текст ошибки обращения совпал с шаблоном, сигнатурой становится ключ записи. В обращении сотрудник видит блок "Что известно по коду", одним нажатием создаёт черновик решения из записи и нажимает "Разобрать по коду": агент получает событие, пишет внутреннюю заметку с гипотезой, помеченную "AI-сотрудник, не проверено". Клиент, AI-помощник и подсказка знаний из кода не видят.

**Архитектура:** знания из кода живут в модуле `hda` (таблица модулей 10.3, `docs/naming.md`), код в `src/modules/hda/code/`, снаружи только `src/modules/hda/api/code-*.ts`. Отчёт приходит инструментом сервера MCP `code_catalog_upsert` (имя из экрана 8.12) по токену AI-сотрудника: новая точка входа и новая сетевая зависимость не нужны, сторона Hermes и доступ к репозиториям в тестах заменены отчётом-примером. Шаблон превращается в выражение для сопоставления только в базе: генерируемая колонка `pattern` строится функцией `app.hda_code_pattern(text)` из текста с именованными подстановками; агент выражения не передаёт и не может передать. Сигнатуру по шаблону отдаёт функция `app.hda_code_signature(code, lines)` с правами владельца: она возвращает только сигнатуру утверждённой записи, поэтому система, AI-помощник и подсказка не получают прав чтения таблиц знаний вовсе. Анализ по кнопке идёт событием `code_analysis_requested` через очередь событий M8b с токеном запуска на одно обращение; ответ агент пишет инструментом `submit_code_analysis`, портал собирает из полей внутреннюю заметку.

**Стек:** как в вехах M8 и M8b. Новых зависимостей и внешних сервисов нет. Claude портал в этой вехе не вызывает.

**Источник:** `docs/TZ.md` версии 1.2: 7.22 (FR-CODE-01..15, вид отчёта о сканировании), 7.21 (FR-AGT-04 "записи каталога ошибок", FR-AGT-08 "запрошен анализ по коду", FR-AGT-12, задания "Сканирование кода" и "Анализ обращения по коду"), 5.2 (таблица прав, строка "Знания из кода"), 6 (сценарий S11), 8.12 (экраны "Знания из кода", перечень инструментов токена с `code_catalog_upsert`), 10.3 (модуль `hda`), 10.4 (актор `agent`, "записи каталога ошибок"), 10.5 (таблицы `code_scans`, `code_error_entries`, `code_error_templates`, `code_module_notes`, `code_analysis_requests`), 11.5 (сигнатура), FR-SOL-04 (внутренние имена), FR-ADM-15, FR-MET-11, 14.3 ("Исходный код обрабатывается на стороне Hermes Agent"), 15.2 (строка "Клиент запрашивает знания из кода или заметку AI-сотрудника"), 15.3 (сценарий 20), строка M8c раздела 16.2, 17.1 (задания 5, 6, 7 для команды AI-агентов).

## Общие ограничения

- Правила `CLAUDE.md`: сначала тест; `pnpm check`, `pnpm test`, `pnpm test:integration` перед каждым коммитом; каждая новая таблица и представление с FORCE RLS и строкой в `tests/integration/isolation/tables.ts`; каждое изменение статуса и прав (утверждение, правка, отклонение записи и заметки о модуле, запрос анализа) с записью в журнал аудита в той же транзакции; тексты интерфейса только в `messages/*.json` на ru, uz, en по правилам голоса 8.13; значения оформления только из токенов; Zod на каждой точке входа и на входе каждого инструмента; база только через `withActor`; организация и пользователь только из актора.
- **Портал не хранит исходный код Smartup** (CLAUDE.md, 7.22 правило 1, FR-CODE-12): ни одно поле отчёта и заметки анализа не длиннее 10 строк, место в коде только ссылкой (объект, файл, строка). Отклонённый отчёт не сохраняется: в истории только строка с причинами кодами и путями полей.
- **Регулярных выражений от агента портал не принимает** (FR-CODE-05): в отчёте нет поля выражения (строгая схема), шаблон с синтаксисом выражений отклоняется, выражение строит база из текста шаблона.
- **Клиентская часть не видит знаний из кода** (CLAUDE.md, FR-CODE-11, 15.2): у клиента нет ни одной политики на новых таблицах, страниц и полей для клиента нет. Системный актор (AI-помощник, подсказка, Тез, правила) тоже не читает таблиц знаний: только функцию сигнатуры, которая возвращает 32 знака хеша.
- **Инструменты сервера MCP не показывают ничего клиенту и не меняют состояния обращения** (CLAUDE.md, FR-AGT-05): `code_catalog_upsert` пишет только каталог, `search_code_catalog` только читает, `submit_code_analysis` пишет внутреннюю заметку и отметку запроса.
- **Клиент видит только опубликованные шаги**: решение из записи создаётся черновиком `internal`, публикует сотрудник обычным порядком FR-SOL-04, 05.
- Внешний сервис только за интерфейсом с реализацией и заглушкой: приёмник событий Hermes (`AgentEventSender` M8b), чат команды (`staffBotSender` M8b). Локально и в тестах всё работает без сети.
- Ни кеширования (`use cache`, `unstable_cache`), ни хранения шаблонов в памяти процесса: сопоставление каждый раз в базе.
- Применённые миграции 0001-0117 не правятся. Политики RLS и тесты изоляции не ослабляются.

## Решения, принятые по рекомендации

1. **Имена объектов.** `code_scans` → `hda_code_scans`, `code_error_entries` → `hda_code_error_entries`, `code_error_templates` → `hda_code_error_templates`, `code_module_notes` → `hda_code_module_notes`, `code_analysis_requests` → `hda_code_analysis_requests`; представление первой линии `hda_code_checks`; функции `app.hda_code_reader()`, `app.hda_code_pattern(text)`, `app.hda_code_signature(text, text[])`. Колонки по `docs/naming.md`: `scan_key` (поле `scanId` отчёта), `commit_ref` (`commit`), `received_on`, `finished_on` (в 10.5 `finished_at`), у запроса анализа первой колонкой `org_id` (данные клиента). Причина: префикс модуля, как в M5c и M8b.
2. **Где живёт код.** `src/modules/hda/code/{report,rules,scan,catalog,analysis,note}.ts` (чистые функции и операции), `src/modules/hda/api/{code-knowledge,code-analysis,code-match}.ts` (точки входа), инструменты `src/modules/hda/agent/tools/code.ts`. Модуль `hdk` берёт сопоставление через `@/modules/hda/api/code-match`, модуль `hdw` запрос анализа через `@/modules/hda/api/code-analysis`. Причина: таблица модулей 10.3 ("знания из кода" в `hda`), граница модулей линтера.
3. **Отчёт приходит инструментом `code_catalog_upsert` сервера MCP.** Токен с этим инструментом в перечне получает предел тела запроса 2 МБ, остальные прежние 64 КБ (M8b, решение 4). Вход сервера проверяет токен по заголовкам до чтения тела, поэтому большой запрос без токена не читается. Отчёт принимается одним вызовом целиком или не принимается совсем. Журнал вызовов, журнал аудита `agent.tool_called`, пределы и отзыв токена работают как у остальных инструментов записи. Причина: точка входа и проверки M8b уже есть; отдельный приёмник повторил бы вход, журнал и пределы; без новой сетевой зависимости (CLAUDE.md).
4. **Схема отчёта.** Строгая схема Zod по примеру 7.22: `scanId` (до 40 знаков), `repository` (до 80, `[a-z0-9._-]`), `commit` (7-64 знака шестнадцатеричных), `modules` (до 500: `code`, `name` по языкам, `summary`, `dependsOn`, `screens` с кодом и названием), `errors` (до 2000: `key` вида `orders.insufficient_stock`, `code` до 40, `messageTemplates` по языкам `ru`, `uz`, `en`, `kk`, `tr`, `module`, `raisedIn` до 10 ссылок `{ object, path, line }` с относительным путём без `..`, `conditions`, `userCause` до 2000 знаков, `whatToCheck` до 10 пунктов по 300, `kind`, `confidence` от 0 до 1), `changes` (`added`, `changed`, `removed`). Лишнее поле (например `pattern` или `regex`) делает вызов неверным (`invalid_arguments`, ничего не сохраняется).
5. **Что считается кодом и регулярным выражением** (FR-CODE-05, 12). Правила проверяет портал после схемы, отчёт отклоняется целиком: поле текста больше 10 строк (`code_too_long`), шаблон с синтаксисом выражений (`regex`: обратная косая черта, `.*`, `.+`, `.?`, `(?`, классы `[...]`, повторители `{n,m}`, якоря `^` и `$`, чередование `|`), фигурные скобки вне подстановок, имя подстановки не по правилу или больше 10 подстановок (`bad_placeholder`), меньше 8 букв вне подстановок (`template_too_loose`). Отклонённый отчёт оставляет строку `hda_code_scans` со статусом `rejected` и причинами (код правила и путь поля, без значений), ответ инструмента `{ status: "rejected", reasons }`.
6. **Выражение строит база.** Генерируемая колонка `pattern = app.hda_code_pattern(template)`: подстановки `{name}` → `(.{1,200}?)`, остальной текст экранируется, пробелы → `\s+`, выражение привязано к началу и концу строки и допускает точку или восклицательный знак в конце; сравнение без учёта регистра (`~*`). Функция неизменяемая, правки шаблона сотрудником перестраивают выражение. Агент выражения не передаёт, колонку записать нельзя.
7. **Сигнатура из ключа.** Генерируемая колонка `hda_code_error_entries.signature`: первые 32 знака sha256 от `code-key|<ключ>`. Сигнатура записи совпадает по виду со всеми таблицами сигнатур (`hdk_error_signatures_c1`, `hdp_problem_signatures_c1`, `hda_signature_spikes_c1`), поэтому решения, известные проблемы, всплески и правила работают с ней без изменений, а сигнатура не меняется от правки текста шаблона. Правка к ТЗ (FR-CODE-04 "сигнатурой становится ключ записи") в `docs/TZ-1.2-changes.md`.
8. **Сопоставление.** Функция `app.hda_code_signature(code, lines)` (`SECURITY DEFINER`) берёт утверждённые записи, у которых код пуст или совпадает с кодом строки ошибки, и шаблоны, совпавшие с одной из строк; первая по порядку строк, затем по длине шаблона. Строки: текст строки ошибки (11.5, `findErrorLine`), затем до 30 непустых строк описания по 500 знаков. Нет совпадения: прежний способ 11.5. Общая функция `resolveErrorSignature` модуля `hdk` используется во всех местах, где считается сигнатура: запись сигнатуры обращения во всех каналах и починка, подсказка на портале и в виджете, баннер известной проблемы, привязка сигнатуры к решению сотрудником. Причина: подсказка, обращение и решение должны давать одну сигнатуру.
9. **Кто что видит** (FR-CODE-11, 5.2). Читают `agent_l2`, `care`, `admin` (функция `app.hda_code_reader()`); первая линия только представление `hda_code_checks` (ключ, сигнатура, модуль, "что проверить" утверждённых записей); `product`, клиент, система: ничего. Утверждают, правят и отклоняют записи `agent_l2`, `care`, `admin`; заметки о модулях утверждает только `admin` (FR-CODE-13). AI-сотрудник читает каталог (основной токен и токен запуска анализа) и пишет сканирования, записи, шаблоны и заметки о модулях только основным токеном; утвердить запись или задать утвердившего агент не может (триггер базы).
10. **Изменения между сканированиями.** Портал сам сравнивает отпечаток содержимого записи от агента (`scan_digest`: шаблоны, код, модуль, место, условия, причина, что проверить, род, уверенность) с прошлым: новая запись: черновик `change_kind = 'new'`; изменилась: поля агента перезаписываются, статус снова `draft` (даже у утверждённой и отклонённой), `change_kind = 'changed'`; не изменилась: статус и правки сотрудника сохраняются, `change_kind = 'same'`; нет в отчёте того же репозитория: `removed`; вернулась после `removed`: черновик `new`. Поле `changes` отчёта проверяется схемой, но числа истории считает портал. Выделение "новое" и "изменено" в очереди по `change_kind` последнего сканирования. Цена: изменённая утверждённая запись не даёт точной сигнатуры до повторного утверждения.
11. **Повтор отчёта.** Принятый отчёт того же репозитория с тем же `scanId` повторно ничего не меняет и возвращает прежний итог (уникальный индекс).
12. **Род и уверенность.** `kind`: `user_error`, `setting`, `data`, `probable_defect` (FR-CODE-02 "ошибка пользователя, настройка, данные, вероятный дефект"); `confidence` число от 0 до 1 с двумя знаками.
13. **Модуль записи.** Код модуля отчёта ищется в справочнике `hdr_product_modules`; неизвестный модуль: `module_id` пуст, код хранится в `module_code`.
14. **Заметки о модулях** (FR-CODE-13). Строки `hda_code_module_notes` по коду модуля с теми же правилами изменений; на странице видно отличие от справочника ("нового модуля нет в справочнике", "экраны отличаются"). "Утвердить" администратором применяет предложение к справочнику: новый модуль с названием из отчёта или новый список экранов у существующего (название существующего не меняется), журнал аудита той же транзакцией; "Отклонить" только меняет статус.
15. **Сводка о сканировании** (FR-CODE-14). Строка `hda_code_scans` хранит дату, репозиторий, версию кода, числа новых, изменённых и исчезнувших ошибок. ## На что смотреть при проверке

1. Код в портале: поле отчёта или заметки больше 10 строк сохраняется; отклонённый отчёт оставляет содержимое; место в коде с текстом кода; шаблон с выражением или поле `pattern` от агента принимаются; колонку `pattern` можно записать.
2. Клиент видит знание из кода: любая из новых таблиц, представление, заметка анализа, текст записи в черновике решения до публикации, ссылка в портале или виджете; клиент получает "не найдено" не во всех местах.
3. Знания у системы и AI: системный актор, помощник, подсказка или Тез читают записи, условия или "что проверить"; функция сигнатуры отдаёт что-то кроме сигнатуры утверждённой записи.
4. Сигнатура: черновик, отклонённая или исчезнувшая запись определяет сигнатуру; подсказка, обращение и решение дают разные сигнатуры для одного текста; совпадение с чужим кодом ошибки.
5. Права: первая линия видит что-то кроме "что проверить" утверждённых; `product` видит знания; агент утверждает запись; не администратор утверждает заметку о модуле; утверждение без журнала аудита или в другой транзакции.
6. Анализ: инструмент меняет статус, исполнителя, сроки обращения или пишет клиенту; токен запуска пишет вторую заметку или читает другое обращение; событие для организации без AI-обработки; тело события с текстом; запрос без ответа не истекает.
7. Решение из записи: в черновик попадают ключ, объекты, пути, таблицы; черновик виден подсказке до публикации.
