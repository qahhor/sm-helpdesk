## Проверка ветки

Две проверки. Первая: исполнитель приёмки по разделу "На что смотреть при проверке" плана и по решениям 0066-0069. Вторая: независимый проверяющий с отдельным контекстом на всей ветке подготовки, с планом и решениями журнала. Найдено одно важное и шесть мелких замечаний; каждое исправление кода сначала тестом, который падал.

- **важное, I1: "Войти заново" через Smartup не требовал нового входа.** Страница входа делала обычный вход через Smartup, и браузер, где открыта сессия Smartup Web, получал свежую сессию портала без пароля. Теперь вход заново шлёт серверу `prompt=login` и `max_age=0` и ставит куку с временем начала; на возврате `id_token` с `auth_time` раньше начала отклоняется (`tests/integration/sso-reauth.test.ts`, ложный сервер выполняет требование или нет). В договоре со Smartup поля `auth_time` нет: без него вход проходит с событием `auth.reauth_unverified`. Обычный вход через Smartup без "Войти заново" тоже даёт свежую сессию, поэтому V7.5.1 и V7.5.2 для входа через Smartup снова "частично"; вопрос разработчикам Smartup в `docs/questions.md`, инструкции клиента больше не обещают, что "никто другой" не завершит сессии (решение 0067, пункт 11).
- **повтор черновика решения (первая проверка):** `hub seed:pilot` искал черновик в списке решений, ограниченном 200 строками; при большем числе решений повтор создавал вторую копию. Теперь поиск по языку оригинала и названию.
- M1: при двух куках темы побеждала первая; теперь важнее `__Host-hub_theme`, как у языка, а выбор темы стирает прежнюю куку (`tests/unit/pref-cookies.test.ts`).
- M2: `seed:pilot` сравнивал обрезанный текст, а модули хранят текст после очистки от невидимых знаков; файл с таким знаком писался заново при каждом запуске. Схема очищает так же; тест повтора охватывает и календарь.
- M3: сообщение и справка команды больше не обещают "ничего не изменено" при отказе модуля посреди записи.
- M4: памятка инцидента: после аварийного перезапуска базы `pg_stat_archiver` обнуляется, и `backup_stale` по `wal` может прийти ложно до следующего сегмента.
- M5: отметка "только разработка" в `.env.example` действовала до пустой строки и могла снять проверку с соседних переменных; теперь только на следующую.
- M6: файлы профиля и шага первого входа возвращены к одинарным кавычкам репозитория (перевёрстка без изменения поведения).

По пунктам раздела "На что смотреть":
1. Доказательства ASVS: тест проверяет каждый путь; строки 7.3.2, 7.5.1, 7.5.2 ссылаются на тесты именно этих требований.
2. Полнота CSP: проверка `csp-pages` в `pnpm check` зелёная, новых страниц подготовка не добавила.
3. Сигналы: `backup_stale` без архива проверяет только ночную копию (тест `ops-watch-backup`); остановка фонового процесса видна снаружи (сухой прогон).
4. Замер шёл под `hub_app` с актором из сессии (решение 0068).
5. Восстановление: тест сверяет владельцев функций, `FORCE` RLS и пустую выдачу без актора; памятка проверяет владельца функций идей.
6. Начальные данные: ноль изменений и ноль записей аудита при повторе, файл с организациями отклоняется целиком, решения черновиками (тесты `seed-pilot`).
7. Инструкции: названия сверяет проверка `guides`, обещаний нет, AI первой линии и функции этапа 2 не описаны.

## Не проверено

- Ничего из того, что требует сервера: TLS, Cloudflare, R2, Resend, Telegram, ClamAV, TEI, сборка и запуск образа Docker, внешняя проверка доступности.
- Шаги инструкций руками в портале: названия кнопок сверены проверкой, ход шагов проверен сценариями браузера, а не человеком.
- Проверка удобства на людях: протокол готов, пробный прогон только сценариями браузера.
- Узбекские инструкции: нужен носитель языка.
- В сухом прогоне администратор для `seed:pilot` заведён строкой в базе, а не по ссылке со вторым фактором.

## Отложено

- Поиск сотрудника по тексту на миллионе обращений с частым словом около 60 мс (решение 0068, пункт 3).
- Похожие идеи на тысячах идей отвечают около 470 мс (решение 0068, пункт 2).
- Шаг памятки, как администратор проверяет личность сотрудника перед сбросом второго фактора (ASVS 6.4.4).
- Страница 404 в тёмной теме светлая (решение 0066, пункт 3).
