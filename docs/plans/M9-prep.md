# Подготовка к M9 "Готовность к пилоту": план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** до появления сервера, юридических текстов и пилотных клиентов сделать всё из вехи M9, что можно сделать и проверить в среде разработки: чек-лист ASVS уровня 2 с доказательством по каждому требованию и исправленными пробелами в коде, проверку политики содержимого на всех страницах, наблюдение без внешних сервисов, замер на миллионе обращений, повторную репетицию восстановления, команду начальных данных, инструкции сотрудника и клиента на трёх языках, сквозную памятку запуска и протокол проверки удобства. После этого M9 сводится к работе на сервере и с людьми.

**Архитектура:** новых модулей нет. Наблюдение дополняет задачу `ops.watch` (`src/worker/ops-watch.ts`) и таблицу сигналов `hdc_ops_alerts`; отметки копий пишет команда `hub` через `withActor` под системным актором. Начальные данные грузит команда `hub seed:pilot`, которая вызывает слой `api` модулей (`hdr` справочники, `hdu` сотрудники, `hdk` черновики решений, `hdc` настройки), а не пишет в таблицы сама. Замер живёт в проекте `perf` Vitest рядом с `tests/perf/suggest-p95.test.ts`. Инструкции и протокол лежат в `docs/`, их проверяют сценарии `scripts/checks`.

**Стек:** как в вехах M5-M7. Новых зависимостей нет.

**Источник:** `docs/TZ.md` версии 1.2: строка M9 раздела 16.2 и 16.6, пилот 16.7, 8.10 (проверка на людях), 8.13 (голос портала), 13.7 (копии), 13.8 (наблюдение), 13.5 (переменные), 14.1 (ASVS 5.0 уровень 2), 14.4 (CSP), 15.1 (уровни тестов, нагрузка), 15.5 (условия выхода в пилот), 16.4 (что за владельцем), 17. Аудит `docs/audit/2026-11-23-technical-audit.md`, раздел 4.3 (цели времени). Отчёты `W0-report.md`, `W1-report.md`, `W2-report.md`, `M5-report.md`-`M8-report.md`. - Правила `CLAUDE.md`: сначала тест; `pnpm check`, `pnpm test`, `pnpm test:integration` перед каждым коммитом; новая таблица с RLS (`ENABLE` и `FORCE`) и строкой в `tests/integration/isolation/tables.ts`; изменение прав и настроек пишется в журнал аудита в той же транзакции; база только через `withActor`; тексты интерфейса только в `messages/*.json`; оформление только из токенов.

- Начальные данные не содержат данных клиентов: организации, пользователи клиентов и обращения появляются только из входа и работы.

## Решения, которых нет в ТЗ (нужно подтверждение)

1. **Подготовка идёт отдельной веткой и своим запросом на слияние.** M9 делится на "подготовку" и "M9 на сервере". Правило "одна веха - одна ветка" нарушается один раз. Причина: сервера может не быть неделями, а готовая работа не должна лежать на ветке. Цена: два отчёта по одной вехе.
2. **CSP не переключается, а проверяется полнотой.** Политика действует с волны 0, копия в режиме отчётов не вводится. Вместо переключения тест сверяет список страниц обхода со всеми `page.tsx` приложения, чтобы новая страница не ушла без проверки. Цена: при новой странице нужно дописать её в обход, иначе падает `pnpm check`.
3. **ASVS сверяется по тексту стандарта 5.0.0.** Каждое требование уровня 1 и 2 получает строку: состояние "есть", "отклонение", "на staging" или "не применимо" (V17 WebRTC целиком), ссылку на тест или файл. Текст стандарта берётся из репозитория OWASP на GitHub; если среда сборки его не скачает, нужна копия от владельца. Цена: около 350 строк таблицы, которые надо держать в каждой следующей вехе.
4. **Адреса показателей для Prometheus нет.** ТЗ его не просит (13.8), собирать показатели некому без внешнего сервиса. Наблюдение: журнал, сигналы `ops.watch`, `pg_stat_statements`. Цена: графиков нет до решения о сервисе.
5. **Фоновый процесс виден снаружи отдельным адресом.** Если упал `worker`, падает и `ops.watch`, сигнал не уходит никому. Процесс раз в минуту ставит отметку, адрес `/api/ready/worker` отвечает 503 при отметке старше 3 минут. `/api/ready` не меняется: по нему Caddy делит запросы, и сбой фонового процесса не должен снимать портал. Внешняя проверка в M9 смотрит оба адреса. Цена: ещё одна запись в базу раз в минуту.
6. **Возраст копий через отметку команды.** `backup.sh` и `base-backup.sh` после успеха вызывают `hub ops:backup-mark --kind dump|base`; новая таблица `hdc_ops_backups` (RLS, строка изоляции, только система). Сигнал `backup_stale`: ночной копии больше 26 часов (13.8), базовой больше 8 суток, последний выгруженный сегмент журнала (`pg_stat_archiver`) старше 26 часов при включённом архиве. Цена: сценарии копий зависят от образа портала; без отметки сигнал ложный, и это видно в первый же день.
7. **Нагрузка меряется в Vitest, без k6.** Как в решении 0054: функции портала целиком с настоящей базой, 40 вызовов после прогрева, p50 и p95. k6 - новый инструмент, а время ответа по HTTP без сервера не показательно. Пороги: аудит 4.3 (страница клиента 300 мс, страница сотрудника 400 мс, запрос очереди 50 мс), FR-SOL-14 (подсказка 500 мс при 50 запросах в секунду). Для доски идей порог страницы клиента 300 мс, для страницы показателей за 90 дней 2 секунды (в ТЗ порога нет, M8 намерила 0,6 с на 50 тысячах). Цена: замер по HTTP на сервере может дать другие числа, он повторяется в M9.
8. **Набор замера.** Миллион обращений в 1000 организаций, 95% закрыты (как в волне 2); 1000 решений; 10 000 идей и 500 000 голосов. Цена: заливка около 2 минут, замер не входит в CI.
9. **Начальные данные одним файлом JSON.** `hub seed:pilot --file <путь> --admin <адрес> [--dry-run]`: справочник модулей, праздники, шаблоны ответов, памятки первой линии, теги, настройка `ideas.vote_mode`, сотрудники приглашениями, решения только черновиками. Повторный запуск ничего не дублирует: ключ - код модуля, дата, код шаблона, адрес сотрудника. Схема Zod строгая, поля организаций, клиентов и обращений отклоняются. Решения не публикуются: FR-SOL-04 требует человека. Цена: значения по умолчанию из кода (SLA, календарь) файл не трогает, если владелец их не задал.
10. **Инструкции в репозитории, без ссылки в портале.** Раздел "Справка" появляется на этапе 2 (FR-WG-06, KB-33), поэтому `docs/guides/*.md` раздаются пилотным клиентам файлом или письмом (16.7, шаг 1). Названия кнопок в инструкции берутся в кавычках «...», проверка `guides` сверяет каждое с `messages/<язык>.json`, а правила голоса и тире проверяются как в текстах интерфейса. Цена: ссылку "Как пользоваться порталом" в меню владелец может попросить отдельно.
11. **Узбекские инструкции пишет исполнитель, вычитывает носитель языка.** До вычитки файл помечен "черновик". Цена: клиенты на узбекском получат вычитанный текст только после ответа владельца.
12. **Проверка удобства только на staging, на тестовой организации.** Без данных настоящих клиентов, запись экрана только с письменного согласия участника, в протокол пишутся время, остановки и ошибки, без имён. Цена: участникам нужен вход на staging.

## На что смотреть при проверке

1. Доказательства ASVS: ссылка ведёт на тест, который проверяет требование, а не на соседний. Отклонения перечислены отдельно и не спрятаны в "есть".
2. Полнота CSP: каждая страница из `src/app` есть в обходе, включая `/embed`, `/m`, редактор решений, доску идей и показатели; на страницах виджета `frame-ancestors` по ключу сервера не сломан.
3. Сигналы: падение фонового процесса видно снаружи; ложный `backup_stale` не уходит, пока архив выключен; в тексте сигнала нет адресов бакета и ключей.
4. Замер: набор действительно миллион строк, запросы идут под `hub_app` с политиками, а не под суперпользователем.
5. Восстановление: после `pg_restore` функции пересчёта идей принадлежат `hub_hdi_counter`, все таблицы с `FORCE` RLS, приложение без актора строк не видит.
6. Начальные данные: повторный запуск даёт ноль изменений и ноль записей аудита; файл с полем организации отклоняется целиком; решения остаются черновиками.
7. Инструкции: нет ни одного названия кнопки, которого нет в интерфейсе; нет обещаний "точно", "гарантированно"; ничего о функциях, которых нет (AI первой линии M5b).
