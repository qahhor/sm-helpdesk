# Отчёт по волне 0 плана оптимизации: готовность к staging

Дата: 23.11.2026. План: `docs/plans/W0.md` (9 задач). Источник: `docs/audit/2026-11-23-technical-audit.md`. Ветка: `claude/smartup-customer-portal-iszbit`. Решение: `docs/decisions/0037-ops-readiness.md`. Выполнение: задачи по порядку в одной сессии, в конце независимая проверка ветки.

## Итоговая независимая проверка ветки

Проверяющий с отдельным контекстом прочитал план, аудит, решение 0037 и весь diff. Вердикт: "готово после исправлений". Важные замечания и что сделано:

1. **Журнал доступа Caddy мог содержать секреты.** Фильтр вырезал только значения из адреса запроса, а заголовки писались целиком: секрет вебхука Telegram, подпись вебхука почты и `Referer` со страницы с `?token=`. Теперь эти заголовки и `Location` ответа удаляются. Проверено на настоящем Caddy.
2. **Событие `outbox.state` предупреждало бы каждую минуту вечно** после первой недоставки и просматривало всю очередь. Теперь считаются сбои только за последний час, добавлен частичный индекс (миграция 0042).
3. **Сигнал "не отправлено" будил бы дежурного из-за опечатки в адресе клиента.** Сбоем отправки теперь считается только строка, которая исчерпала повторы и не ушла. Отказ почтового сервера виден на обращении отметкой "Письмо не доставлено" (ТЗ 13.8). Повторное событие об уже не доставленном письме строку не трогает.
4. **Сигнал считался отправленным, когда не ушёл никуда.** Если дежурные не настроены или оба способа отказали, в журнале ошибка `ops.alert_undelivered`.
5. **Шаблоны ответов меняет только администратор, но свежий вход для них не требовался.** Добавлен, как и для доменов почты организации (мелкое замечание 6). Запись решения 0037 исправлена.

Заодно исправлены мелкие замечания 1, 6, 8, 9, 10, 11, 12: журнал сохраняет стек ошибки и не вырезает полезные поля; медленная транзакция считается без ожидания соединения; пределы памяти уменьшены до 6,8 ГБ; в инструкции при инциденте исправлено утверждение о простое при смене пароля роли; в памятке запуска добавлены срок хранения копий в бакете и сборка `.env.bootstrap` при восстановлении; тест не оставляет соединение без триггеров.

### Решения, принятые при выполнении

Все записаны в `docs/decisions/0037-ops-readiness.md`. Главные:

- Прежние вызовы `console` не переписаны, а переведены в формат JSON при запуске. Цена: их текст лежит в поле `msg`, а не в отдельных полях.
- Строки журнала на каждый запрос в приложении нет: время ответа берётся из журнала доступа Caddy. Число запросов к базе на страницу появится в волне 1.
- Неудачные входы сотрудников для сигнала считает общий счётчик, а не журнал аудита: журнал читает только администратор, политики RLS не менялись. Цена: окно фиксированное, перебор несуществующих адресов счётчик не видит.
- Право на сигнал занимается до отправки. Цена: при сбое отправки следующий сигнал этого вида уйдёт только через час; о сбое говорит журнал.
- Политика содержимого включена без копии в режиме отчётов (отступление от решения 0010 и от текста плана): копия повторяла бы ту же политику.
- Расширение статистики запросов живёт в схеме `ops`: в общей схеме его представления попадали в набор изоляции.
- В приёмочном браузерном тесте "Отправить и к следующему" проверяется переход на другое обращение очереди; точный порядок закреплён интеграционным тестом. Причина: параллельные браузерные тесты работают под тем же сотрудником.

### Мелкие замечания: отложены

| № | Замечание | Почему отложено |
|---|---|---|
| 2 | Сигнал о заражённом файле может повториться, когда старый заражённый файл гостя переходит к пользователю | Редкий случай, сигнал один; ключ по времени проверки появится с экраном очереди писем (M8) |
| 3 | Письмо, которое никогда не разбирается, даёт сигнал каждый час трое суток | Это и есть повод разобраться; подтверждение сигнала появится с экраном наблюдения (M8) |
| 5 | Комментарий в конце миграции 0041 говорит о журнале аудита, а счёт ведёт счётчик; ключ таблицы текстовый, а не `uuid` | Применённую миграцию править нельзя; на работу не влияет |
| 7 | Счётчик неудачных входов не видит перебор несуществующих адресов | Его ловят пределы частоты по адресу посетителя; записано в решении 0037 |
| 13 | Статический заголовок политики запретит встраивание будущих страниц виджета | Учесть в вехе M6 |
| 14 | Turnstile и загрузка в R2 при действующей политике не проверены | Шаг первой выкладки на staging |
| 15 | Второй слой держит только границу организации, не видимость личных обращений | Соответствует плану; записано в решении 0037 |

## Что нужно от владельца

1. Включить GitHub Actions (вопрос 10 в `docs/HANDOFF.md`): последняя незакрытая находка волны 0.
2. Сервер, Cloudflare и DNS для staging; на нём проверить Turnstile, R2 и восстановление из копии.
3. Создать пару ключей копий `age-keygen` на своём компьютере, закрытый ключ положить в менеджер паролей.
4. Задать дежурных в "Настройки", "Уведомления и почта": без них сигналы портала не уходят никуда.
5. Решить про внешний сервис сбора ошибок и про перенос непрерывного архива базы из M9.
