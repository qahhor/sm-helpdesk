# Отчёт по волне 1 плана оптимизации: запас по нагрузке и защите

Дата: 23.11.2026. План: `docs/plans/W1.md` (12 задач). Источник: `docs/audit/2026-11-23-technical-audit.md`, раздел 9, волна 1. Ветка: `claude/smartup-customer-portal-iszbit`. Решение: `docs/decisions/0038-capacity-and-hardening.md`. Выполнение: задачи по порядку в одной сессии, в конце замер на 200 тысячах обращений и независимая проверка ветки.

## Замер на 200 тысячах обращений

Набор: 200 тысяч обращений в 400 организациях, 95% закрыты. Время функций портала целиком (запросы и код), 40 вызовов после прогрева, PostgreSQL 18 во временном контейнере на машине сборки. Числа сравнимы между собой, но не равны числам боевого сервера.

| Что | p50 | p95 | Цель раздела 4.3 |
|---|---|---|---|
| Список обращений клиента | 2,3 мс | 2,9 мс | страница до 300 мс |
| Боковая панель очередей (все счётчики) | 9,8 мс | 15,2 мс | запрос очереди до 50 мс |
| Очередь "Новые" | 5,5 мс | 7,1 мс | до 50 мс |
| Очередь "Мои" | 8,5 мс | 11,4 мс | до 50 мс |
| Очередь "Вторая линия" | 9,6 мс | 12,8 мс | до 50 мс |
| Очередь "Ждём клиента" | 4,5 мс | 5,9 мс | до 50 мс |
| Очередь "Срок нарушен" | 5,6 мс | 8,8 мс | до 50 мс |
| Очередь "Все" по последнему изменению | 3,9 мс | 5,3 мс | до 50 мс |
| Обращение у сотрудника | 11,5 мс | 16,3 мс | страница до 400 мс |
| Задача раз в минуту | 1,0 с | | до 5 секунд |

Замер нашёл то, чего не было в аудите. Очереди "Мои" и "Вторая линия" сначала показали 78 и 81 мс при запросах к базе в 1-4 мс. Причина была в коде: расчёт фазы срока шёл по дням от создания обращения и на каждый день четыре раза форматировал дату, около 1 мс на строку у давно открытого обращения. Границы рабочих дней теперь запоминаются.

Сравнение с аудитом: список клиента был 134 мс, счётчики очередей 152 мс.

## Итоговая независимая проверка ветки

Проверяющий с отдельным контекстом прочитал план, аудит, журнал решений исполнителя и весь diff. Вердикт: "готово после исправлений".

Важные замечания:

1. **Ссылка в заметке "Письмо на проверке" собиралась разметкой.** Адреса из текста вырезались, но заметку показывает Markdown, и запись вида `[Войти](https:\//узел)` превращалась в настоящую ссылку. Теперь в тексте непроверенного письма экранируются все знаки разметки. Тест отрисовывает заметку и проверяет, что ссылок нет, на 15 способах записи.
2. **Ссылки страницы очередей теряли сортировку.** После того как у очереди "Все" появилась своя сортировка по умолчанию, вторая страница "Все" по сроку открывалась в другом порядке, а переход из "Все" в "Новые" молча переносил сортировку по последнему изменению. Адрес теперь считает умолчание для той очереди, куда ведёт.

Мелкие замечания, которые исправлены:

- Памятка выкладки: при смене `compose.prod.yaml` нужен перезапуск всех служб. По прежнему тексту Caddy остался бы в старой сети и отвечал 502. Оценено как важное.
- Правило частых паролей пропускало "MyPassword123" и "Summer2026!!". Добавлены: частое слово с короткой добавкой, пароль из одного ряда на две трети, месяцы и частые имена. Оценено как важное.
- Скачивание вложения оставляло соединение открытым при отказе.
- Сетевой слой молча отбрасывал тело и метод запроса: теперь отказывает.
- Не было теста успешного пути проверки адреса при соединении.
- Три вида адресов IPv6 с внутренним адресом внутри не были закрыты.
- Ошибка базы при перешифровании выглядела как "секрет не открывается".
- Тесты планов не видели запросы, написанные текстом, и изменения; сверялись не все счётчики.
- Один негодный идентификатор получателя оставлял без уведомления всех остальных.

### Решения, принятые при выполнении

Все записаны в `docs/decisions/0038-capacity-and-hardening.md`. Главные, с ценой:

- **Листание очередей по ключу не сделано.** Далёкие страницы "Все" стоят пропорционально смещению.
- **Задача "настройки один раз на запрос" сокращена** до объединения боковой панели и тестов бюджета: страницы открывают 4-6 транзакций, а не 15.
- **Идентификатора ключа в формате секрета нет:** ключ определяется пробной расшифровкой. При трёх и более ключах это перебор.
- **Вход из бота Telegram даёт две записи в журнале:** общую и прежнюю.
- **Сбой записи входа в журнал вход не отменяет.**
- **Запись о чтении обращения идёт на сервере при каждом открытии:** одна запись в базу на открытие.
- **У PostgreSQL и ClamAV привилегии не сброшены,** только запрет новых. Проверяющий предлагал сузить набор у базы; оставлено до staging.
- **Запросы библиотеки входа идут мимо нового сетевого слоя:** остаток находки S14, нужен пакет `undici`.
- **Переадресация вложения разрешена внутри доверенных узлов,** до 3 переходов.
- **Шестое непроверенное письмо в обращение за час сотруднику не видно** до экрана очереди писем (M8). Проверяющий возражал: знающий адрес ответа может на час заглушить непроверенного участника.
- **Подмена сетевого слоя в тестах** (`setOutboundFetchForTests`): новый общий шов, аудит просил их не добавлять. Без него проверку связи с сервером в тестах с базой не подменить.
- **Запрос привязки Telegram без заголовков Fetch Metadata пропускается.**

## Что нужно для staging

1. **Перезапуск всех служб.** В этой версии изменились сети: после миграций `hubc up -d` без имён служб, простой до минуты (памятка запуска, раздел 13).
2. **Образ по идентификатору:** `HUB_IMAGE=sha256:...` из `docker image inspect` (памятка, шаг 7).
3. **Вложения писем:** отправить письмо с файлом и убедиться, что файл дошёл. Если нет, добавить узел из журнала в `INBOUND_DOWNLOAD_HOSTS`.
4. **Замена ключа:** отрепетировать шаги из `docs/runbooks/incident.md` (прежний ключ, `hub secrets:reseal`, убрать прежний ключ).
5. **Привилегии PostgreSQL:** попробовать `cap_drop: ALL` с пятью нужными привилегиями.

## Что нужно от владельца

1. Срок хранения журнала аудита (вместе с юристом): журнал теперь растёт быстрее, в нём входы клиентов и чтения сотрудников.
2. Выгрузка журнала аудита за пределы сервера: нужен внешний сервис.
3. Пакет `undici` для запросов библиотеки входа (остаток находки S14): новая зависимость.
4. Прежние вопросы волны 0: GitHub Actions, сервер и DNS для staging, внешний сервис сбора ошибок, непрерывный архив базы.
