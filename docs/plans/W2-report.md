Выводы:

1. **Списки, очереди, страница обращения и фоновая задача держат цели на миллионе.** Время очередей растёт вместе с числом открытых обращений (их в наборе 40 тысяч), а не с размером таблицы. Боковая панель со всеми счётчиками на границе цели: 53 мс при цели 50 мс и сигнале тревоги 200 мс.
2. **Поиск сотрудника по тексту цели не держит: 4,4 секунды на миллионе.** Причина известна с задачи 4 (решение 0039, пункт 6): под политиками RLS оператор `ILIKE` не выполняется раньше условий политики, поэтому индекс по тексту не используется и таблица просматривается целиком. Время растёт вместе с таблицей: 0,9 с на 200 тысячах, 4,4 с на миллионе. Исправление одной командой в начальной настройке базы ждёт ответа владельца (вопрос 19 в `docs/HANDOFF.md`). Клиента это не касается: его поиск ограничен обращениями своей организации.
3. **Запрос из одних цифр это тоже поиск по тексту.** Цифры могут быть номером обращения, ИНН или частью текста, поэтому портал ищет все три. Быстрый поиск по номеру даёт только запрос с приставкой: `SUP-1042`. До исправления из пункта 2 сотрудникам стоит набирать номер с приставкой; палитра команд открывает обращение по номеру без поиска.

## Итоговая независимая проверка ветки

Проверяющий с отдельным контекстом прочитал план, аудит, решение 0039, журнал решений исполнителя и весь diff (16 коммитов, 110 файлов). Вердикт: "готово после исправлений". Критичных замечаний нет.

Важные замечания:

1. **Общий предел писем с неизвестных адресов отключал приём от новых клиентов.** Предел в 60 писем в час я добавил в задаче 13. Проверяющий показал, что 61 письмом в час с любых адресов можно на час остановить приём от всех, кто не подтверждён, и что остановленное письмо нельзя вернуть. Предел снят. Вместо него дежурным идёт сигнал, когда за час в "Неопознанных" появилось 60 обращений и больше: письма не теряются, решает человек.
2. **Повтор фоновой задачи расходовал предел частоты.** Письмо с файлом при недоступном хранилище разбиралось повторно и после нескольких попыток закрывалось как `rate_limited`. Теперь пределы считают письма, а не попытки.
3. **Запасное письмо уходило вместе с сообщением Telegram.** После перехода на одновременную отправку (задача 2) обе строки могли оказаться в одной пачке, и клиент, выключивший почту, получал и сообщение, и письмо. Запасные письма идут вторым проходом.
4. **Файл письма без строки после сбоя хранилища.** Не подтвердилось: правило базы не даёт удалить строку вложения моложе суток, строка остаётся, файл убирает суточная очистка. При проверке нашёлся код немедленной уборки, который никогда ничего не удалял; он убран, поведение закреплено тестом.

Мелкие замечания, которые исправлены:

- Память запуска очереди исходящих запоминала отказ чтения: одно неудачное чтение адреса проводило через ошибку всю очередь запуска.
- Команда архива не записывала сегмент на диск до ответа базе: после внезапной перезагрузки в архиве мог оказаться обрезанный файл.
- Базовая копия при выключенном архиве сообщала об успехе, хотя восстановить такую копию нельзя. Теперь сценарий отказывает.
- В памятке восстановления не было шага о прежних каталогах архива: после восстановления из логической копии новые сегменты получили бы имена прежних.
- Не было описания, что делать по каждому сигналу дежурным: добавлен раздел 6 в `docs/runbooks/incident.md`.
- Тест листания уведомлений не видел повтора строки на двух страницах.

После исправлений репетиция восстановления на момент времени повторена на PostgreSQL 18 с новой командой архива: прошла.

### Решения, принятые при выполнении

Все записаны в `docs/decisions/0039-scale-and-recovery.md`. Главные, с ценой:

- **Память запуска очереди исходящих живёт до 50 секунд.** Письмо может уйти на адрес, который сменили в эту минуту.
- **Два действия оставлены с двумя обновлениями строки обращения:** ответ клиента со снятием паузы и поднятие до P1.
- **Индекс (организация, статус) оставлен:** без статистики боевой базы убирать рано.
- **`ILIKE` не отмечен как безопасный для выполнения раньше политик.** Это меняет порядок применения условий политик RLS, решает владелец. Цена: поиск сотрудника по тексту 4,4 с на миллионе обращений.
- **Окно истории задаётся числом последних записей, а не курсором.** Каждая следующая часть перечитывает предыдущие, предел 1000.
- **Развязка модулей в одну сторону:** `hdu` по-прежнему берёт `hdn` для писем, собрать `hdu` без `hdn` нельзя.
- **Связи модулей собирает `src/wiring.ts` через общий объект процесса.** Точка входа без этого импорта упадёт при первом уведомлении; перечень точек входа держит тест.
- **Архив без pgBackRest.** Нет сжатия и проверки целостности архива.
- **Архив выключен по умолчанию,** включение на сервере ждёт решения владельца.
- **Нет теста двух фоновых процессов на одном расписании.** Поведение взято из кода pg-boss.
- **Вторая копия портала на том же сервере.** От гибели сервера не защищает.
- **Цепочка объединённых обращений проходится при чтении,** строки дублей не правятся: иначе пришлось бы ослабить правило базы "объединённое закрыто навсегда". Цена: до 20 запросов на длинную цепочку.
- **Общего предела на письма с неизвестных адресов нет,** только сигнал дежурным. Поток писем по-прежнему создаёт обращения в "Неопознанных".
- **Шесть отложенных замечаний вех не взяты** (решение 0039, пункт 16).
- **Три теста задачи 13 написаны до кода, но отдельно красными не запускались** (сигнал о придержанных письмах, форма каналов, журнал блокировки бота). Тест уборки загрузок письма прошёл сразу: он закрепляет поведение, а не исправление.

## Что нужно для staging

1. **Архив базы:** положить сценарии на сервер, включить `PG_ARCHIVE_MODE=on`, сделать первую базовую копию и один раз пройти восстановление на момент времени по `docs/runbooks/restore.md` (памятка запуска, раздел о копиях).
2. **Сигналы дежурным:** убедиться, что настроены чат и адреса дежурных; новых видов сигнала три: сбой архива, письма, остановленные пределом частоты, поток обращений с неизвестных адресов.
3. **Очередь исходящих на настоящем почтовом сервисе:** отправить несколько сотен писем и посмотреть, не упирается ли одновременная отправка в предел частоты сервиса.
4. **Вторая копия портала:** попробовать профиль `replica` и обновление без простоя (памятка запуска, раздел 12а).
