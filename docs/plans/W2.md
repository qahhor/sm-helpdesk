# Волна 2 плана оптимизации "До пилота": план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** портал держит всплески и рост до миллиона обращений, модули развязаны, копии базы позволяют восстановиться на момент времени, портал готов к запуску в двух копиях; закрыты отложенные замечания вех, которые стоит закрыть до пилота.

**Источник:** `docs/audit/2026-11-23-technical-audit.md`, раздел 9, волна 2. Владелец поручил вести разработку по плану аудита без остановок 23.11.2026; отдельного подтверждения этого плана по его поручению не ждём.

**ТЗ:** `docs/TZ.md`, разделы 9.2, 9.4, 11.8-11.11, 13.3-13.7, 14.3.

## Что в волну не входит и почему

- **Вычитка узбекского и английского носителем языка** (3 дня из оценки аудита). Её делает человек; список мест для вычитки лежит в `docs/i18n-review.md`.
- **Выпуск ТЗ 1.2 одним документом.** Вопрос 9 в `docs/HANDOFF.md` ждёт ответа владельца. В волне готовится перечень правок `docs/TZ-1.2-changes.md`: по нему ТЗ правится за один проход после подтверждения. Текст ТЗ не меняется.
- **Непрерывный архив на боевом сервере.** В волне делаются конфигурация, сценарии, инструкция и репетиция восстановления на момент времени во временных контейнерах. Включение на сервере ждёт решения владельца о переносе из M9 и самого сервера.
- **Второй сервер.** Делается готовность кода и конфигурации к двум копиям портала и проверка двух копий на одной машине.

## Общие ограничения

Правила `CLAUDE.md`. Новых пакетов и внешних сервисов нет. Политики RLS не ослабляются. Каждая новая таблица: RLS и строка в наборе изоляции. Индексы на больших таблицах строятся отдельным шагом вне транзакции (замечание F12 волны 1): для этого у запуска миграций появляется поддержка файлов без транзакции. Каждое изменение запроса проверяется планом на наборе в 200 тысяч обращений, цели раздела 4.3 аудита замеряются на миллионе в приёмке.

### Task 1 (Задача 1): Миграции без транзакции

**Files:** `scripts/db/migrate.mjs`, `tests/integration/migrate*.test.ts`, `docs/decisions/0039-scale-and-recovery.md`.

**Interfaces:** файл миграции, первая строка которого `-- hub:no-transaction`, выполняется вне транзакции, по одной команде; запись о применении ставится после последней команды. Такой файл содержит только `CREATE INDEX CONCURRENTLY IF NOT EXISTS` и `DROP INDEX CONCURRENTLY IF EXISTS`: повтор после сбоя безопасен.

- [ ] Падающие тесты: файл с отметкой выполняется вне транзакции (в нём проходит `CREATE INDEX CONCURRENTLY`); файл с отметкой и другой командой отклоняется до выполнения; сбой посреди файла не ставит запись о применении, повтор доводит до конца; недействительный индекс после сбоя пересоздаётся.
- [ ] Реализация, коммит `feat(db): migrations outside a transaction for concurrent indexes`.

### Task 2 (Задача 2): Очередь исходящих

**Files:** `src/modules/hdn/core/outbox.ts`, `src/worker/main.ts`, `tests/integration/outbox*.test.ts`.

- [ ] Падающие тесты: один запуск `outbox.dispatch` отправляет 500 ждущих писем (сейчас одну пачку); настройки и бот читаются один раз на запуск, а не на строку; одновременно идёт не больше 4 отправок; запуск останавливается по бюджету времени 50 секунд и не захватывает строки, которые не успеет отправить; ошибка одной строки не останавливает остальные (M4, мелкое 4: один негодный адрес дежурных).
- [ ] Реализация: цикл "взять пачку, отправить с ограничением одновременности, повторить" до пустой очереди или бюджета. Коммит `perf(hdn): outbox drains the queue within a time budget`.

## На что смотреть проверяющему

1. Очередь исходящих при сбое процесса посреди пачки: письмо не теряется и не уходит дважды сверх прежнего.
2. Одно обновление на действие не меняет порядок записи в журнал аудита и событий обращения.
3. История частями: граница страницы при записях с одинаковым временем; внутренние записи у клиента.
4. Файлы письма до транзакции: файл без строки после сбоя убирает очистка.
5. Развязка модулей: никакая точка входа не обращается к интерфейсу до его регистрации.
