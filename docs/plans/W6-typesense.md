# Волна 6 "Поиск на Typesense": план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** подключить Typesense как ускоритель текстового поиска там, где он даёт пользователю больше всего: поиск обращений на рабочем месте, подсказка решений на форме обращения и в виджете, похожие идеи и поиск по доске, поиск организаций и людей. Пользователь получает опечатки, поиск по началу слова, стемминг, синонимы, перевод письменности кириллица и латиница для узбекского и русского и свёртку похожих по звучанию написаний. Typesense ничего не решает о правах: он отдаёт только идентификаторы, строки читаются из PostgreSQL через `withActor`, и политика RLS остаётся последним словом. Если Typesense не отвечает или медлит, каждый поиск тихо идёт прежним путём PostgreSQL.

**Архитектура:** внутренний сервис по образцу векторов (`hdk/embeddings`, решение 0053). Интерфейсы `SearchReader` (портал) и `SearchIndexWriter` (фоновый процесс) в `src/modules/hdc/search/` (`types.ts`, `typesense.ts`, `postgres.ts`, `stub.ts`, `index.ts`, `scoped-key.ts`, `collections.ts`), чистые функции перевода письменности и свёртки в `hdc/search/fold.ts`; другие модули берут их только через `@/modules/hdc/api`. Документы строит модуль-владелец в своём `api` (`hdt` обращения, `hdk` решения из `hdk_published`, `hdi` идеи, `hdu` организации и люди), фоновый процесс собирает построители в `src/worker/main.ts`. Запись идёт через очередь `hdc_search_outbox`, которую пишут триггеры исходных таблиц в той же транзакции, что и изменение; разбирает её задача `search.sync`. Вызов идёт обычным `fetch` по внутреннему адресу во внутренней сети `search` без выхода в интернет, как TEI.

**Стек:** как в вехах M5-M9. Новый контейнер `typesense/typesense:30.2`. Новых пакетов npm нет: клиент на `fetch`, ключи с областью через `node:crypto`, контейнер в тестах через уже подключённый `testcontainers` (у Typesense есть руководство для него, `guide/testcontainers`).

## Общие ограничения

- Правила `CLAUDE.md`: сначала тест; `pnpm check`, `pnpm test`, `pnpm test:integration` перед каждым коммитом; новая таблица с RLS (`ENABLE` и `FORCE`) и строкой в `tests/integration/isolation/tables.ts`; база только через `withActor` (люди через `withIdentity`); тексты интерфейса только в `messages/*.json`; новая настройка и смена прав пишутся в аудит в той же транзакции.
- Политики RLS и тесты изоляции не ослабляются и не меняются. Typesense только сужает набор строк до запроса в PostgreSQL.
- Организация и пользователь для фильтра Typesense берутся только из актора.
- Ничего в AI: встроенные модели векторов, разговорный поиск (RAG) и поиск на естественном языке Typesense не включаются, ключей моделей у Typesense нет, раздел 14.3 не меняется.
- Данные клиентов не кешируются: кеш выдачи Typesense выключен по умолчанию (`use_cache`, `api/search`), каждый запрос несёт `use_cache: false` явно, своего кеша ответов в портале нет.
- Ни один ключ Typesense не попадает в браузер: модули `server-only`, переменных `NEXT_PUBLIC_*` нет, `--enable-cors` не ставится.
- Длинное и среднее тире и запрещённые разделом 8.13 слова запрещены и в новых документах.

## Возможности Typesense и где они нужны нам

Обязательно: без этого цель волны не достигается. Полезно: делается в волне, если укладывается, или следующей. Не нужно: не включается, причина справа.

| Возможность (страница) | Что даёт | Где у нас | Приоритет | Почему |
|---|---|---|---|---|
| Опечатки `num_typos`, `min_len_1typo` 4, `min_len_2typo` 7, `typo_tokens_threshold`, `enable_typos_for_numerical_tokens` (`api/search`) | До 2 правок Дамерау-Левенштейна на слово | Все поиски по тексту | Обязательно | Главное, чего нет в `ILIKE`; для цифр опечатки выключаются, номер `SUP-1042` не находит `1043` |
| Поиск по началу `prefix` (`api/search`) | Последнее слово как начало | Поиск при наборе: похожие идеи, подсказка, справочники | Обязательно | "Подбор слов" при наборе |
| Внутри слова `infix` (поле `infix: true`, только первое слово запроса) | Часть слова в середине | ИНН и код организации на сервере Smartup | Полезно | Заменяет `ILIKE '%...%'` для кодов; для текста не нужен |
| `split_join_tokens`, `drop_tokens_threshold` | Слитное и раздельное написание, отбрасывание лишних слов | Длинные описания в подсказке | Обязательно | Описание клиента длиннее заголовка решения (решение 0054, пункт 1) |
| Стемминг `stem: true` по `locale`, Snowball (`api/stemming`) | Формы слова | Русский и английский текст | Обязательно | Как `russian` и `english` в PostgreSQL сейчас |
| Свои словари стемминга `stem_dictionary` (`api/stemming`) | Пары "слово, корень" из файла JSONL | Узбекский | Полезно | Для узбекского нет конфигурации ни в PostgreSQL (`simple`), ни у Snowball; словарь частых окончаний предметной области ведёт команда базы знаний |
| `locale` поля (`guide/locale`: `ru` в списке, любой код ISO 639-1, ICU) | Разбор слов по правилам языка | `ru`, `en`, для узбекского проверить `uz` | Обязательно | Для не английских полей диакритика сохраняется, это важно для `ў`, `ғ`, `ʻ` |
| Перевод письменности | Нет как функции поиска: в примечаниях 30.2 только внутренний транслитератор разбора кириллицы | Узбекский на двух письменностях, русский латиницей | Обязательно, своим кодом | Делает портал: поле `*_fold` и свёрнутый запрос (решение 8) |
| Фонетика, soundex | Нет ни в одной странице 30.2 | "Похоже звучит" | Своим кодом | Честная замена: свёртка написаний плюс опечатки (решение 8) |
| Синонимы, наборы `synonym_sets` (с v30 общие для коллекций), одно- и многосторонние, `locale` у синонима, `synonym_prefix`, `synonym_num_typos`, `demote_synonym_match` (`api/synonyms`) | Связи слов внутри и между языками | Решения, идеи, обращения | Обязательно | "Похожие слова": `склад`, `ombor`, `warehouse` |
| Стоп-слова `stopwords` (только из запроса, не при записи; `api/stopwords`) | Отбрасывает "пожалуйста", "помогите" | Подсказка и похожие идеи | Полезно | Длинные описания клиентов с вежливыми словами |
| `token_separators`, `symbols_to_index` на поле (`api/collections`) | Свои разделители слов | Коды ошибок, `SUP-1042`, версии `5.12` | Полезно | Код ошибки ищется целиком |
| Фильтры `filter_by`, сортировка `sort_by` (до 3 полей) | Условия и порядок | Аудитория, организация, язык, модуль, статус идеи | Обязательно | Фильтр организации и аудитории вкладывается в ключ |
| Фасеты `facet_by` и счётчики | Число совпадений по значению | "Все" у сотрудника по статусу и организации | Не нужно сейчас | Счётчики очередей уже считает PostgreSQL под RLS; число из Typesense не проходит проверку RLS |
| Группировка `group_by`, `group_limit` | Одна строка на группу | Решение на трёх языках | Полезно | Заменяет "одно решение один раз" (решение 0054, пункт 3) прямо в поиске |
| Многократный поиск `multi_search`, объединение `union` с `remove_duplicates` (`api/federated-multi-search`) | Несколько запросов одним вызовом | Прямой и свёрнутый запрос; языки цепочки | Обязательно | Один сетевой вызов вместо трёх |
| Подсветка и отрывки | Текст с `<mark>` | Нигде | Не нужно | Текст из Typesense не показывается (решение 2), `highlight_fields: none` |
| `include_fields`, `exclude_fields` | Какие поля вернуть | Каждый запрос: только `id` | Обязательно | Вкладывается в ключ |
| Ключи с областью: HMAC от ключа только `documents:search`, вложенные параметры нельзя переопределить, `expires_at` (`api/api-keys`) | Фильтр арендатора на стороне Typesense | Каждый запрос | Обязательно | Первый слой изоляции; важно: закреплённые и спрятанные записи ключом не фильтруются, если не вложить `filter_curated_hits: true` |
| Курирование `pinned_hits`, `hidden_hits`, правила (с v30 общие) (`api/curation`) | Закрепить или спрятать запись по запросу | Решения: "по запросу 'накладная' первым решение KB-12" | Полезно | Даёт команде базы знаний рычаг без кода; только с `filter_curated_hits: true` |
| Разнообразие выдачи MMR (`api/curation`, новое в 30.1) | Меньше почти одинаковых результатов | Похожие идеи | Не нужно сейчас | Дубли идей сводит модератор |
| Объединения `JOIN` между коллекциями (`api/joins`) | Поля связанной коллекции | Нигде | Не нужно | Ключ поиска коллекции открывает и связанную коллекцию через объединение; поля организации у обращения не нужны |
| Вложенные поля `object` | Документы со структурой | Нигде | Не нужно | Документы плоские |
| Гео | Поиск по месту | Нигде | Не нужно | Нет такой задачи |
| Векторы: свои (`vector_query` с вектором запроса) и встроенные модели `ts/*` или OpenAI (`api/vector-search`) | Смысловой поиск | Решения и идеи | Не нужно в волне | Векторы BGE-M3 уже в pgvector и TEI; встроенные модели качают веса из Hugging Face и занимают память; внешние API нарушают 14.3 |
| Гибрид в Typesense: слова и вектор, `alpha` 0.3, `rerank_hybrid_matches`, `distance_threshold` | Слияние рангов внутри Typesense | Подсказка | Полезно, позже | Возможен со своими векторами; переносить векторы стоит только если замер задачи 10 покажет, что смысловой список pgvector под RLS медленнее цели |

## Решения, которых нет в ТЗ (нужно подтверждение)

1. **Что попадает в Typesense.** Коллекции через псевдонимы `hub_<имя>` на `hub_<имя>_v<N>`:
   - `hub_tickets`: `id`, `org_id`, `number`, `title`, первые 1000 знаков `description`, `title_fold`, `created_on`, `version`. Без внутренних заметок, сообщений, вложений, имени автора, адресов, ИНН и названия организации: автора и организацию сотрудник находит через `hub_people` и `hub_orgs`, как сейчас, поэтому переименование не тянет перезапись миллиона документов.
   - `hub_solutions`: строка на решение и язык только из `hdk_published` (`article_id`, `locale`, `audience`, `module_id`, `title`, текст без разметки до 5000 знаков, `title_fold`, `signature_codes`, `version`). Черновики, версии и переводы на проверке не попадают.
   - `hub_ideas`: только опубликованные статусы (решение 2 M7), `title`, `body`, `title_fold`, `module_id`, `status`. Без автора и организации.
   - `hub_orgs` (`name`, `inn`, `external_company_id` с `infix`, `name_fold`, `state`) и `hub_people` (`name`, `name_fold`, `is_staff`, `org_ids`). Адреса почты и телефоны не попадают никуда.
   Цена: поиск по заметкам и переписке не ускоряется (вопрос 3).
2. **Изоляция в два слоя.** Первый: портал держит только ключ `documents:search` на `hub_*` и на каждый запрос считает ключ с областью (HMAC-SHA256 по `api/api-keys`) с вложенными `filter_by`, `include_fields: id`, `highlight_fields: none`, `use_cache: false`, `filter_curated_hits: true` и `expires_at` через 60 секунд. Клиенту вкладывается `org_id:=<org актора>` для обращений и `audience:=clients` для решений; сотруднику `audience:[clients,internal]`, обращения и справочники ему видны все, как в RLS. Функция вызова принимает только тип `ScopedKey` от `scopeFor(actor, collection)`, ключ без области передать нельзя (тип и тест). Второй: проверка после. Из ответа берутся только идентификаторы и порядок; строки читаются `withActor` по `= any(ids)`, RLS отбрасывает чужое. Без второго слоя ошибка фильтра отдала бы клиенту темы и описания чужой организации или внутреннее решение; с ним клиент получает меньше совпадений и ни одного чужого текста, потому что текст, отрывки и `found` из Typesense не показываются. Каждый отброшенный у клиента идентификатор пишет `search.isolation_drop` (коллекция, число, без текста) и сразу поднимает `search_isolation`. Цена: лишний запрос по ключу, 1-3 мс.
3. **Ключи по процессам.** Главный ключ (`--api-key`) только в секрете контейнера и в команде `hub search:keys`, которая создаёт ключ записи (коллекции, документы, псевдонимы, `synonym_sets`, курирование на `hub_*`) для фонового процесса и `hub`, и ключ поиска для портала. Портал ключа записи не получает. Смена: `hub search:keys --rotate`; отзыв ключа поиска сразу гасит все ключи с областью от него. Цена: два секрета в `.env` сервера.
4. **Поиск обращений сотрудника.** Текст от трёх знаков даёт до 250 идентификаторов по релевантности (`per_page` до 250, `api/search`); запрос очереди ставит `ticket_id = any(ids)` вместо двух `containsText`, фильтры, порядок и ключ страницы очереди не меняются, номер, цифры, организации и авторы объединяются через `or`, как сейчас. Больше 250: "Показаны лучшие совпадения, уточните запрос". Цена: при частом слове часть совпадений не в списке, зато время не зависит от частоты (решение 0068, пункт 3).
5. **Поиск клиента.** Тот же путь с `org_id:=<org актора>`; кого из организации видит клиент, решает RLS. Цена: та же отсечка.
6. **Решения и идеи: слова в Typesense, смысл в pgvector.** Списки `fts` и `trg` запроса 11.6 заменяются одним `multi_search` (до 20 мест на язык цепочки, `group_by: article_id`); смысловой список остаётся в `hdk_search_documents`; RRF и пороги `ranking.ts` не меняются, признак "все слова" из `text_match_info`. Цена: подсказка зависит от двух сервисов; при сбое Typesense слова и триграммы идут прежним SQL.
7. **Опечатки и начало слова.** Значения по умолчанию 30.2 (`num_typos` 2, длины 4 и 7), опечатки в цифрах и кодах выключены, начало слова только у последнего слова, `split_join_tokens` для подсказки. Цена: короткие слова с опечаткой не находятся.
8. **Перевод письменности и свёртка вместо soundex.** Фонетики в Typesense нет. Чистая функция `foldText`: кириллица русского и узбекского в латиницу по одной схеме, нижний регистр, апострофы узбекской латиницы убраны (`o‘`, `o'`, `oʻ`, `g'`), `x`, `h`, `kh` в `h`, `q` в `k`, `ц` и `ts` в `s`, `ы` в `i`, `э` и `ё` в `e`, `ь` и `ъ` убраны, двойные буквы в одну. Свёрнутый текст в поле `*_fold`, запрос сворачивается той же функцией; прямой запрос по полям со стеммингом и свёрнутый по `*_fold` уходят одним `multi_search`, итог сливается RRF с весом свёрнутого 0.7 (подбирается в задаче 9). Описание обращения не сворачивается (память). Цена: лишние совпадения на коротких словах.
9. **Похожие слова.** Стемминг для `ru` и `en`; для узбекского свой словарь стемминга (`stem_dictionary`) частых окончаний предметной области, если `locale: uz` в задаче 1 работает, иначе только начало слова и опечатки. Синонимы: один общий набор `hub_synonyms` из файла `config/search-synonyms.json`, загрузка `hub search:synonyms` с проверкой Zod и аудитом; синонимы не срабатывают на исправленных опечатках (`synonym_num_typos` 0) и стоят ниже прямых совпадений (`demote_synonym_match`). Цена: без списка связи между языками нет, кроме смыслового поиска.
10. **Запись: очередь в той же транзакции.** Таблица `hdc_search_outbox` (`org_id`, `outbox_id`, `entity_kind`, `entity_id`, `op` `upsert` или `delete`, `created_on`, `attempts`, `last_error_code`). Строки пишут триггеры `t_hdt_tickets_search`, `t_hdk_published_search`, `t_hdi_ideas_search`, `t_hdi_idea_translations_search`, `t_hdu_organizations_search`, `t_hdu_memberships_search` только при изменении индексируемых колонок, публикации и аудитории: откатилось изменение, нет и строки. В строке только вид и идентификатор, поэтому вставка разрешена любому актору `hub_app`, чтение и удаление только системе. Имена людей в схеме `auth`: строку для `hub_people` ставит код входа через `withIdentity`, пропуск ловит сверка. Цена: лишняя строка на правку обращения.
11. **Задача `search.sync`.** Будится после фиксации и раз в минуту; до 500 строк `FOR UPDATE SKIP LOCKED`, повторы схлопываются, актуальные строки читаются под системным актором, импорт `action=upsert` пачкой; нет строки, архив, сужение аудитории, отклонение или объединение идеи дают удаление. `version` = `modified_on` в микросекундах, старое не перезаписывает новое. 5 попыток с паузами 10, 60, 300, 900 секунд. Цена: задержка обычно до секунд; в эту задержку решение, ставшее внутренним, ещё находится по слову, но RLS не отдаёт его клиенту.
12. **Переиндексация и сверка.** `hub search:reindex [--collection]` строит `hub_<имя>_v<N+1>`, заливает пачками по 5000, сверяет число и переключает псевдоним; старая удаляется через сутки. Ночная `search.reconcile` в 04:10 по Ташкенту: число документов и выгрузка `id,version` против PostgreSQL, расхождения в очередь, больше 0.1% дают `search_drift`. После восстановления базы Typesense строится заново, снимки не нужны. Цена: около минуты ночной нагрузки.
13. **Память.** По `guide/system-requirements` нужно 2-3 размера индексируемых полей. Обращения: около 80 байт темы, до 1000 знаков описания (кириллица 2 байта), свёрнутая тема; на миллион обращений при среднем описании 400 знаков около 0,9 ГБ полей, то есть 1,8-2,7 ГБ памяти. Решения, идеи, организации, люди: до 100 МБ. Предел `TYPESENSE_MEM_LIMIT` по умолчанию 2,5 ГБ, точное число даёт задача 10; `--memory-used-max-percentage=90`. Сумма пределов служб станет около 12,3 ГБ, на сервере 8 ГБ Typesense не включается (вопрос 1). Цена: без 16 ГБ на production остаётся `SEARCH_PROVIDER=postgres`.
14. **Откат.** Ожидание: 60 мс у очередей сотрудника, 100 мс у поиска клиента и справочников, 120 мс у подсказки и похожих идей. Ошибка, ожидание дольше, ответ не по схеме Zod или пустой ключ дают прежний поиск PostgreSQL и событие `search.fallback` (коллекция, причина, время, без текста). После 5 сбоев за 30 секунд процесс 60 секунд не ходит в Typesense (состояние здоровья, не данные). `search_unavailable`: больше 20 откатов за час или `/health` не отвечает 3 проверки подряд. Цена: при сбое пропадают опечатки и свёртка.
15. **Переменные.** `SEARCH_PROVIDER` (`postgres`, `typesense`, `stub`; по умолчанию `postgres`), `TYPESENSE_URL` (внутренний адрес, проверка как у `EMBEDDINGS_URL`), `TYPESENSE_SEARCH_KEY` (только `web`), `TYPESENSE_WRITE_KEY` (только `worker` и `hub`), `TYPESENSE_MEM_LIMIT`. Цена: нет.
16. **Контейнер.** Служба `typesense` в `compose.prod.yaml` и `compose.yaml`: `typesense/typesense:30.2@sha256:610f2d34b1f93d00762869da2c67736775e5798d19a2c8b91b014b8a0cc1e110`, сеть `search` (портал, фоновый процесс, Typesense; `internal: true`), том `typesense_data`, `cap_drop: ALL`, `no-new-privileges`, главный ключ из секрета, флаги `--log-slow-searches-time-ms=-1`, `--enable-search-logging=false`, `--enable-access-logging=false`, `--enable-search-analytics=false`, без `--enable-cors`, порт не публикуется. Цена: ещё один образ для обновления.
17. **Что клиенты ищут и не находят.** Без ответа владельца аналитика Typesense выключена. Вместо неё портал сам считает пустые подсказки по уже записанным исходам (FR-SOL-13): число показов без решения по модулю и языку за неделю, без текста запроса, на странице показателей рядом с FR-MET-05. Если владелец разрешит тексты (вопрос 5): правило `nohits_queries` только для подсказки, событие портал шлёт сам после `findInText` и маски данных, без пользователя и организации, хранение 90 дней, видит только `admin` и роль базы знаний. Цена: без текстов команда видит, где пусто, но не что именно искали.

## На что смотреть при проверке

1. Изоляция: клиент А не видит обращение Б при нарочно сломанном фильтре заглушки и при живом Typesense с ключом без `org_id`; закреплённое правилом курирования внутреннее решение не доходит до клиента; ни один ответ портала не содержит текста из Typesense.
2. Ключи: в клиентском коде нет ключа и адреса Typesense; ключ без области не принимается функцией вызова; ключ поиска не пишет (проверка на контейнере); просроченный ключ с областью отклоняется.
3. Состав индекса: нет заметок, сообщений, адресов, телефонов, имён авторов, текста не из `hdk_published`.
4. Откат: остановленный, медленный и отвечающий мусором Typesense дают ту же выдачу, что PostgreSQL, и событие без текста; с открытым выключателем время не больше прежнего плюс 2 мс.
5. Синхронизация: откат транзакции не оставляет строки; архив, сужение аудитории, отклонение, объединение убирают документ; старая пачка не перезаписывает новую; сверка чинит удалённый руками документ.
6. Кеш, журналы, AI: `use_cache: false` в каждом запросе; флаги журналов решения 16; нет полей встроенных векторов и моделей.
7. Замер под `hub_app` с политиками на миллионе обращений.

План и решения 1-17 приняты вместе с ответами на вопросы.
