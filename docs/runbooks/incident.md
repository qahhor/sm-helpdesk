# Если что-то случилось: действия при инциденте безопасности

ТЗ 14.7. Короткая инструкция для дежурного и администратора. Один раз проигрывается на staging до первого клиента.

Ниже `hubc` означает `docker compose -f /opt/smartup-hub/compose.prod.yaml`, `hub` означает `hubc exec web node hub.mjs`.

## 1. Первые 15 минут

1. Записать время, что замечено и кем. Ничего не удалять: журналы и база нужны для разбора.
2. Сообщить владельцу продукта и техническому руководителю.
3. Остановить развитие инцидента подходящим действием из раздела 2.
4. Сохранить журналы: `hubc logs --since 24h > /root/incident-$(date +%F).log`, выгрузить журнал аудита из рабочего места ("Настройки", "Журнал аудита").

## 2. Как остановить

| Что нужно | Как |
|---|---|
| Закрыть портал для всех | `hubc stop web`. Письма и вебхуки при этом не теряются: почтовый сервис и Telegram повторят доставку |
| Отозвать все сессии (клиентов и сотрудников) | `hub sessions:revoke --all`: все входят заново, в журнале аудита запись `session.revoked_bulk` с числом. Когда: подозрение на кражу куки или ключа `BETTER_AUTH_SECRET`, утечка между организациями, неизвестный сотрудник в журнале входов |
| Отозвать сессии всех сотрудников | `hub sessions:revoke --staff`: клиенты остаются в портале. Когда: подозрение, что ноутбук или пароль сотрудника скомпрометирован, а кого именно, неясно |
| Отозвать сессии одного человека | `hub sessions:revoke --user <адрес>` (сессии клиента или сотрудника, доступ остаётся). Сотруднику с подозрением на кражу второго фактора: "Настройки", "Сотрудники", сброс доступа, или `hub staff:reset --email <адрес>` после проверки личности (раздел 3) |
| Отключить вход через один сервер Smartup | Рабочее место: "Настройки", "Серверы Smartup", "Отключить"; или `hub server:disable --code <код>`. Клиенты этого сервера не входят, их данные остаются |
| Отключить вход из бота и уведомления в Telegram | Убрать `TELEGRAM_BOT_TOKEN` из `.env`, затем `hubc up -d web worker`. В @BotFather отозвать токен (`/revoke`) |
| Остановить приём писем | В кабинете Resend отключить вебхук приёма. Письма останутся у Resend |
| Отозвать все токены виджета в Smartup Web | Заменить `EMBED_TOKEN_SECRET` (раздел 3): токены виджета живут 15 минут и подписаны этим секретом, после перезапуска все прежние перестают действовать. Открытая панель виджета просит открыть её снова |
| Закрыть виджет одного сервера Smartup | Рабочее место: "Настройки", "Серверы Smartup", карточка сервера, блок "Виджет": режим "Виджет выключен" (у команды `hub server:widget` такого режима нет). Утёк общий секрет токена контекста: там же "Создать новый секрет", прежний перестаёт действовать сразу, новый передать разработчикам Smartup |
| Выключить AI | Удалить `/opt/smartup-hub/.env.worker` (или строку `ANTHROPIC_API_KEY` в нём), затем `hubc up -d worker`. Решения и переводы работают без AI: черновик заполняется темой, перевод пишет сотрудник. Ключ отозвать в консоли Anthropic. `AI_STUB` на сервере не включать: портал с ним не запустится |
| Остановить обмен с таск-менеджером | `DEV_TRACKER=manual` в `.env` (строки `DEV_TRACKER_URL`, `DEV_TRACKER_TOKEN`, `DEV_TRACKER_WEBHOOK_SECRET` можно оставить), затем `hubc up -d web worker`. Передача в разработку идёт вручную, адрес `/api/webhooks/tracker` отвечает 404 |
| Заблокировать адрес или страну | Правило в Cloudflare WAF |

### Проверка личности перед сбросом доступа сотрудника (ASVS V6.4.4)

Сотрудник потерял телефон со вторым фактором или пароль и просит сброс. Сбросить можно, только убедившись, что просит он сам, так же строго, как при выдаче доступа:

1. Не отвечать на просьбу в том же канале, где она пришла (письмо, чат). Администратор сам звонит сотруднику по номеру из списка сотрудников у владельца, а не по номеру из просьбы.
2. Руководитель линии сотрудника подтверждает просьбу отдельно: звонком или лично.
3. Только после обоих шагов: "Настройки", "Сотрудники", сброс доступа, или `hub staff:reset --email <адрес>`. Ссылку на новый пароль передать сотруднику лично или по номеру из шага 1, не письмом на адрес из просьбы.
4. Строка в журнале инцидентов (раздел 7): дата, кого сбросили, кто подтвердил. Сброс сам пишет `staff.reset` в журнал аудита.

Если подтвердить не удалось, доступ не сбрасывается; при подозрении на подмену завершить сессии сотрудника (`hub sessions:revoke --user <адрес>`) и сообщить владельцу.

## 3. Смена секретов

Каждый секрет меняется в `.env` на сервере, затем `hubc up -d web worker`. Новое значение сохранить в менеджере паролей.

| Секрет | Что происходит при смене | Порядок |
|---|---|---|
| `BETTER_AUTH_SECRET` | Все сессии перестают действовать. Сотрудникам, возможно, придётся заново подключить второй фактор: проверить на staging | Новое значение `openssl rand -hex 32` |
| `ENCRYPTION_KEY` | Простоя нет, если идти по шагам справа. Без прежнего ключа сохранённые секреты серверов Smartup, токен бота дежурных и секреты исходящих вебхуков перестают расшифровываться: серверы пропускаются при входе, вебхуки ждут повтора с причиной "секрет не расшифровывается" | 1. Прежнее значение перенести в `ENCRYPTION_KEY_PREVIOUS`, в `ENCRYPTION_KEY` записать новое (`openssl rand -base64 32`). 2. `hubc up -d web worker`. 3. `hub secrets:reseal` (консоль `hub`, как в памятке запуска): команда перешифровывает секреты новым ключом и называет те, что не открылись. 4. Убрать `ENCRYPTION_KEY_PREVIOUS`, снова `hubc up -d web worker`. Если ключ утёк, шаги 1-4 в тот же день и замена самих секретов: секрет клиента каждого сервера в Smartup, токен бота в @BotFather и секрет каждого вебхука (кнопка "Сменить секрет" на странице адреса) |
| `REPLY_HMAC_SECRET` | Простоя нет: прежнее значение переносится в `REPLY_HMAC_SECRET_PREVIOUS`, ответы на уже отправленные письма принимаются по обеим подписям, новые письма подписываются новым значением | Новое значение `openssl rand -hex 32`. Прежнее держать 30 суток (столько клиенты отвечают на старые письма), затем убрать. Если ключ утёк, прежнее значение не оставлять: ответы на старые письма пойдут по цепочке писем и номеру в теме |
| Пароли ролей базы (`DATABASE_URL_*`) | Короткий простой: после смены пароля новые соединения этой роли не открываются, пока служба не перезапущена с новым адресом | Сначала записать новый адрес в `.env` или `.env.migrate`, затем `alter role <роль> password '<новый>'` под суперпользователем и сразу `hubc up -d web worker` |
| `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET` | Письма не уходят и не принимаются до перезапуска с новым значением | Новые значения в кабинете Resend |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` | Бот молчит до перезапуска | `/revoke` в @BotFather, новый секрет вебхука `openssl rand -hex 32`, затем `hub telegram:set-webhook` |
| Ключи R2 | Загрузка и скачивание файлов не работают до перезапуска | Новый ключ в Cloudflare, старый удалить |
| `TURNSTILE_SECRET` | Проверка "не робот" недоступна до перезапуска, действуют пределы частоты | Новый ключ в Cloudflare |
| Секрет клиента OAuth сервера Smartup | Вход через этот сервер не работает до ввода нового | Запросить у разработчиков Smartup, ввести в "Серверы Smartup" |
| `EMBED_TOKEN_SECRET` | Все токены виджета перестают действовать сразу: открытая панель виджета в Smartup Web просит открыть её снова, обращения и черновики не теряются | Новое значение `openssl rand -base64 32` (не совпадает с `BETTER_AUTH_SECRET` и `ENCRYPTION_KEY`), затем `hubc up -d web worker`. Прежнего значения портал не держит: замена и есть отзыв |
| `DEV_TRACKER_TOKEN`, `DEV_TRACKER_WEBHOOK_SECRET` | Опрос таск-менеджера и его вебхук не работают, пока значения не совпадут с таск-менеджером; передачи в разработку не теряются, статусы задач догонят при следующем опросе (раз в 15 минут) | Новый токен портала выпускает таск-менеджер Smartup; новый секрет вебхука `openssl rand -hex 32` задать в обоих местах, затем `hubc up -d web worker`. На время согласования можно `DEV_TRACKER=manual` |
| `ANTHROPIC_API_KEY` | Задачи AI ждут повтора, пока ключ не заменён | Новый ключ в консоли Anthropic, прежний отозвать, записать в `.env.worker`, затем `hubc up -d worker` |
| Ключ `age` резервных копий | Старые копии читаются старым ключом | Новая пара `age-keygen`, открытый ключ в `backup.env`; старый закрытый ключ хранить, пока живы старые копии |

## 4. Кого уведомить

| Кого | Срок | Кто уведомляет |
|---|---|---|
| Владелец продукта | сразу | дежурный |
| Клиенты, чьи данные затронуты | по решению владельца и юриста; срок по закону о персональных данных уточняет юрист (вопрос 39 раздела 20 ТЗ) | владелец |
| Разработчики Smartup | сразу, если затронут вход через Smartup или секрет клиента OAuth | технический руководитель |
| Resend, Cloudflare, Hetzner | если инцидент на их стороне или утёк их ключ | администратор |

## 5. После инцидента

- Разбор без поиска виноватых в течение 5 рабочих дней: что случилось, как заметили, что остановило, что меняем.
- Запись решения в `docs/decisions/`, тест на найденную ошибку, правка этой инструкции.

## 6. Сигналы дежурным: что означает и что делать

Портал сам шлёт сигнал в чат дежурных и письмом раз в 5 минут, один вид не чаще раза в час (задача `ops.watch` фонового процесса). В сигнале только вид и числа, без адресов, текстов и ключей. В скобках код сигнала: так он назван в журнале процесса (`ops.alerts_sent`, `ops.alert_undelivered`). Сверку кодов с этой таблицей делает `pnpm check` (`scripts/checks/alerts-runbook.mjs`).

| Сигнал | Что случилось | Что делать |
|---|---|---|
| Упали фоновые задачи (`jobs_failed`) | Задача фонового процесса завершилась ошибкой после всех повторов | `hubc logs --since 1h worker`, найти задачу и ошибку. Задачи по расписанию повторятся сами |
| Не отправлены письма и сообщения (`outbox_failed`) | Строка очереди исходящих исчерпала повторы | Журнал фонового процесса и кабинет почтового сервиса: отказ адреса, предел частоты, ключ. На обращении у сотрудника видна отметка "Письмо не доставлено" |
| Исходящие не уходят (`outbox_lag`) | Самая старая строка ждёт дольше 5 минут | Работает ли фоновый процесс (`hubc ps`), отвечает ли почтовый сервис. После запуска процесс отправит очередь сам |
| Письма без разбора (`inbound_stuck`) | Входящее письмо не разобрано дольше 10 минут | Журнал фонового процесса: чаще всего недоступно хранилище или почтовый сервис. Разбор повторяется сам до трёх суток |
| Неудачные входы сотрудников (`staff_signin_failures`) | 20 и больше неудачных входов за 15 минут | Возможен подбор пароля: журнал аудита, при необходимости закрыть адреса на Cloudflare |
| Заражённые файлы (`infected_files`) | Антивирус нашёл заражённый файл | Файл клиенту и сотруднику не отдаётся. Посмотреть обращение, предупредить клиента |
| Архив журнала базы не сохраняется (`archive_failing`) | Архив включён, последняя попытка сохранить сегмент неудачна | Место на диске и права каталога `/opt/smartup-hub/wal-archive`, журнал базы. Пока сигнал не снят, восстановления на момент времени нет |
| Предел частоты остановил письма (`inbound_held`) | За час 10 и больше писем получили итог `rate_limited`: много писем с одного адреса или в одно обращение | Письма сохранены в таблице входящих на 90 суток, но обращением не стали и повторно не разбираются. Если среди них письмо клиента, попросить его написать ещё раз или ответить в обращении. Назойливый адрес: закрыть его обращение как спам, тогда следующие письма с него не станут обращениями |
| Поток обращений с неизвестных адресов (`unidentified_flood`) | За час 60 и больше обращений в очереди "Неопознанные" | Письма не теряются. Закрыть лишние как спам (адрес попадает в список блокировки), при продолжении ограничить отправителя у почтового сервиса или на время снять переадресацию адреса поддержки |
| Не разобраны события автоматизации (`automation_dropped`) | Событие обращения снято с очереди после пяти сбоев разбора: его правила, вебхуки и уведомления не выполнены. Среди них может быть сообщение дежурным о P1 | `hubc logs --since 1h worker`, событие `automation` с ошибкой. Открыть обращения за последний час в рабочем месте: срочные посмотреть вручную. После исправления причины новые события разбираются сами, снятое событие не повторяется |
| События автоматизации не разбираются (`automation_lag`) | Самое старое событие ждёт разбора дольше 5 минут: фоновая задача не идёт или события ждут повтора после сбоев | Работает ли фоновый процесс (`hubc ps`, `/api/ready/worker`), журнал процесса. Пока сигнал не снят, правила и уведомления опаздывают: срочные обращения смотреть в очереди вручную |
| Встроенное уведомление не работает (`builtin_rule_inactive`) | Предустановленное правило выключено, негодно или осталось без действия; в сигнале их коды | "Настройки", "Правила автоматизации": включить правило или вернуть ему действие. Пока сигнал не снят, дежурные о P1, руководитель линии о сроке или Customer Care о низкой оценке не узнают |
| Резервные копии устарели (`backup_stale`) | В сигнале виды копий: `dump` ночной копии нет дольше 26 часов, `base` базовой копии нет дольше 8 суток, `wal` журнал базы не сохранялся в архив дольше 26 часов. `base` и `wal` проверяются только при включённом архиве. Отметку удачной копии ставит сам сценарий командой `hub ops:backup-mark` | Журнал сценариев копий (`/var/log/hub-backup.log`, `/var/log/hub-wal.log`), место на диске, ключи бакета. `dump`: запустить `backup.sh` вручную; если копия выгрузилась, а сценарий завершился ошибкой об отметке, проверить, что служба `web` запущена (`hubc ps`). `base`: запустить `base-backup.sh`. `wal`: смотреть сигнал `archive_failing` и журнал базы. Сразу после первой выкладки сигнал `dump` приходит до первой ночной копии: сделать её вручную. После аварийного перезапуска базы счётчики `pg_stat_archiver` обнуляются (время последнего сегмента пустое), и `wal` может прийти ложно, пока не уйдёт следующий сегмент журнала: проверить `hubc exec -T postgres psql -U postgres -Atc "select archived_count, last_archived_time from pg_stat_archiver"` через 5-10 минут (или `select pg_switch_wal()`), сигнал после этого не повторяется |
| Поиск Typesense не отвечает (`search_unavailable`) | За час больше 20 откатов поиска на PostgreSQL или `/health` Typesense не ответил 3 проверки подряд (план W6, решение 14) | Поиск работает прежним путём, без опечаток, синонимов и свёртки письменности; данных не теряется. `hubc ps` (служба `typesense`), `hubc logs --since 1h typesense`, память (`hubc exec worker node hub.mjs search:status`). Если служба упала по памяти: поднять `TYPESENSE_MEM_LIMIT` или вернуть `SEARCH_PROVIDER=postgres` в `.env` и перезапустить `web` |
| Очередь индекса поиска стоит (`search_lag`) | Строка очереди `hdc_search_outbox` ждёт записи дольше 5 минут: фоновый процесс не идёт или Typesense отклоняет запись | Работает ли `worker` и `typesense`, событие `search.sync_failed` в журнале процесса (код сбоя). Пока сигнал не снят, новые и изменённые обращения находятся только прежним путём. После исправления очередь разбирается сама; строки после пяти сбоев починит ночная сверка или `search:reindex` |
| Индекс поиска расходится с базой (`search_drift`) | Ночная сверка нашла больше 0,1% недостающих, устаревших или лишних документов; в сигнале коллекции | Недостающее уже поставлено в очередь, лишнее удалено. Если сигнал повторяется вторую ночь: `hubc exec worker node hub.mjs search:reindex --collection <коллекция>` |
| Поиск вернул клиенту чужое (`search_isolation`) | Typesense вернул клиенту идентификатор чужой организации или внутреннего решения, и проверка базы (RLS) его отбросила: клиент ничего не увидел, но фильтр ключа поиска сломан | Срочно: событие `search.isolation_drop` в журнале портала (коллекция и число). Вернуть `SEARCH_PROVIDER=postgres` в `.env`, перезапустить `web`, сменить ключи `search:keys --rotate`. Разобрать причину до повторного включения |

### Внешняя проверка и правила хостинга

Сигналы выше шлёт сам портал. Если упал фоновый процесс, молчит и `ops.watch`, поэтому снаружи нужны ещё проверки (решение владельца о сервисе в M9; до него шаги памятки запуска).

| Что проверяется | Порог | Что делать |
|---|---|---|
| `GET https://<домен>/api/ready` раз в минуту | Не 200 два раза подряд | Портал не принимает запросы или база недоступна: `hubc ps`, `hubc logs --since 15m web postgres`. Caddy сам снимает копию портала, которая не готова |
| `GET https://<домен>/api/ready/worker` раз в минуту | Не 200 два раза подряд (503, если фоновый процесс не отмечался дольше 3 минут) | Фоновый процесс упал или не берёт задачи: `hubc ps worker`, `hubc logs --since 15m worker`, затем `hubc up -d worker`. Пока он стоит, не уходят письма, сигналы дежурным и не идут сроки SLA. На `/api/ready` и на портал это не влияет |
| Диск сервера | Занято 80% | Каталоги копий (`/var/backups/smartup-hub`, `wal-archive`), журналы контейнеров. Не удалять файлы базы |
| Память сервера | Занято 80% дольше 10 минут | `docker stats`: какая служба вышла за свой предел памяти (`*_MEM_LIMIT` в `.env`) |
| Процессор сервера | Занято 80% дольше 10 минут | `docker stats`, медленные запросы в `ops.pg_stat_statements` (памятка запуска) |

## 7. Журнал инцидентов

Каждый инцидент (утечка между организациями, подозрение на кражу сессии или ключа, сброс доступа сотрудника по потере фактора) записывается сюда строкой: дата, что случилось, затронутые организации числом, что сделано, кто вёл. Строка "Утечки данных между организациями" сводки пилота (`/agent/metrics/pilot`) считается по этому журналу. Утечка между организациями останавливает пилот сразу (ТЗ 16.7). Текстов обращений, адресов и токенов в журнале нет.
