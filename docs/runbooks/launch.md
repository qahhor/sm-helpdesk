# Запуск Smartup Hub на сервере: полная инструкция для администратора

Документ ведёт от пустого сервера до работающего портала: что подготовить, что настроить, в каком порядке запускать и как проверить результат. Подходит для staging и production: различия отмечены. Идите сверху вниз и отмечайте пункты. Пропуск пункта обычно не видно сразу: портал запустится, но не будет отправлять письма, принимать файлы или пускать клиентов.

Основание: раздел 13 ТЗ (инфраструктура), решения 0013-0033 в `docs/decisions/`. Файлы развёртывания лежат в корне репозитория: `compose.prod.yaml`, `Caddyfile`, `Dockerfile`, `.env.example`.

Состав портала в `compose.prod.yaml`:

| Служба | Что делает |
|---|---|
| `caddy` | Принимает HTTPS, получает сертификат, передаёт запросы порталу |
| `web` | Портал: кабинет клиента и рабочее место сотрудников |
| `worker` | Фоновый процесс: проверка файлов, задача обращений раз в минуту, ночная очистка |
| `clamav` | Антивирус для вложений |
| `tei` | Смысловые векторы подсказки решений: модель BGE-M3 на сервере, без выхода в сеть |
| `typesense` | Поиск с опечатками, синонимами и свёрткой письменности (план W6). Профиль `search`: включается только на сервере 16 ГБ |
| `postgres` | База PostgreSQL 18 с pgvector |
| `bootstrap`, `migrate` | Одноразовые задачи: начальная настройка базы и миграции |

Правила, которые действуют на всех шагах:

- Секреты хранятся только в файлах на сервере и в менеджере паролей. В репозиторий, чат и почту они не попадают.
- Данные production никогда не копируются на staging (ТЗ 13.1).
- У staging свои домен, бакет, бот Telegram, домен почты и ключи: тестовые письма не должны портить репутацию основного домена (ТЗ 13.10).

## 0. Что подготовить заранее

- [ ] **Сервер.** Hetzner Cloud или сервер в дата-центре Узбекистана, Ubuntu LTS (ТЗ 13.2). Production: 8 vCPU, 16 ГБ памяти, 160 ГБ NVMe. Staging: 4 vCPU, 8 ГБ памяти.
- [ ] **Домен в Cloudflare.** Портал: `hub.smartup24.com` (решение 70). Staging: отдельный поддомен, например `hub-staging.smartup24.com`.
- [ ] **Учётная запись Cloudflare** с доступом к DNS домена, R2, Turnstile и WAF.
- [ ] **Учётная запись Resend** для отправки писем.
- [ ] **Telegram:** доступ к @BotFather. Для staging отдельный бот.
- [ ] **Данные от разработчиков Smartup** по каждому серверу Smartup (общее облако и выделенные): адрес Smartup Web, адрес сервера входа (issuer), идентификатор и секрет клиента OAuth портала, какие роли Smartup дают администратора клиента.
- [ ] **Доступ к репозиторию** на GitHub, чтобы собрать образ портала.
- [ ] **Менеджер паролей**, куда сохраняются все секреты этой инструкции.
- [ ] **Второй фактор** включён у хостинга, GitHub, Cloudflare, Resend и регистратора домена (ТЗ 13.9).
- [ ] **Первый администратор портала:** рабочий адрес почты и телефон с приложением кодов (Google Authenticator, 1Password или любое с TOTP).
- [ ] **Файл справочника модулей Smartup** (`modules.json`) для поля "Модуль" в обращениях, если он уже есть.

## 1. Сервер

- [ ] Обновления системы: `sudo apt update && sudo apt -y upgrade`.
- [ ] Автоматические обновления безопасности: `sudo apt install -y unattended-upgrades && sudo dpkg-reconfigure -plow unattended-upgrades`.
- [ ] Отдельный пользователь администратора с `sudo`. Вход по SSH только по ключу: в `/etc/ssh/sshd_config` задать `PasswordAuthentication no` и `PermitRootLogin no`, затем `sudo systemctl restart ssh`. Проверить вход по ключу в новом окне, прежде чем закрыть текущее.
- [ ] Точное время: `timedatectl` показывает `System clock synchronized: yes`. От часов зависят коды второго фактора.
- [ ] Docker Engine и Compose по официальной инструкции для Ubuntu (docs.docker.com, Install Docker Engine on Ubuntu). Проверка: `docker compose version`.
- [ ] Ротация журналов Docker (ТЗ 13.8). В `/etc/docker/daemon.json`:

  ```json
  { "log-driver": "json-file", "log-opts": { "max-size": "50m", "max-file": "10" } }
  ```

  затем `sudo systemctl restart docker`.
- [ ] **Проверка защиты сервера** (ТЗ 13.9, план M9, решение 16) после шагов этого раздела, раздела 9 и после каждой выкладки: скопировать `scripts/ops/server-audit.mjs` той же версии в `/opt/smartup-hub/server-audit.mjs` и запустить `sudo node /opt/smartup-hub/server-audit.mjs`. Сценарий только читает (настройки SSH, `20auto-upgrades`, `docker inspect`) и печатает по пункту "есть", "нет" или "исключение" без значений переменных и секретов; код 1, если есть "нет". Вывод целиком переписать в журнал сухих прогонов в конце памятки. На staging без Cloudflare пункт "Caddy: только адреса Cloudflare" даёт "нет": это ожидаемо (`TRUSTED_PROXIES` всех адресов). Правила сетевого экрана хостинга сценарий не видит: их проверить в кабинете хостинга по пункту ниже.
- [ ] **Сетевой экран хостинга** (Hetzner Cloud Firewall или аналог): входящие 80 и 443 только с адресов Cloudflare (списки: `https://www.cloudflare.com/ips-v4` и `https://www.cloudflare.com/ips-v6`), SSH только с доверенных адресов, остальное закрыто. Важно: экран нужен именно на стороне хостинга. Порты, которые публикует Docker, обходят правила `ufw` на самом сервере. Без экрана посетитель мог бы подделать заголовок адреса и обойти пределы частоты (решение 0020).
- [ ] Второй слой той же защиты уже в `Caddyfile`: Caddy отвечает 403 всем адресам вне списка `TRUSTED_PROXIES` (по умолчанию адреса Cloudflare, список в `compose.prod.yaml`). Раз в квартал сверять список с `https://www.cloudflare.com/ips-v4` и `ips-v6`. Для staging без Cloudflare задать в `.env` рядом с `compose.prod.yaml`: `TRUSTED_PROXIES="0.0.0.0/0 ::/0"`. Проверка после запуска: `curl -sk -o /dev/null -w '%{http_code}' --resolve <домен>:443:<IP сервера> https://<домен>/` с адреса не из списка возвращает 403.
- [ ] Память: значения в `compose.prod.yaml` рассчитаны на сервер 8 ГБ (база 3 ГБ, антивирус 2 ГБ, портал и фоновый процесс по 768 МБ, в сумме 6,8 ГБ). Для другого сервера задать `PG_MEM_LIMIT`, `PG_SHARED_BUFFERS` (четверть памяти базы), `PG_EFFECTIVE_CACHE_SIZE`, `CLAMAV_MEM_LIMIT`, `WEB_MEM_LIMIT`, `WORKER_MEM_LIMIT`.

## 2. Cloudflare: DNS и защита

- [ ] DNS: запись A (и AAAA, если у сервера есть IPv6) для домена портала на адрес сервера, проксирование включено (оранжевое облако).
- [ ] SSL/TLS: режим **Full (strict)**.
- [ ] SSL/TLS, Edge Certificates: **Always Use HTTPS выключено.** Caddy сам переводит посетителей на HTTPS и по порту 80 получает и продлевает сертификат. Если перевод на HTTPS делает Cloudflare, первый сертификат не выпустится.
- [ ] **Turnstile** (проверка "не робот"): создать виджет, имя узла равно домену портала, режим Managed. Ключ сайта и секрет пойдут в `TURNSTILE_SITE_KEY` и `TURNSTILE_SECRET`. На настоящем адресе в production без них портал не запустится (решение 0033).
- [ ] **WAF, управляемые правила** (Security, WAF, Managed rules): включить управляемый набор Cloudflare. Он отсекает типовые SQL-инъекции и XSS до портала.
- [ ] **Ограничение частоты** (Security, WAF, Rate limiting rules): путь содержит `/login`, `/staff/login`, `/invite`, `/confirm-email` или начинается с `/api/auth/`; больше 30 запросов за 10 секунд с одного адреса: блокировать на 10 секунд. Если тариф даёт одно правило, оно ставится сюда.
- [ ] **Bot Fight Mode** пока не включать: решение принимается в шаге 11 после проверки вебхука Telegram и входа через Smartup.

## 3. Cloudflare R2: хранилище файлов

- [ ] Бакет без публичного доступа: `hub-files` для production, `hub-staging-files` для staging.
- [ ] Ключ API R2 с правом **Object Read & Write только на этот бакет**. Идентификатор ключа пойдёт в `R2_ACCESS_KEY_ID`, секрет в `R2_SECRET_ACCESS_KEY`, адрес `https://<идентификатор счёта>.r2.cloudflarestorage.com` в `R2_ENDPOINT`.
- [ ] CORS бакета (Settings, CORS Policy). Браузер кладёт файл прямо в бакет и показывает картинки оттуда:

  ```json
  [
    {
      "AllowedOrigins": ["https://<домен портала>"],
      "AllowedMethods": ["PUT", "GET"],
      "AllowedHeaders": ["content-type"],
      "MaxAgeSeconds": 3600
    }
  ]
  ```

- [ ] Правило жизненного цикла (Settings, Object lifecycle rules) на префикс `quarantine/`: удалять объекты старше 2 дней. На префикс `files/` правило не ставится.
- [ ] Отдельный бакет для резервных копий базы (шаг 12), например `hub-backups`, и отдельный ключ с правом записи только в него.

## 4. Почта: Resend

- [ ] Добавить в Resend домен отправки: `mail.smartup24.com` для production, отдельный поддомен для staging.
- [ ] Записи SPF и DKIM, которые показывает Resend, добавить в DNS Cloudflare (записи почты не проксируются).
- [ ] Политика DMARC (ТЗ 13.10): запись TXT `_dmarc.mail.smartup24.com` со значением `v=DMARC1; p=none; rua=mailto:<адрес для отчётов>`. После месяца без ошибок в отчётах ужесточить до `p=quarantine`.
- [ ] Дождаться в Resend статуса домена Verified.
- [ ] Записи почты сценарием (план M9, решение 18): `node scripts/ops/mail-dns-check.mjs --mail mail.smartup24.com --reply reply.smartup24.com` (для staging свои поддомены) с любой машины. Проверяет SPF Resend на `send.<домен>` (только `include:amazonses.com`, `~all` или `-all`), ключ DKIM `resend._domainkey`, DMARC и MX приёма. Код 1 при ошибках; предупреждение `p=none` в первый месяц ожидаемо. Вывод переписать в журнал сухих прогонов.
- [ ] Ключ API только с правом отправки. Он пойдёт в `RESEND_API_KEY`.
- [ ] Адрес отправителя для `MAIL_FROM`: `Smartup Hub <hub@mail.smartup24.com>`.

**Приём писем (веха M4: ответы клиентов и обращения по почте).**

- [ ] Добавить в Resend домен приёма `reply.smartup24.com` (для staging свой поддомен) и включить на нём приём писем. Запись MX, которую показывает Resend, добавить в DNS Cloudflare без проксирования. Это значение пойдёт в `REPLY_DOMAIN`.
- [ ] В Resend создать вебхук на `https://<домен портала>/api/webhooks/email` с событиями приёма (`email.received`) и доставки (`email.delivered`, `email.bounced`, `email.complained`, `email.delivery_delayed`). Секрет подписи вида `whsec_...` пойдёт в `RESEND_WEBHOOK_SECRET`. Без верной подписи портал отвечает 401 и ничего не пишет.
- [ ] Секрет подписи адресов ответа: `openssl rand -hex 32`. Он пойдёт в `REPLY_HMAC_SECRET`. Смена секрета делает недействительными адреса ответа во всех уже отправленных письмах: клиент, ответивший на старое письмо, получит новое обращение.
- [ ] Адреса поддержки `support@greenwhite.uz` и `support@smartup24.com`: у владельца почты каждого адреса включить переадресацию на адрес приёма `inbox@reply.smartup24.com`. Письмо на любой адрес домена приёма, кроме адресов ответа `reply+...`, становится обращением. Проверка каждого адреса идёт с экрана "Уведомления и почта" (шаг 10).

## 5. Бот Telegram

- [ ] В @BotFather команда `/newbot`: название и имя бота. Токен пойдёт в `TELEGRAM_BOT_TOKEN`.
- [ ] Секрет вебхука: `openssl rand -hex 32`. Он пойдёт в `TELEGRAM_WEBHOOK_SECRET`. Нужен именно hex: Telegram принимает в секрете только латинские буквы, цифры, `_` и `-`.
- [ ] Для staging отдельный бот со своим токеном. Боевой бот к staging не подключать.
- [ ] Production: бот портала для клиентов один, @SmartupSupportBot (решение владельца 23.11.2026). Его токен идёт в `TELEGRAM_BOT_TOKEN`. До установки вебхука портала убедиться, что к боту больше ничего не подключено: у бота Telegram один получатель сообщений, прежнее подключение (другая система, операторы, автоответчик) после вебхука портала перестанет получать сообщения клиентов.

## 6. Серверы Smartup (вход клиентов)

- [ ] По каждому серверу Smartup получены адрес Smartup Web, issuer, идентификатор клиента и секрет клиента (шаг 0).
- [ ] Согласовано соответствие ролей: например, роль Smartup `director` даёт роль портала `client_admin`.
- [ ] Адрес возврата портала команда `server:add` напечатает в шаге 10. Его нужно передать разработчикам Smartup для регистрации портала.

## 7. Образ портала

Автоматическая сборка GitHub Actions пока выключена (решение 99), поэтому образ собирается вручную на сервере или на машине сборки.

- [ ] Получить код нужной версии: `git clone https://github.com/qahhor/sm-helpdesk.git && cd sm-helpdesk && git checkout <тег или коммит>`.
- [ ] Собрать образ: `docker build -t smartup-hub:<версия> .`. Если Docker Hub недоступен: `docker build --build-arg NODE_IMAGE=mirror.gcr.io/library/node:26.13.1-slim@sha256:e6bedef217677b276c591795e169840edd9096dbf13f29df8ef8d1856b8820bc -t smartup-hub:<версия> .`
- [ ] Если образ собран на другой машине, перенести его на сервер: `docker save smartup-hub:<версия> | ssh <сервер> docker load`.
- [ ] Узнать идентификатор образа: `docker image inspect --format '{{.Id}}' smartup-hub:<версия>`. Ответ вида `sha256:...`. Портал запускается по идентификатору, а не по метке: метку можно незаметно переставить на другой образ, идентификатор это отпечаток содержимого (аудит 23.11.2026, находка S9). Идентификатор записать рядом с версией: он нужен для отката.
- [ ] Записать тег образа: он нужен для отката (шаг 13).

## 8. Файлы и секреты на сервере

- [ ] Каталог портала: `sudo mkdir -p /opt/smartup-hub/secrets && sudo chmod 700 /opt/smartup-hub`. Скопировать туда `compose.prod.yaml` и `Caddyfile` из той же версии репозитория, что и образ.
- [ ] Сгенерировать секреты и **сразу сохранить их в менеджер паролей**:

  | Секрет | Команда | Куда |
  |---|---|---|
  | Пароль суперпользователя PostgreSQL | `openssl rand -hex 24` | `secrets/pg_superuser`, `.env.bootstrap` |
  | Пароли ролей `hub_owner`, `hub_app`, `hub_auth` | `openssl rand -hex 24` для каждой, все разные | `.env.bootstrap`, адреса подключения |
  | `BETTER_AUTH_SECRET` | `openssl rand -base64 32` (не меньше 32 знаков) | `.env` |
  | `ENCRYPTION_KEY` | `openssl rand -base64 32`: ровно 32 байта, 44 знака со знаком `=` в конце; не совпадает с `BETTER_AUTH_SECRET` | `.env` |
  | `TELEGRAM_WEBHOOK_SECRET` | `openssl rand -hex 32` | `.env` |
  | `REPLY_HMAC_SECRET` | `openssl rand -hex 32` | `.env` |
  | `EMBED_TOKEN_SECRET` | `openssl rand -base64 32` (не меньше 32 знаков, не совпадает с `BETTER_AUTH_SECRET` и `ENCRYPTION_KEY`) | `.env` |
  | `RESEND_WEBHOOK_SECRET` | из настроек вебхука Resend (шаг 4) | `.env` |

  Пароли в формате hex не требуют экранирования в адресах подключения. Потеря `ENCRYPTION_KEY` означает потерю секретов серверов Smartup: их придётся задать заново.

- [ ] Пароль суперпользователя в файл без перевода строки: `printf '%s' '<пароль>' > /opt/smartup-hub/secrets/pg_superuser`.
- [ ] Ключ Claude API (по желанию, план M5, решение 3): файл `/opt/smartup-hub/.env.worker`, его получает только контейнер `worker` (`compose.prod.yaml`, `env_file` службы `worker`; в `.env` ключа нет, у `web` его нет никогда). Без файла решения работают без AI: черновик из обращения заполняется темой, перевод пишет сотрудник. Исходящие запросы сервера к `api.anthropic.com` должны быть разрешены.

  ```dotenv
  ANTHROPIC_API_KEY=<ключ>
  AI_MODEL_FAST=claude-haiku-5-5
  AI_MODEL_QUALITY=claude-sonnet-5-5
  ```

  Модели необязательны (план M5b, решение 1): по умолчанию первая линия на `claude-sonnet-5-5`, остальные цели на `claude-haiku-5-5`, выбор по целям в "Настройки > AI-помощник"; `AI_MODEL_FAST` и `AI_MODEL_QUALITY`, если заданы, меняют значения уровней по умолчанию. `AI_STUB` (заготовленные ответы вместо модели) в production не задаётся никогда: портал с `AI_STUB=1` на настоящем адресе не запускается, и вместе с ключом тоже. Выключить AI: удалить `.env.worker` (или строку ключа) и `hubc up -d worker`, см. `docs/runbooks/incident.md`, раздел 2.

- [ ] Файл `/opt/smartup-hub/.env` (портал и фоновый процесс). Узел базы внутри сети Compose называется `postgres`:

  ```dotenv
  NODE_ENV=production
  HUB_URL=https://hub.smartup24.com
  HUB_DOMAIN=hub.smartup24.com
  DATABASE_URL_APP=postgres://hub_app:<пароль hub_app>@postgres:5432/hub
  DATABASE_URL_AUTH=postgres://hub_auth:<пароль hub_auth>@postgres:5432/hub
  BETTER_AUTH_SECRET=<секрет>
  ENCRYPTION_KEY=<ключ>
  MAIL_TRANSPORT=resend
  RESEND_API_KEY=<ключ Resend>
  MAIL_FROM=Smartup Hub <hub@mail.smartup24.com>
  RESEND_WEBHOOK_SECRET=<секрет вебхука Resend>
  REPLY_DOMAIN=reply.smartup24.com
  REPLY_HMAC_SECRET=<секрет адресов ответа>
  EMBED_TOKEN_SECRET=<секрет токена виджета>
  # Задаётся после первого настоящего письма (шаг 11, "Почта"). Пока не задан, отправитель письма не опознаётся.
  # INBOUND_AUTHSERV_ID=<имя сервиса приёма из Authentication-Results>
  TURNSTILE_SITE_KEY=<ключ сайта>
  TURNSTILE_SECRET=<секрет Turnstile>
  TELEGRAM_BOT_TOKEN=<токен бота>
  TELEGRAM_WEBHOOK_SECRET=<секрет вебхука>
  CLIENT_IP_HEADER=cf-connecting-ip
  FILE_STORAGE=r2
  R2_ENDPOINT=https://<идентификатор счёта>.r2.cloudflarestorage.com
  R2_BUCKET=hub-files
  R2_ACCESS_KEY_ID=<идентификатор ключа>
  R2_SECRET_ACCESS_KEY=<секрет ключа>
  CLAMAV_HOST=clamav
  EMBEDDINGS=tei
  EMBEDDINGS_URL=http://tei:80
  HUB_SHOWCASE=0
  LOG_LEVEL=info
  LOG_FORMAT=json
  ```

  Переменные, которых нет в файле выше, и когда они нужны:

  | Переменная | Когда задаётся |
  |---|---|
  | `EMBED_TOKEN_SECRET` | Всегда в production: подпись токена виджета в Smartup Web (план M6). Без него на настоящем адресе портал не запускается |
  | `ENCRYPTION_KEY_PREVIOUS` | Только на время замены `ENCRYPTION_KEY`: прежний ключ, затем `hub secrets:reseal` и убрать (`docs/runbooks/incident.md`, раздел 3) |
  | `REPLY_HMAC_SECRET_PREVIOUS` | Только на время замены `REPLY_HMAC_SECRET`: прежний ключ на 30 суток, пока клиенты отвечают на старые письма |
  | `LOG_FORMAT` | `json` (по умолчанию в production) или `text`. На сервере `json`: строки журнала читают как JSON |
  | `DEV_TRACKER`, `DEV_TRACKER_URL`, `DEV_TRACKER_TOKEN`, `DEV_TRACKER_WEBHOOK_SECRET` | `DEV_TRACKER=manual` (по умолчанию): передача в разработку вручную, остальные три не задаются. `DEV_TRACKER=smartup` после описания API таск-менеджера: адрес API (только https), токен портала в таск-менеджере, секрет подписи вебхука `openssl rand -hex 32`; таск-менеджер шлёт события на `https://<домен>/api/webhooks/tracker` |
  | `MCP_ALLOWED_IPS` | Сервер MCP для AI-сотрудников (`https://<домен>/api/mcp`): адреса и сети, с которых ходит Hermes Agent, через запятую, например `10.0.3.0/24`. Запрос принимается, только если адрес входит и в этот список, и в список адресов токена. Не задана: проверяется только список токена. Токены выпускает администратор на экране "AI-сотрудники". Адрес берётся из заголовка `CLIENT_IP_HEADER`: списки адресов надёжны, только если порт портала закрыт для всех, кроме доверенного прокси (Cloudflare или свой nginx), и прокси перезаписывает этот заголовок своим значением (решение 0125). Проверка: запрос к `https://<адрес сервера в обход прокси>/api/mcp` не доходит до портала |
  | `MCP_MAX_INFLIGHT` | Сколько вызовов инструментов сервера MCP процесс выполняет одновременно, от 1 до 32, по умолчанию 4: каждый вызов занимает соединение пула базы. Сверх предела ответ 429. Обычно не задаётся |
  | `AGENT_WEBHOOK_URL`, `AGENT_WEBHOOK_SECRET` | События для AI-сотрудника (Hermes Agent): адрес приёма событий (только https) и секрет подписи `openssl rand -hex 32`, задаются парой. Не заданы: события агенту не ставятся, портал работает как раньше. Задаются после получения адреса и секрета от команды AI-агентов |
  | `AI_STUB` | Никогда на сервере: только разработка на localhost |
  | `ANTHROPIC_API_KEY`, `AI_MODEL_FAST`, `AI_MODEL_QUALITY` | Только в `.env.worker`, см. пункт выше |
  | `EMBEDDINGS`, `EMBEDDINGS_URL` | `tei` и `http://tei:80`, когда веса модели скачаны (шаг 9); до этого `EMBEDDINGS=stub` |
  | `HUB_OAUTH_CLIENT_SECRET` | Не в файле: переменная оболочки для одного вызова `hub server:add`, иначе команда спросит секрет без показа на экране |
  | `HUB_DB_NAME` | В `.env.bootstrap`, если база называется не `hub` |

  `TELEGRAM_API_URL`, `CLAMAV_PORT`, `MAIL_FILE_DIR` и `FILE_STORAGE_DIR` на сервере не задаются. `DEV_TRACKER` не задаётся: передача в разработку работает в ручном режиме, пока нет описания API таск-менеджера Smartup (`docs/integrations/dev-tracker.md`). Полный перечень с пояснениями: `.env.example`. При неверном значении портал не запускается и в журнале называет переменную, не печатая значение.

## 9. Первый запуск

Команды выполняются из `/opt/smartup-hub`.

- [ ] База: `hubc up -d postgres`. Проверка: `hubc ps` показывает `postgres` в состоянии healthy.
- [ ] Начальная настройка базы: `hubc run --rm bootstrap`. Создаются роли `hub_owner`, `hub_app`, `hub_auth`, роль без входа `hub_hdi_counter` (владелец функций пересчёта счётчиков идей, решение 0065), база `hub`, расширения `vector`, `pg_trgm` и `pg_stat_statements` (в схеме `ops`). Повторный запуск безопасен.
- [ ] Удалить `.env.bootstrap`: `shred -u .env.bootstrap`. Пароли уже в менеджере паролей.
- [ ] Начальную настройку базы запускать снова на уже работающем сервере в двух случаях: при выкладке версии с миграцией 0052 (поиск по тексту) и после обновления старшей версии PostgreSQL. Она ставит отметку оператору поиска, без которой поиск по тексту идёт без индекса. Признак: `migrate` пишет "Поиск по тексту идёт без индекса". Для запуска `.env.bootstrap` собирается заново из менеджера паролей и после удаляется.
- [ ] Начальную настройку базы запускать снова и перед выкладкой версии с миграцией 0084 (счётчики идей без подмены актора): она создаёт роль `hub_hdi_counter`. Без роли миграция 0084 останавливается с сообщением "Роль hub_hdi_counter не создана", ничего не применив; после `bootstrap` миграции запускаются повторно. `.env.bootstrap` собирается так же, как выше.
- [ ] Миграции: `hubc run --rm migrate`. В конце строка "Применено миграций: N" (при повторе "База актуальна, новых миграций нет"). Здесь же ставятся очереди фонового процесса.
- [ ] Веса модели векторов (решение 0053; один раз на сервер, около 2,3 ГБ): `hubc --profile tools run --rm tei-download`. Служба скачивает BGE-M3 с huggingface.co в том `tei_models` и запускает модель; после строки `Ready` в выводе остановить её (Ctrl+C). Дальше служба `tei` работает без выхода в сеть и читает веса с тома. **Этот шаг ни разу не выполнялся:** у среды разработки нет доступа к huggingface.co. При первом запуске проверить: `hubc logs tei` заканчивается строкой `Ready`, а не ошибкой загрузки модели; `hubc exec web node -e "fetch('http://tei:80/embed',{method:'POST',headers:{'content-type':'application/json'},body:JSON.stringify({inputs:['проверка']})}).then(r=>r.json()).then(v=>console.log(v[0].length))"` печатает `1024`. Если `tei` без сети не находит модель в кеше, сеть не открывать (она закрыта намеренно), а указать в `--model-id` путь к каталогу модели на томе (`/data/models--BAAI--bge-m3/snapshots/<хеш>`). Память: службе нужно до 3 ГБ (`TEI_MEM_LIMIT`), с ней сумма пределов превышает 8 ГБ сервера; на сервере 8 ГБ уменьшить `PG_MEM_LIMIT` и `CLAMAV_MEM_LIMIT` или взять сервер на 16 ГБ.
- [ ] Без весов или без службы `tei` портал работает: подсказка ищет по сигнатуре и словам и пишет в журнал событие `kb.suggest_embedder_unavailable`. Пока веса не скачаны, можно оставить `EMBEDDINGS=stub`: тогда смысловой поиск идёт по буквосочетаниям, без модели.
- [ ] Поиск на Typesense (план W6; ответ владельца 0070: на production только с сервером 16 ГБ, до этого шаг пропускается и `SEARCH_PROVIDER` не задаётся, поиск идёт через PostgreSQL). Главный ключ: `install -m 600 /dev/null secrets/typesense_api_key && openssl rand -hex 32 > secrets/typesense_api_key`. Запуск: `hubc --profile search up -d typesense`, `hubc ps` показывает `typesense` в состоянии healthy. Ключи процессов: `hubc exec worker node hub.mjs search:keys`; команда спрашивает главный ключ без отображения (`cat secrets/typesense_api_key` в другом окне) и печатает три ключа один раз. В `.env` портала: `SEARCH_PROVIDER=typesense`, `TYPESENSE_URL=http://typesense:8108`, `TYPESENSE_SEARCH_KEY` и `TYPESENSE_STAFF_SEARCH_KEY`; в `.env.worker`: `SEARCH_PROVIDER=typesense`, `TYPESENSE_URL=http://typesense:8108`, `TYPESENSE_WRITE_KEY`. Ключ записи в `.env` не кладётся: портал его не читает. Затем `hubc up -d web worker` и первая заливка `hubc exec worker node hub.mjs search:reindex`; `hubc exec worker node hub.mjs search:status` показывает документы каждой коллекции, пустую очередь и память. После любого периода с `SEARCH_PROVIDER=postgres` (выключение, откат при сбое) индекс не обновлялся: при возврате к `typesense` сначала `hubc exec worker node hub.mjs search:reindex`, потом перезапуск `web`. Смена ключей: `search:keys --rotate` (прежние ключи перестают действовать сразу, после неё обновить оба файла и перезапустить `web` и `worker`). Память: `TYPESENSE_MEM_LIMIT` (по умолчанию 2560m, число из замера в `docs/plans/W6-report.md`).
- [ ] Запуск всех служб: `hubc up -d`. Первое обновление баз ClamAV идёт до 10 минут, фоновый процесс ждёт его.
- [ ] Состояние: `hubc ps` показывает `web` и `clamav` в состоянии healthy, `caddy`, `worker` и `postgres` запущены.
- [ ] Сертификат: в `hubc logs caddy` есть строка о выпуске сертификата (`certificate obtained successfully`). Если её нет 10 минут, проверить шаг 2 (Always Use HTTPS выключено) и что порт 80 открыт для адресов Cloudflare.
- [ ] Портал отвечает: `curl -fsS https://<домен>/api/health` возвращает `{"status":"ok"}`, `curl -fsS https://<домен>/api/ready` возвращает `{"status":"ready","checks":{"db":"ok"}}`, то есть портал видит базу. Ответ 503 с `not_ready` означает, что база недоступна или неверны пароли в `.env`.
- [ ] Фоновый процесс: в `hubc logs worker` есть "Фоновый процесс запущен".
- [ ] Фоновый процесс берёт задачи: `curl -fsS https://<домен>/api/ready/worker` возвращает `{"status":"ready","checks":{"worker":"ok"}}`. Ответ 503 значит, что процесс не отмечался дольше 3 минут (решение 0066).
- [ ] Расписания фонового процесса (новая версия процесса, запущенная раньше миграций, ждёт свои очереди и не падает): `hubc exec postgres psql -U postgres -d hub -c "select name, cron, timezone from pgboss.schedule order by name"` показывает `attachment.sweep`, `automation.process`, `devtasks.sync`, `ideas.cycle` (1-го числа в 09:00 по Ташкенту), `ideas.moderation_digest` (в 09:30), `kb.reconcile`, `maintenance.cleanup`, `ops.heartbeat`, `ops.watch`, `outbox.dispatch`, `tickets.minute` и `webhooks.dispatch`.
- [ ] Если служба не запускается: `hubc logs web` или `hubc logs worker`. Ошибка окружения называет переменную и причину.

Скопировать сценарий в `/opt/smartup-hub/host-watch.sh`, права 700. Если тома базы лежат не в `/var/lib/docker/volumes`, задать `HOST_WATCH_PATHS` в `Environment=` службы.  
  ```ini
  [Unit]
  Description=Smartup Hub: отметка ресурсов сервера
  [Service]
  Type=oneshot
  ExecStart=/opt/smartup-hub/host-watch.sh
  ```

  ```ini
  [Unit]
  Description=Smartup Hub: отметка ресурсов раз в 5 минут
  [Timer]
  OnBootSec=2min
  OnUnitActiveSec=5min
  [Install]
  WantedBy=timers.target
  ```

| Журнал инцидентов | `docs/runbooks/incident.md`, раздел 7 | Инциденты и сбросы доступа | Без срока | Владелец и дежурные |

Все журналы, кроме журнала аудита, не уходят за пределы сервера (отклонение ASVS V16.4.3, принято по рекомендации 5 плана M9).

- [ ] Ротация журналов сценариев: файл `/etc/logrotate.d/smartup-hub` со строкой `/var/log/hub-*.log { daily rotate 30 compress missingok notifempty }`.

## 12а. Вторая копия портала (по необходимости)

Одна копия держит пилот. Вторая нужна для выкладки без простоя и на случай зависания процесса; от гибели сервера она не спасает: обе копии на одном сервере (решение 0039). Вынос базы и копий на разные серверы: этап роста.

- [ ] В `.env`: `DB_POOL_MAX=6` (у каждого процесса два пула по 6 соединений; две копии портала и фоновый процесс вместе занимают до 45 соединений из 100) и `HUB_UPSTREAMS="web:3000 web2:3000"`.
- [ ] Запуск: `hubc --profile replica up -d`. Дальше все команды `hubc up` идут с `--profile replica`, иначе вторая копия не обновится.
- [ ] Проверка: `hubc --profile replica ps` показывает `web` и `web2` в состоянии healthy; `hubc stop web`, сайт продолжает открываться; `hubc start web`.
- [ ] Память: вторая копия занимает ещё до 768 МБ. На сервере 8 ГБ сумма пределов станет 7,5 ГБ: перед включением уменьшить `CLAMAV_MEM_LIMIT` или взять сервер больше.
- [ ] Выкладка без простоя: после миграций `hubc --profile replica up -d --no-deps web`, дождаться healthy, затем `hubc --profile replica up -d --no-deps web2`, затем `worker`. Пока копии разных версий работают вместе, страница, открытая на старой версии, может получить ошибку отправки формы: человек обновляет страницу. Миграции пишутся совместимыми с предыдущей версией кода (ТЗ 13.6).
- [ ] Фоновый процесс остаётся один. Запускать два можно: задачи по расписанию библиотека очереди ставит один раз на всех, но пользы при нынешней нагрузке нет.

## 13. Выкладка новой версии и откат

- [ ] Прочитать отчёт новой вехи (`docs/plans/M<n>-report.md`), раздел "Что нужно для staging": там шаги, которые появились с этой версией.
- [ ] Собрать образ новой версии (шаг 7) и записать оба тега: прежний и новый.
- [ ] Если в новой версии изменились `compose.prod.yaml` или `Caddyfile`, скопировать их в `/opt/smartup-hub`.
- [ ] Если изменился `compose.prod.yaml` (сети, привилегии, параметры служб), частичного перезапуска мало: после миграций выполнить `hubc up -d` без имён служб. Все службы пересоздаются, база перезапускается (простой до минуты). Так нужно при переходе на версию волны 1 плана аудита: в ней одна общая сеть заменена тремя, и Caddy, оставшийся в старой сети, не найдёт портал (ответ 502). Выкладку такой версии назначать на нерабочее время.
- [ ] Идентификатор нового образа: `docker image inspect --format '{{.Id}}' smartup-hub:<новая версия>`. Затем `export HUB_IMAGE=sha256:<идентификатор нового образа>` (и то же значение в `~/.bashrc`), затем миграции: `hubc run --rm migrate`.
- [ ] Перезапуск: `hubc up -d web worker` (если `compose.prod.yaml` не менялся; иначе `hubc up -d`, см. выше).
- [ ] Проверка: `curl -fsS https://<домен>/api/ready` возвращает `"status":"ready"`, в `hubc logs worker` есть "Фоновый процесс запущен".
- [ ] Откат при неудаче: `export HUB_IMAGE=sha256:<идентификатор прежнего образа>` и `hubc up -d web worker`. Миграции пишутся совместимыми с предыдущей версией кода (ТЗ 13.6), поэтому база не откатывается.

## 14. Что известно заранее

- Посетитель, у которого заблокирован `challenges.cloudflare.com`, не пройдёт проверку "не робот" (решение 0018).
- Первое письмо и первую привязку Telegram проверить вручную: поля запросов Resend и Telegram взяты из описания API (решение 0018).
- Куки входа на https называются `__Host-hub.*` (решение 0021): портал работает только по адресу из `HUB_URL`.
- При первой выкладке версии с вехой M3 открытые обращения прежних версий получают сроки от момента создания и могут сразу попасть в "Срок нарушен". Это ожидаемо, уведомлений до M4 нет.
- Ночную очистку служебных таблиц выполняет фоновый процесс в 03:00 по Ташкенту. Отдельное расписание cron для неё не нужно; ручной запуск: `hub maintenance:cleanup`.
- Сотрудник потерял телефон с кодами: `hub staff:reset --email <адрес>` удаляет пароль и второй фактор, завершает сессии и печатает новую ссылку.
