# Восстановление базы из резервной копии

ТЗ 13.7. Копия считается существующей только после проверки восстановления: раз в месяц на staging, результат записывается в таблицу в конце этого файла. Цель: восстановление не дольше 4 часов.

Копии делает `scripts/ops/backup.sh` (на сервере `/opt/smartup-hub/backup.sh`): `pg_dump` шифруется открытым ключом `age` до записи на диск и выгружается в отдельный бакет. Закрытый ключ хранится только в менеджере паролей владельца, на сервере его нет.

Ниже `hubc` означает `docker compose -f /opt/smartup-hub/compose.prod.yaml`.

## Что понадобится

- Файл копии `hub-<дата>.dump.age` из бакета копий.
- Закрытый ключ `age` (файл `key.txt`) из менеджера паролей.
- Секреты портала: `.env`, `.env.migrate`, `secrets/pg_superuser` из зашифрованного архива в менеджере паролей. Файл `.env.bootstrap` на сервере не хранится: он собирается заново по шагу 8 памятки запуска из тех же паролей.
- Образ портала той версии, которая работала в момент копии, или новее.

## Порядок

1. Подготовить сервер по `docs/runbooks/launch.md`, шаги 1 и 8: Docker, каталог `/opt/smartup-hub`, файлы и секреты. Портал и фоновый процесс не запускать.
2. Запустить пустую базу и создать роли:

   ```bash
   hubc up -d postgres
   hubc run --rm bootstrap
   ```

3. Скачать копию и закрытый ключ на сервер. Ключ положить во временный каталог в памяти, чтобы он не остался на диске:

   ```bash
   rclone copy r2-backups:hub-backups/hub-<дата>.dump.age /var/backups/smartup-hub/
   install -m 600 /dev/null /dev/shm/key.txt   # затем вставить содержимое ключа
   ```

4. Расшифровать и восстановить одним потоком, без открытого файла на диске:

   ```bash
   age -d -i /dev/shm/key.txt /var/backups/smartup-hub/hub-<дата>.dump.age \
     | hubc exec -T postgres pg_restore -U postgres -d hub --clean --if-exists --exit-on-error
   ```

5. Удалить ключ с сервера: `shred -u /dev/shm/key.txt`.
6. Применить миграции (если образ новее копии) и запустить службы:

   ```bash
   hubc run --rm migrate
   hubc up -d
   ```

7. Проверить:
   - `curl -fsS https://<домен>/api/ready` возвращает `"status":"ready"`;
   - сотрудник входит, последнее обращение перед аварией на месте;
   - политики на месте: `hubc exec -T postgres psql -U postgres -d hub -Atc "select count(*) from pg_class where relkind = 'r' and relnamespace = 'public'::regnamespace and not (relrowsecurity and relforcerowsecurity)"` возвращает 0;
   - в `hubc logs worker` есть "Фоновый процесс запущен".
8. Файлы вложений лежат в R2 и копией базы не затрагиваются. Если бакет файлов тоже потерян, восстановить версии объектов средствами R2 (ТЗ 13.7).
9. После восстановления на staging удалить данные production со staging.

## Что теряется

Всё, что произошло после момента копии: до 24 часов при ночной копии. Цель ТЗ в 15 минут достигается непрерывным архивом pgBackRest (веха M9, по плану аудита переносится на время до первого клиента). Письма клиентов, пришедшие после копии, остаются у почтового сервиса: вебхук приёма Resend можно отправить повторно из его кабинета.
