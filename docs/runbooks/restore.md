# Восстановление базы из резервной копии

ТЗ 13.7. Копия считается существующей только после проверки восстановления: раз в месяц на staging, результат записывается в таблицу в конце этого файла. Цель: восстановление не дольше 4 часов.

Копии делает `scripts/ops/backup.sh` (на сервере `/opt/smartup-hub/backup.sh`): `pg_dump` шифруется открытым ключом `age` до записи на диск и выгружается в отдельный бакет. Закрытый ключ хранится только в менеджере паролей владельца, на сервере его нет.

Ниже `hubc` означает `docker compose -f /opt/smartup-hub/compose.prod.yaml`.

## Что понадобится

- Файл копии `hub-<дата>.dump.age` из бакета копий.
- Закрытый ключ `age` (файл `key.txt`) из менеджера паролей.
- Секреты портала: `.env`, `.env.migrate`, `secrets/pg_superuser` из зашифрованного архива в менеджере паролей. Файл `.env.bootstrap` на сервере не хранится: он собирается заново по шагу 8 памятки запуска из тех же паролей.
- Образ портала той версии, которая работала в момент копии, или новее.

## Порядок

1. Подготовить сервер по `docs/runbooks/launch.md`, шаги 1 и 8: Docker, каталог `/opt/smartup-hub`, файлы и секреты. Портал и фоновый процесс не запускать.
2. Запустить пустую базу и создать роли:

   ```bash
   hubc up -d postgres
   hubc run --rm bootstrap
   ```

3. Скачать копию и закрытый ключ на сервер. Ключ положить во временный каталог в памяти, чтобы он не остался на диске:

   ```bash
   rclone copy r2-backups:hub-backups/hub-<дата>.dump.age /var/backups/smartup-hub/
   install -m 600 /dev/null /dev/shm/key.txt   # затем вставить содержимое ключа
   ```

4. Расшифровать и восстановить одним потоком, без открытого файла на диске:

   ```bash
   age -d -i /dev/shm/key.txt /var/backups/smartup-hub/hub-<дата>.dump.age \
     | hubc exec -T postgres pg_restore -U postgres -d hub --clean --if-exists --exit-on-error
   ```

5. Удалить ключ с сервера: `shred -u /dev/shm/key.txt`.
6. Применить миграции (если образ новее копии) и запустить службы:

   ```bash
   hubc run --rm migrate
   hubc up -d
   ```

7. Проверить:
   - `curl -fsS https://<домен>/api/ready` возвращает `"status":"ready"`;
   - сотрудник входит, последнее обращение перед аварией на месте;
   - политики на месте: `hubc exec -T postgres psql -U postgres -d hub -Atc "select count(*) from pg_class where relkind = 'r' and relnamespace = 'public'::regnamespace and not (relrowsecurity and relforcerowsecurity)"` возвращает 0;
   - функции пересчёта счётчиков идей принадлежат роли `hub_hdi_counter` (решение 0065; без неё голос за идею не пересчитывается): `hubc exec -T postgres psql -U postgres -d hub -Atc "select p.proname, pg_get_userbyid(p.proowner) from pg_proc p where p.pronamespace = 'app'::regnamespace and p.proname like 'hdi\_%' and p.prosecdef order by 1"` называет у каждой функции `hub_hdi_counter`. Если роль другая или функций нет, восстановление шло без `bootstrap` (шаг 2): выполнить его и восстановить заново;
   - в `hubc logs worker` есть "Фоновый процесс запущен";
   - фоновый процесс берёт задачи: `curl -fsS https://<домен>/api/ready/worker` через 1-2 минуты возвращает `"status":"ready"`.
8. Если включён поиск на Typesense (`SEARCH_PROVIDER=typesense`, план W6): индекс производный и строится заново из восстановленной базы, снимков Typesense нет. `hubc exec worker node hub.mjs search:reindex`, затем `hubc exec worker node hub.mjs search:status` показывает число документов каждой коллекции и пустую очередь. Пока индекс не построен, поиск отдаёт только то, что уже есть в Typesense: чего нет в индексе, не находится. Чтобы на это время искать прежним путём, задать `SEARCH_PROVIDER=postgres` в `.env` и перезапустить `web`, после переиндексации вернуть `typesense`.
9. Файлы вложений лежат в R2 и копией базы не затрагиваются. Если бакет файлов тоже потерян, восстановить версии объектов средствами R2 (ТЗ 13.7).
10. После восстановления на staging удалить данные production со staging.

## Восстановление на момент времени

Нужно, когда ночной копии мало: данные испорчены ошибкой или действием, и вернуться надо на минуту до этого, либо сервер потерян, а с ночной копии прошло много часов. Работает, если на сервере был включён непрерывный архив (`docs/runbooks/launch.md`, шаг "Непрерывный архив"). Решение 0039.

Что понадобится сверх списка выше:

- Базовая копия `base-<дата>.tar.age` из бакета копий, каталог `base`: последняя, сделанная **до** нужного момента.
- Сегменты журнала из каталога `wal` бакета: все, выгруженные после этой базовой копии. Проще скачать каталог целиком.
- Момент времени с часовым поясом, например `2026-11-23 10:15:00+05`. Если нужен момент "до ошибки", берите на минуту раньше первой записи об ошибке.

Порядок:

1. Остановить портал и фоновый процесс: `hubc stop web worker`. Если прежняя база ещё жива, не удалять её том: восстановление идёт в новый каталог.
2. Скачать базовую копию и сегменты: `rclone copy r2-backups:hub-backups/base/base-<дата>.tar.age ./` и `rclone copy r2-backups:hub-backups/wal ./wal`.
3. Создать пустой каталог данных, например `/opt/smartup-hub/pg-restore`, и принести закрытый ключ `age` на сервер на время работ.
4. Расшифровать копию и сегменты и записать настройки восстановления:

   ```bash
   BACKUP_IDENTITY=./key.txt WAL_RESTORE_PATH=/var/lib/postgresql/18/docker/wal-restore \
     /opt/smartup-hub/restore-pitr.sh ./base-<дата>.tar.age ./wal '2026-11-23 10:15:00+05' /opt/smartup-hub/pg-restore
   sudo chown -R 999:999 /opt/smartup-hub/pg-restore && sudo chmod 700 /opt/smartup-hub/pg-restore
   ```

   Сценарий отказывает, если каталог не пуст или момент времени записан без часового пояса.
5. Запустить базу на восстановленном каталоге отдельным контейнером и дождаться конца восстановления:

   ```bash
   docker run -d --name hub-pg-restore -v /opt/smartup-hub/pg-restore:/var/lib/postgresql/18/docker pgvector/pgvector:pg18@<digest из compose.prod.yaml>
   docker exec hub-pg-restore psql -U postgres -tAc "select pg_is_in_recovery()"   # ждать ответа f
   ```

   В журнале контейнера появится строка `recovery stopping before commit of transaction ...` с временем остановки.
6. Проверить данные: последние обращения, число строк в основных таблицах, что записей после нужного момента нет.
7. Перенести данные в рабочую базу одним из двух способов. Проще и надёжнее первый.
   - Снять логическую копию с восстановленной базы (`docker exec hub-pg-restore pg_dump -U postgres -Fc hub > restored.dump`) и восстановить её по разделу "Порядок" выше, начиная с шага про `pg_restore`.
   - Либо остановить стек, заменить содержимое тома `pg_data` восстановленным каталогом и запустить стек. Архив журнала в восстановленном каталоге выключен настройкой в `postgresql.auto.conf`: перед запуском убрать из файла четыре строки, которые дописал сценарий.
8. Удалить закрытый ключ с сервера, расшифрованные сегменты и каталог восстановления. Прежние сегменты журнала к новой истории базы не подходят, а имена новых сегментов совпадут с прежними. Поэтому до включения архива перенести в бакете каталоги `wal` и `base` в каталог с датой (например `rclone moveto <бакет>/wal <бакет>/до-2026-12-01/wal`), очистить `/opt/smartup-hub/wal-archive` и только потом сделать новую базовую копию: `base-backup.sh`.
9. Запустить портал и фоновый процесс, проверить `https://<домен>/api/ready`.

## Что теряется

Без непрерывного архива: всё, что произошло после ночной копии, до 24 часов. С включённым архивом (раздел "Восстановление на момент времени"): до 10 минут, столько занимает закрытие сегмента журнала (5 минут) и его выгрузка. Цель ТЗ 15 минут. Архив сделан средствами PostgreSQL и сценариями проекта, без pgBackRest: новых зависимостей нет (решение 0039). Письма клиентов, пришедшие после копии, остаются у почтового сервиса: вебхук приёма Resend можно отправить повторно из его кабинета.
